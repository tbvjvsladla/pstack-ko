# 이슈 재현 및 수정 (Reproduce and fix issues)

소스 스레드에 신뢰할 수 있는 트리아지 마커가 올라올 때까지 기다립니다. 대상 앱의 실제 UI를 통해 정확한 증상을 재현합니다. 기존 수정 사항이 존재하면 이를 검증합니다. 확인된 재현이 이루어진 후에만 범위가 제한된(bounded) 수정을 시도합니다.

자동화가 제공한 외부 Benny 설정을 로드합니다. 설정, 필수 액션, 컨트롤 어댑터 또는 작성 완료된 기능 맵(feature map)이 누락되어 있다면 안전하게 실패 후 종료(fail closed)합니다.

## 엄격한 안전 규칙 (Hard safety rules)

- 어떤 작업이든 시작하기 전에 소스 채널과 루트 스레드 좌표를 고정(freeze)하세요.
- 소스 채널에 루트 메시지를 게시하는 일은 절대 없어야 합니다.
- 소스 스레드에 게시하기 전에는 매번 소스 부모 메시지를 사전 점검(preflight)하세요.
- 코디네이터만 유일하게 Slack에 게시할 수 있습니다.
- 위임된 분석 워커는 읽기 전용이며 발견 사항이나 미디어 검토 메모만 반환합니다.
- 수정 단계의 코드 워커는 그 실행 환경에서 Slack 자격 증명과 모든 Slack 쓰기 액션이 배제되었음이 입증된 경우에만 편집할 수 있습니다. 그렇지 않으면 코디네이터가 직접 편집합니다.
- 모든 하위(child) 프롬프트는 `SendSlackMessage`, `PostToSlack`, `chat.postMessage` 및 그 밖의 모든 Slack 쓰기 작업을 명시적으로 금지해야 합니다.
- 하위 에이전트에게 Slack 토큰, 게시 지침, 게시용 소스 좌표 또는 외부 보고 권한을 절대 부여하지 마세요.
- 하위 에이전트가 실행되기 위해 Slack 쓰기 권한이 필요하다면 그 에이전트를 실행하지 마세요.
- 유틸리티 봇은 증거 소스일 뿐입니다. 사람이 명시적으로 수정을 위임한 경우가 아니라면 봇은 수정 소유권을 갖지 않습니다.
- 구별 가능한 정확한 증상이 실제 UI 상호작용을 통해 두 번 나타나야 합니다.
- 상태 검사(state inspection)는 관찰 내용을 확인하는 용도로만 쓸 수 있습니다. 증상을 주입하거나 강제로 만들어내서는 안 됩니다.
- 확인된 재현이 없으면 직접 작성하는 수정도 없습니다.
- 기존 풀 리퀘스트나 커밋이 있으면 실행 모드를 검증(verify) 모드로 전환합니다. 기존 작업을 덮어쓰며 새로 작성하지 마세요.
- `github.com` 풀 리퀘스트 링크를 사용하세요.
- 캡처 이미지, 녹화본, 로그, 토큰이 소스 컨트롤에 포함되지 않게 하세요.
- 위임된 분석에는 pstack의 `principle-guard-the-context-window`를 사용하세요.
- 재현, 수정, 검증 전반에 걸쳐 pstack의 `principle-sequence-verifiable-units`, `principle-fix-root-causes`, `principle-prove-it-works`를 적용하세요.

## 1. 소스 좌표 고정

작업 목록을 만들거나 위임하기 전에 다음을 수행합니다:

1. 트리거 채널이 설정된 소스 채널과 일치하는지 확인합니다.
2. `trigger.thread_ts`가 존재하면 `SOURCE_THREAD_TS`를 그 값으로 설정합니다. 없으면 `trigger.ts`를 사용합니다.
3. `SOURCE_THREAD_TS`가 비어 있지 않은지 확인합니다.
4. `SOURCE_CHANNEL_ID`와 `SOURCE_THREAD_TS`를 불변(immutable) 값으로 저장합니다.
5. 소스 스레드를 읽고 루트 메시지가 그 정확한 좌표를 가지고 있는지 검증합니다.
6. 소스 퍼머링크(permalink)를 가져옵니다.

이 값들을 답글 타임스탬프, 운영 채널 타임스탬프 또는 상태 메시지 타임스탬프로 절대 교체하지 마세요.

소스 채널에 게시하기 전에는 매번 다음을 수행합니다:

1. 불변 좌표로 스레드를 읽습니다.
2. 부모 메시지가 존재하고, 삭제되지 않았으며, 여전히 소스 채널에 속해 있는지 확인합니다.
3. 오직 `channel=SOURCE_CHANNEL_ID` 및 `thread_ts=SOURCE_THREAD_TS`를 지정해서만 전송합니다.
4. 스레드를 다시 읽고 새 메시지가 답글로 달렸는지 검증합니다.

어느 점검이라도 실패하면 아무것도 게시하지 마세요. 루트 위치나 폴백(fallback) 채널에 재시도하는 일은 절대 없어야 합니다.

## 2. 트리아지 계약 대기

설정된 판정 대기 예산(verdict budget) 동안 소스 스레드를 감시합니다. 기다리는 동안에는 침묵을 유지합니다.

다음 조건을 모두 만족할 때만 판정(verdict)을 수락합니다:

- 작성자가 `slack.triage_identity_user_id`와 일치합니다.
- `SOURCE_THREAD_TS` 아래의 답글입니다.
- 설정된 마커를 정확히 하나 포함하고 있습니다.

공개 마커 형식:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

오직 `bug` 또는 `performance`일 때만 진행합니다. 선택적인 트래커 URL이 있다면 캡처합니다. `other`, 판정 누락, 신뢰할 수 없는 작성자, 충돌하는 마커 또는 타임아웃의 경우 아무 메시지도 남기지 않고 조용히 중단합니다.

이 마커는 비공개 봇 ID와 자유 형식 판정 매칭을 대체합니다.

## 3. 소유권 및 수정 아티팩트 게이트 적용

작업을 시작하기 직전에 스레드를 다시 읽습니다.

### 누군가 명시적으로 수정 중인 경우

사람이 수정을 명확히 자처하거나, 구체적인 구현 계획을 제시하거나, 다른 에이전트에게 구현, 패치, 수정 또는 풀 리퀘스트 생성을 요청한 경우 즉시 중단합니다.

다음 경우는 수정 소유권으로 취급하지 마세요:

- 봇이 증거를 요약하는 경우.
- 도구가 로그나 티켓을 조회하는 경우.
- 누군가 봇에게 진단, 설명, 검사 또는 재현을 요청하는 경우.
- 봇이 구현에 동의하지 않은 채 원인 가설만 게시하는 경우.

봇의 존재 여부가 아니라 요청된 행동이 무엇인지를 기준으로 판단하세요.

### 수정 아티팩트가 이미 존재하는 경우

열려 있는 풀 리퀘스트나 머지된 커밋이 해당 제보를 해결할 가능성이 높다면 `references/verify-existing-fix.md`로 전환합니다.

아티팩트는 스레드, 트래커 이슈, 저장소 히스토리 또는 풀 리퀘스트 검색에서 나올 수 있습니다. 커밋이나 풀 리퀘스트가 없는 단순 주장은 수정 아티팩트가 아닙니다.

사람이 작업을 소유하고 있지만 아직 아티팩트를 내놓지 않은 경우에도 중단하세요. 사람과 경쟁하지 마세요.

## 4. 선택적 운영(operations) 스레드 열기

`slack.operations_channel_id`가 설정되어 있다면 코디네이터는 그곳에 루트 상태 메시지를 하나 생성할 수 있습니다. 이는 재현 워크플로우에서 허용되는 유일한 루트 게시물입니다.

그 좌표를 `OPERATIONS_CHANNEL_ID`와 `OPERATIONS_THREAD_TS`로 저장하세요. 이를 소스 좌표와 절대 혼동하지 마세요.

설정된 일반 유니코드 상태 문자열을 사용하세요. 상태 텍스트는 짧게 유지합니다:

- Reproducing
- Could not reproduce
- Blocked
- Reproduced
- Verifying existing fix
- Attempting bounded fix
- Draft pull request opened
- Fix did not land

설정된 Cursor Slack 액션을 우선 사용하세요. `BENNY_SLACK_BOT_TOKEN`은 이 단일 상태 메시지 편집처럼 부족한 좁은 범위의 기능을 위해 사용자가 명시적으로 설정한 경우에만 사용하세요. 토큰을 워커에게 절대 노출하지 마세요.

운영 채널이 설정되지 않았다면 상세 상태는 자동화 실행 출력에 유지하세요. 소스 채널의 루트 메시지로 대체하지 마세요.

## 5. 컨트롤 어댑터 로드 및 점검

`references/control-adapter.md`와 `control.feature_map_path`에 있는 완성된 맵을 읽은 뒤, `control.skill_name`에 지정된 스킬을 호출합니다.

제보된 사용자 경로와 일치하는 기능 맵 섹션을 찾습니다. 앱을 구동하기 전에 해당 섹션을 먼저 읽으세요. 해당 기능을 다루는 섹션이 없다면 경로나 셀렉터를 임의로 지어내는 대신 실행 상태를 `Blocked`로 표시하세요.

다음 일곱 가지 기능이 모두 필요합니다:

1. 설정된 대상 앱과 테스트 환경을 기동(bring up)합니다.
2. 매핑된 기능을 탐색하고 문서화된 상태들을 실행해 봅니다.
3. 클릭, 타이핑, 키 입력, 스크롤, 드래그, 리사이즈 또는 내비게이션으로 실제 UI를 구동합니다.
4. 상태를 변경(mutate)하지 않고 검사합니다.
5. 스크린샷을 캡처합니다.
6. 화면 녹화를 시작하고 중지합니다.
7. 프로세스, 세션, 프로필 및 임시 데이터를 정리(clean up)합니다.

어댑터가 없거나 필수 기능 중 하나라도 누락된 경우 운영 상태를 `Blocked`로 표시하고 중단하세요. 스크린샷, 단위 테스트, 상태 변조 또는 소스 코드 읽기를 UI 재현인 것처럼 가장하지 마세요.

## 6. 제보 내용 분석

전체 소스 스레드와 (존재하는 경우) 트래커 이슈를 읽습니다.

다음을 수집합니다:

- 정확한 액션 경로
- 기대 동작(Expected behavior)
- 관찰된 동작(Observed behavior)
- 두 동작이 갈라지는 구별 가능한 상태(Discriminating state)
- 발생 빈도
- 버전, 환경 및 플랫폼
- 첨부 파일 및 에러 시그니처
- 후보 코드 영역

스크린샷과 비디오를 검사합니다. 유용한 경우 코드 히스토리, 테스트 아이디어, 영향 반경(blast-radius) 매핑 및 미디어 검토를 위해 읽기 전용 병렬 워커를 사용하세요. 각 워커에는 좁은 범위의 질문과 Slack 쓰기 금지 지침을 전달합니다.

pstack의 `how` 스킬을 사용하여 저장소 전반에서 액션을 추적하세요. 회귀 히스토리와 방어적 코드를 파악하기 위해 `why`를 사용하세요. 경쟁하는 원인 가설들을 세우고 이를 가려낼 수 있는 증거를 식별하세요.

## 7. 재현 (Reproduce)

컨트롤 어댑터를 통해 대상 앱을 기동합니다.

행동을 시작하기 전에 올바른 앱, 워크스페이스, 계정, 데이터셋 및 기능 상태인지 확인하세요. 안정적인 앱 마커를 사용하세요. 창 순서나 익숙한 제목에만 의존하지 마세요.

실제 UI 액션을 통해 제보된 경로를 구동합니다.

재현되었다고 선언하기 전에 다음을 수행합니다:

1. 올바른 최종 상태를 명시합니다.
2. 깨진(broken) 최종 상태를 명시합니다.
3. 두 상태가 갈라지는 지점에 도달합니다.
4. 깨진 상태를 관찰합니다.
5. 두 번째 시도가 독립적으로 이루어질 수 있도록 충분한 상태를 초기화(reset)합니다.
6. 동일한 경로를 반복하고 동일한 깨진 상태를 다시 관찰합니다.
7. 가능한 경우 실제 상태 값을 교차 검증(cross-check)합니다.

예상된 대화상자, 로딩 상태 또는 셋업 단계는 버그가 아닙니다. 올바른 동작과 깨진 동작을 구별해 주는 최종 상태를 캡처하세요.

설정된 재현 예산을 사용하세요. 예산 내에 증상이 재현되지 않으면 깔끔하게 `Could not reproduce` 결과를 보고합니다. 환경에서 필수 기능을 제공할 수 없는 경우 `Blocked`를 보고하고 무엇이 누락되었는지 명시합니다.

## 8. 증거 캡처 및 검토

성공적인 재현의 경우:

- 증상이 나타나는 전체 경로를 녹화합니다.
- 깨진 최종 상태의 스크린샷을 캡처합니다.
- 정확한 단계와 관찰된 상태를 담은 짧은 메모를 저장합니다.
- 아티팩트는 설정된 임시 아티팩트 디렉터리에 보관합니다.

읽기 전용 미디어 리뷰어에게 단 하나의 질문에 답하게 하세요: 증거에 구별 가능한 깨진 상태가 눈으로 확인될 만큼 명확히 나타나는가?

답이 아니오이거나 불확실하면 재현은 확인되지 않은 것입니다. 더 나은 증거를 캡처하거나 `Could not reproduce`를 사용하세요.

상세한 증거는 운영 스레드가 설정된 경우에만 그곳에 게시하세요. 소스 스레드 업데이트는 간결하게 유지합니다.

## 9. 재현 결과 보고

먼저 운영 상태를 업데이트합니다.

`Could not reproduce` 또는 `Blocked`의 경우 소스 스레드에는 아무것도 게시하지 마세요. 결과는 운영 스레드나 실행 출력에 남깁니다.

확인된 재현의 경우 소스 사전 점검(preflight)을 실행하고 요청받지 않은(unprompted) 소스 답글을 최대 하나만 게시합니다:

- 이슈가 재현되었음을 알립니다.
- 운영 증거 스레드가 존재하는 경우 링크합니다.
- 최대 세 가지의 짧은 발견 사항을 포함합니다.
- 트래커 이슈가 존재하는 경우 링크합니다.
- 기본적으로 오너를 호출(ping)하지 않습니다.

설정된 Slack 액션이 증거를 동일한 소스 스레드 안에 유지하고 조직의 보존 정책이 이를 허용하는 경우에만 증거를 첨부하세요.

설정된 거부 대기 시간(rejection window) 동안 기다립니다. 사람이 셋업이나 해석이 잘못되었음을 보여주면 재현을 한 번 교정합니다. 유효한 거부 없이 대기 시간이 닫힐 때까지 수정 단계를 시작하지 마세요.

## 10. 기존 수정 사항 검증

수정 아티팩트가 존재하는 경우 `references/verify-existing-fix.md`를 따릅니다.

검증은 베이스라인에서 증상이 나타나고 패치된 빌드에서 증상이 사라짐을 보여주어야 합니다. 두 경로 모두 실제 UI를 두 번씩 사용합니다.

기존 수정을 편집하거나, 경쟁하는 패치를 추가하거나, 대체 풀 리퀘스트를 열지 마세요.

## 11. 범위가 제한된 수정(Bounded fix) 자격 판별

다음 조건이 모두 성립할 때만 수정을 시도합니다:

- 결과가 명확히 확인된 재현(confirmed repro)입니다.
- 미디어 검토에서 깨진 최종 상태가 확인되었습니다.
- 기존 수정 아티팩트가 나타나지 않았습니다.
- 거부 대기 시간 동안 아무도 수정을 자처하지 않았습니다.
- 런타임 증거가 근본 원인을 식별합니다.
- 예상되는 변경이 설정된 수정 예산과 저장소 범위 안에 들어옵니다.
- 컨트롤 어댑터가 베이스라인 빌드와 패치된 빌드를 모두 실행할 수 있습니다.

어느 조건이라도 충족되지 않으면 재현 보고서만 유지하고 풀 리퀘스트 없이 중단합니다.

게이트를 통과하면 운영 상태를 `Attempting bounded fix`로 업데이트합니다.

## 12. 근본 원인 파악 및 구현

코디네이터가 모든 Slack 게시물, 최종 diff 검토, 커밋 및 풀 리퀘스트를 소유합니다.

읽기 전용 워커는 다음 작업을 수행할 수 있습니다:

- 코드 및 히스토리 추적
- 테스트 제안
- 영향 반경(blast radius) 매핑
- diff 검토
- 미디어 검토

워커는 편집하거나, 외부 쓰기를 실행하거나, 상태를 게시하거나, 수정을 소유하지 않습니다.

도구 격리(tool isolation)를 통해 워커에서 Slack 자격 증명과 모든 Slack 쓰기 액션이 제거된 경우에만 이 단계에서 좁은 범위의 코드 편집을 위임할 수 있습니다. 그 경우에도 워커의 프롬프트에는 명시적인 Slack 쓰기 금지 지침이 포함되어야 합니다. 코디네이터가 편집 내용을 검토하고 필수 테스트를 실행하거나 검증합니다. 도구 격리가 불확실하면 코디네이터가 직접 편집을 수행하세요.

런타임 증거로 메커니즘을 확인하세요. 편집하기 전에 경쟁 가설들을 배제하세요.

정당화될 수 있는 가장 작은 변경으로 근본 원인을 수정합니다.

- 저렴한 로컬 테스트 대상이 있다면 pstack의 `tdd` 스킬을 호출하고, 수정 전에 실패하는 테스트를 먼저 작성합니다.
- 경로가 비용이 많이 들거나 불명확하거나 통합 비중이 커서 TDD를 건너뛴 경우 그 이유를 명시합니다.
- 관련 없는 코드 정리(cleanup)는 배제합니다.
- 변경 사항이 설정된 공수나 위험 예산을 초과해 커지면 중단합니다.

## 13. 수정 증명 (Prove the fix)

원래의 베이스라인 증거를 보관합니다.

패치된 빌드에서 다음을 수행합니다:

1. 동일한 실제 UI 경로를 실행합니다.
2. 이를 두 번 반복합니다.
3. 깨진 상태가 사라졌음을 보여줍니다.
4. 그 자리에 기대 상태가 나타남을 보여줍니다.
5. 수정 후(after) 녹화본과 스크린샷을 캡처합니다.
6. 베이스라인에 사용했던 것과 동일한 실제 상태 값을 교차 검증합니다.

컴파일 성공, 단위 테스트 통과, 코드 리뷰 또는 그럴듯해 보이는 diff는 수정 후 증거가 아닙니다.

집중 테스트를 실행한 뒤 변경된 동작 주변의 영향 반경을 스모크 테스트하세요. 변경이 영향을 미칠 수 있는 인접 상태, 입력, 권한, 플랫폼 및 실패 경로를 다루세요. 회귀(regression)가 남아 있다면 풀 리퀘스트를 열지 말고 중단하세요.

## 14. 드래프트 풀 리퀘스트 열기

전후(before-and-after) 증명이 완료된 후에만 다음을 수행합니다:

- 관련 없는 변경 사항이나 시크릿이 없는지 최종 diff를 검토합니다.
- 저장소의 필수 검사를 실행합니다.
- 저장소 워크플로우가 허용하는 경우 정돈된 작은 커밋들을 생성합니다.
- 드래프트 풀 리퀘스트를 엽니다. 이 워크플로우에서 절대 머지하거나 배포하지 마세요.
- 트래커가 지원하는 풀 리퀘스트 문법을 사용하여 설정된 트래커 이슈를 링크합니다.
- 설정된 공개 URL 형식(일반적으로 `https://github.com/{owner}/{repo}/pull/{number}`)을 사용합니다.
- 재현 단계, 근본 원인, 테스트 결과, 전후 증거 및 영향 반경 점검 결과를 포함합니다.
- 풀 리퀘스트 텍스트와 모든 Slack 업데이트를 pstack의 `unslop` 스킬로 다듬습니다.

풀 리퀘스트 생성이 실패하면 성공했다고 주장하지 마세요. 실행 출력에 커밋이나 브랜치 상태를 유지하고 운영 상태를 `Fix did not land`로 표시하세요.

성공 시 운영 상태를 `Draft pull request opened`로 표시하고, 운영 스레드에 풀 리퀘스트 링크가 포함된 간결한 답글을 하나 게시합니다. 두 번째 소스 채널 루트 메시지나 요청받지 않은 소스 답글을 생성하지 마세요.

## 15. 후속 조치 및 정리 (Follow-ups and cleanup)

한 번의 후속 조치 시간(follow-up window) 동안 설정된 운영 스레드를 감시합니다.

- 이미 수집된 증거를 바탕으로 직접적인 질문에 답합니다.
- 셋업을 무효화하는 구체적인 교정 사항이 제기되면 이를 한 번 반영하여 재현을 1회 다시 실행합니다.
- 사람들의 조율 과정이나 부수적인 잡담에는 끼어들지 않습니다.
- 중단 요청을 받으면 즉시 중단합니다.

항상 컨트롤 어댑터의 정리(cleanup) 기능을 호출하세요. 아티팩트는 설정된 보존 정책이 허용하는 기간 동안만 보관합니다.
