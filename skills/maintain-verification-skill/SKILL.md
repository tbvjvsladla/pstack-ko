# 검증 스킬 유지보수 (Maintain a verification skill)

기능 맵(feature map)은 앱이 변경되는 순간부터 부패하기 시작합니다. 이 스킬은 `/create-verification-skill`로 생성된 스킬(또는 기능 맵을 갖춘 모든 프로젝트 로컬 검증 스킬)을 위한 유지보수 루프입니다. 엄격함의 단위는 개별 문장이 아니라 **기능(feature)**입니다: 모든 기능 파일을 소스 코드와 대조해 점검하고 모든 기능을 라이브로 직접 구동하되, 불릿 하나하나마다 세션을 새로 여닫는 식의 비효율은 피합니다.

## 결과 분류 (Outcomes)

아래 중 하나를 선택하고 무엇인지 명시하세요:

- **clean (깨끗함)** — 모든 기능에 대해 소스 대조 및 라이브 커버리지를 완료했으며, 출하할 만한 변경사항이 없습니다. 브랜치도 PR도 만들지 않습니다.
- **changed (변경됨)** — 증명된 문서, 하네스, 또는 맵 수정사항을 단 하나의 PR로 출하합니다.
- **blocked (차단됨)** — 커버리지를 끝마칠 수 없었거나 증명된 수정사항을 안전하게 출하할 수 없었습니다. 무엇이 작업을 가로막았는지 정확히 밝히세요.

## 편집 범위 (Edit scope)

오직 검증 스킬 자신의 디렉터리(해당 스킬의 `SKILL.md`, `features/`, 그리고 스킬이 소유한 하네스 스크립트들)만 편집하세요. 실행 도중 제품 코드는 절대 편집하지 마세요: 맵에 적혀 있는 동작을 앱이 더 이상 수행하지 않는다면 이는 문서 드리프트(맵을 수정)이거나 제품의 성능·기능 퇴행(regression — 문서로 덮어 가리려 하지 말고 사용자에게 보고) 중 하나입니다.

## 수행 절차 (Pass)

0. **대상 찾기 (Locate the target).** 유지보수할 검증 스킬을 찾습니다: 본문에 launch/drive 섹션과 기능 맵이 있는 프로젝트 로컬 스킬(대개 `.cursor/skills/verify-*/`)입니다. 후보가 여러 개면 어느 것인지 질문하고, 하나도 없으면 임의로 대상을 지어내지 말고 멈춘 뒤 `/create-verification-skill`을 안내하세요.

1. **인덱스 위생 점검 (Index hygiene).** 기능 맵의 README를 읽고 같은 폴더의 기능 파일들을 글로빙(glob)하여 대조합니다. 누락되었거나, 불필요하게 남았거나, 중복되었거나, 깨진(dead) 항목들을 수정합니다. 가벼운 점검 단계이므로 별도의 목록 파일을 새로 생성하지는 않습니다.

2. **소스 코드 분석 웨이브 (Source wave).** 기능 파일당 하나씩 읽기 전용 서브에이전트를 동시에 띄웁니다. 각 서브에이전트는 소스 코드를 바탕으로 "이 사용자 대면 기능은 어떻게 동작하는가?"를 설명하고, 코드 인용과 함께 문서 드리프트가 의심되는 부분을 표시하며, 간결한 라이브 검증 레시피 하나를 반환합니다. 자식 에이전트들은 절대 앱을 직접 구동하거나 파일을 편집하지 않습니다. 반환 형태: 기능 요약 / 소스 진입점 / 의심되는 드리프트(또는 없음) / 단일 레시피.

3. **조율 및 통합 (Reconcile).** 모든 기능 파일에 대해 요약 결과가 반환되면, 겹치는 레시피들을 가능한 한 적은 수의 앱 상태로 병합합니다. 인용된 드리프트 의심 지점들을 표본 점검(spot-check)하되, 이미 문제없다고 확인된 주장들을 처음부터 다시 증명하느라 시간을 쓰지 마세요. 최근 코드 변경 내역(churn)을 훑어보며 기능 맵에 누락된 새로운 사용자 대면 표면이 있는지 확인합니다 — 누락되었다고 판단하려면 반드시 구체적인 소스 경로가 뒷받침되어야 합니다.

4. **라이브 패스 (Live pass).** 소스 코드가 아무리 깨끗해 보여도 필수입니다. 모든 구동은 코디네이터가 직접 전담하며, 검증 스킬 자체의 실행(Launch) 모델을 따릅니다 — 서버와 UI는 하나의 장기 실행 인스턴스를 순차적으로 구동하고, 짧게 실행되는 CLI는 구동마다 격리된 새 세션을 사용합니다(이 문서가 아니라 대상 검증 스킬의 Launch 섹션이 결정합니다). 모든 기능을 최소 한 번 이상 직접 구동하며, 어떤 실패가 발생하든 패스 내내 다음 세 가지 불변식을 철저히 지키세요: (1) 마지막으로 이상 징후를 보인 이후 헬스 체크를 거치지 않은 인스턴스는 절대 구동하지 마세요 — 첫 구동 전에 doctor를 실행하고, 세션 단위로 움직이는 경우 매 새 세션마다 doctor를 실행하며, 구동이 실패한 직후에도 다시 doctor를 실행하세요. 또한 프로세스는 정상이지만 UI 상태가 먹통(wedged)이 되어 doctor가 실패를 감지하지 못하는 경우에는 요행을 바라지 말고 알려진 정상 상태로 리셋하거나 재실행하세요; (2) 그때까지 캡처한 근거(evidence)는 모든 정리(cleanup) 단계를 거친 뒤에도 살아남아야 하며, 막연히 가정하지 말고 지정된 저장 위치를 직접 확인하세요; (3) 특정 구동이 시작한 어떤 프로세스나 상태도 그 구동의 유효 수명을 넘겨 살아남아서는 안 됩니다 — 세션이 멈췄든, 종료되었든, 공유 인스턴스이든 실패한 반복 시도의 잔여물(residue)은 반드시 정리합니다(공유 인스턴스의 경우 인스턴스 자체가 아니라 잔여물만 정리). 스킬 드리프트로 인해 발생한 doctor 실패는 그 자체로 드리프트입니다: 편집 범위 안에서 이를 수정하고 단 한 번 재시도하세요(수정으로 인해 무효화된 것만 재시작하고 그 이상은 건드리지 않음). 그래도 안 될 때 비로소 패스를 `blocked`로 판정합니다. 도달할 수 없는 기능은 구체적인 선행 조건(인증, 권한, OS, 외부 상태)과 시도한 경로가 명확히 확인될 때만 `verified-unreachable`로 분류합니다. 만약 기능 맵에 그 선행 조건이 빠져 있다면 그것은 문서 드리프트입니다. 분류(triage) 단계에서 수정한 모든 하네스는 출하 전에 반드시 라이브로 다시 구동해 검증해야 합니다. 최종 종료(teardown)는 그러한 재증명을 포함한 전체 실행의 마지막 구동이 끝난 뒤에 수행하여, 실행이 끝난 후에는 아무것도 남아 있지 않게 합니다(단, 스킬 규칙에 따라 근거 아티팩트는 유지).

5. **분류 및 조치 (Triage).** 사용자 관점(user-POV) 설명이 틀렸거나 누락됨 → 문서 드리프트이므로 수정합니다. 실제 동작은 정상이지만 하네스가 구동하지 못함 → 하네스 격차(harness gap)이므로 수정합니다. 하네스 수정은 생성 시와 동일한 헬퍼 규칙(스크립트 실행 권한 부여, 스킬 본문에 호출 방법 명시)을 따릅니다. 앱 동작 자체가 실제로 깨져 있음 → 제품 결함(product gap)이므로 사용자에게 보고하기 위해 기록만 해두고 이번 PR에서는 제외합니다.

6. **출하 또는 중단 (Ship or stop).** `changed`인 경우: 변경된 모든 파일을 먼저 다시 읽어 확인한 뒤, 증명된 수정사항들을 단 하나의 PR로 출하합니다. `clean` 또는 `blocked`인 경우: PR을 열지 않고 결과와 커버리지 내역을 정직하게 보고합니다.

간결한 실행 노트(커버한 기능, 도달 불가능했던 선행 조건, 확인된 드리프트, 최종 결과)는 임시(scratch) 위치에 보관하고 커밋하지 마세요.
