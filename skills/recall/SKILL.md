# Recall

**작업을 시작하거나 재개하기 전에 사용자의 최근 작업 맥락을 재구성하고, 현재 상태와 다음에 해야 할 일을 간결한 캡슐 형태로 정리해 돌려줍니다.**

간결하고 주제에 맞게 유지하세요. 범위 내 스레드에 필요한 내용만 읽고 멈추세요.

작업 맥락은 두 가지 기록에 나뉘어 있습니다. 자신의 채팅 기록에는 본인이 수행하고 결정한 내용이 담겨 있습니다. 공유 기록에는 동일한 코드 주변에서 다른 이름으로 일어난 모든 일(사용자가 계속 제보하는 증상, 배포되었다가 되돌려진 수정 사항, 프로덕션에서 여전히 발생하는 에러)이 담겨 있습니다. 이 두 번째 기록은 **why** 스킬이 소스 컨트롤, 이슈 트래커, 채팅 및 이슈 채널, 장문 문서, 에러 트래킹 전반에 걸쳐 검색하는 대상입니다. 오랫동안 버그가 이어진 기능은 대부분의 이야기가 그곳에 남아 있으므로, 트랜스크립트만으로 맥락을 재구성하지 마세요.

트랜스크립트는 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`에 위치하며, 여기서 `<slug>`는 워크스페이스 경로에서 맨 앞의 슬래시를 제거하고 각 "/"를 "-"로 바꾼 값입니다(예: `/Users/you/proj`는 `Users-you-proj`가 됨). 각 줄은 하나의 채팅 메시지입니다.

1. 먼저 분류한 뒤 라우팅하세요. 특정 이전 채팅 하나를 이어서 진행하는 것은 이 스킬이 아니라 `session-pickup` 플레이북의 역할입니다. 습관을 영구적인 스킬로 만드는 것은 `automate-me`입니다. 작업 내역을 사람이 읽기 좋게 요약하는 것도 다른 작업입니다. Recall은 행동에 나서기 전에 최근 채팅 전반에서 작업 맥락을 불러옵니다. 사용자가 이미 전체 상태 캡슐(경로, 브랜치, 변경 사항)을 제공했다면 그대로 사용하고 마이닝은 건너뛰세요.
2. 검색하기 전에 범위를 확정하세요. 기간("최근"은 실제 범위이며 기본값은 지난 7일), 지정된 경우 해당 주제, 그리고 워크스페이스(기본값은 현재 활성 워크스페이스. 요청받지 않은 한 절대 다른 프로젝트의 트랜스크립트를 읽지 마세요)를 고정하세요. 확정한 범위를 먼저 밝히세요. "전체(all)"를 임의로 조용히 "최근 N개"로 바꾸지 마세요.
3. 채팅 기록 전반으로 팬아웃(fan out)하세요. 빠르고 저렴한 모델로 병렬 서브에이전트를 띄워 각각 코퍼스의 일부를 맡기세요. 모든 서브에이전트에게 후보를 절대 UUID 이름이 아닌 실제 수정 시간(`ls -t`) 순으로 정렬하고, 주제를 먼저 grep한 뒤 일치하는 채팅과 그 안의 관련 영역만 읽으며, 현재 채팅과 명백한 노이즈(서브에이전트, 평가(eval), 테스트 채팅)는 건너뛰도록 지시하세요. 각 서브에이전트는 채팅당 하나의 블록으로 동일한 스키마를 반환합니다: 주제, 사용자의 목표, 결정 사항, 미해결 스레드, 겪은 어려움 및 수정 사항, 산출물(PR, 티켓, 브랜치)을 각각 채팅 UUID를 인용하여 작성합니다. 채팅이 한두 개뿐이라면 팬아웃을 건너뛰고 직접 검색하세요. 원본 트랜스크립트는 서브에이전트 안에만 남겨 두고, 메인 스레드는 결과만 받습니다. **poteto-mode** 스킬의 Subagents 섹션에 따라 작업에 맞는 각 서브에이전트의 추론 수준과 속도(빠름 또는 표준)를 선택하세요.
4. 주제가 기능, 파일, 서브시스템, 영역 또는 버그를 지목할 때마다 공유 기록을 훑으세요(sweep). 이것은 판단의 문제가 아니라 기본 동작이며, "X에 대한 내 작업"이라고 해서 예외가 되지 않습니다. **why** 스킬의 소스 조사자(source investigators)들에게 작업을 넘기되, 질문을 "왜 이렇게 만들어졌는가"에서 "현재 상태는 어떠한가, 무엇을 시도했다가 유지되지 못했는가, 사용자들이 여전히 무엇을 제보하고 있는가"로 전환하세요. 소스별 플레이북을 재사용하고, 채팅 기록 마이닝과 병렬로 조사자들을 실행하며, 조사 자세를 그대로 이어받으세요(소스당 조사자 1명, 결과가 없는 것(null)도 하나의 발견 사항임, 사용할 수 없는 MCP는 건너뛰고 그 사실을 명시함). 돌아온 결과를 브리핑에 통합하세요. 지정된 대상이 없는 순수 활동 회상("이번 주에 내가 뭘 했지")의 경우에만 이 단계를 건너뛰세요. 이 경우에는 본인의 기록과 라이브 상태가 곧 전체 답변입니다.
5. 라이브 상태와 대조하여 검증하세요. 마이닝과 공유 기록 조사에서 드러난 PR, 브랜치, 티켓을 가져와 `git`과 `gh`로 확인하세요. 에이전트가 실제로 무엇을 했는지(실행한 도구, 읽은 파일, 마주친 에러)에 따라 답이 달라질 때는 잘라낸 로컬 복사본이 아니라 전체 트랜스크립트를 읽으세요.
6. 아래 계약에 맞춰 브리핑을 작성하세요. 스레드별로 그룹화하고, 지정된 주제에서 벗어나지 마세요.

## 출력 계약 (Output contract)

캡슐을 맨 앞에 두고, 이어서 스레드 상태, 문제점, 다음 행동 순서로 작성하세요. 더 깊은 세부 사항은 아래로 내리거나 덜어내세요.

- **캡슐 (Capsule).** 최대 5개의 불릿. 이 작업이 무엇이며 전반적으로 어디까지 와 있는지 설명합니다.
- **스레드 (Threads).** 각 한 줄씩, 정확히 하나의 상태 태그를 앞에 붙입니다: `[merged #N]`, `[open PR #N]`, `[in flight <branch>]`, `[verified, uncommitted]`, `[reverted #N]`, 또는 `[planned, not started]`. 태그가 없는 스레드는 아직 완료되지 않은 것이므로 반드시 태그를 붙이세요.
- **문제점 (Problems).** 반복해서 나타나는 문제로 최대 5개. 다음 시도가 지난번 실패한 지점에서 출발할 수 있도록, 사용자가 계속 제보하는 증상과 배포되었다가 되돌려진 모든 수정 사항을 포함하세요.
- **다음 행동 (Next move).** 가장 유용한 단 하나의 구체적인 다음 조치.

인접한 기능이나 티켓은 현재 작업을 가로막는(block) 경우가 아니면 제외합니다. 캡슐과 스레드 줄이 한 화면을 넘어가면 스레드를 줄이기 전에 세부 사항을 먼저 덜어내세요. **unslop** 스킬을 거쳐 브리핑을 작성하고, 채팅에서 찾은 내용은 UUID로, 공유 기록에서 찾은 내용은 해당 출처(PR 번호, 티켓 ID, 채팅 퍼머링크, 에러 트래커 이슈)로 인용하며, 외부에 공개되는 출력 전에는 비공개 맥락을 정제(sanitize)하세요.

**응답 (Reply):** 위 계약에 맞춘 브리핑.
