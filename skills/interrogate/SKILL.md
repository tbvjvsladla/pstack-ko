# Interrogate

적대자(adversaries)들이 변경사항이나 설계를 깨뜨리려 시도합니다. 발견 사항(finding)은 오직 실제 실행을 통해 증명되었을 때만 살아남습니다. 발견 사항을 보고하되, 직접 수정을 적용하지는 마세요.

## 틀 잡기 (Frame)

범위는 사용자가 지정한 대상입니다. 별도 지정이 없다면 베이스 브랜치와의 머지 베이스(merge base)부터 현재 워킹 트리까지의 브랜치 diff가 범위가 됩니다. 사용자의 메시지, 커밋, PR 설명을 바탕으로 **in-your-own-words** 스킬을 사용해 의도(intent)를 서술하세요. 의도가 불분명할 때는 사용자에게 질문하세요.

## 병렬 전개 (Fan out)

**arena** 스킬의 Phase A 3~4단계와 Phase B를 실행하되, 다음 네 가지를 변경합니다. `arena runners` 대신 `interrogate reviewers` 줄을 읽으세요. 범위에 포함된 커밋되지 않은 변경사항(uncommitted changes)을 각 워크트리에 복사하세요. 각 적대자를 `generalPurpose`로 띄우세요. 아레나의 과제 및 설계 근거 지침 대신 각 적대자에게 범위, 의도, 그리고 아래 브리핑을 전달합니다:

> 이 변경사항을 깨뜨리세요. 실패하는 테스트, 재현 스크립트, 또는 잘못된 동작을 보여주는 명령어 출력처럼 실제 코드를 대상으로 한 실행을 통해 각 발견 사항을 증명하세요. 대상이 설계나 계획인 경우에는 프로토타입을 실행하거나 현재 트리를 직접 탐색(probe)하여 증명하세요. 재현 코드는 당신의 워크트리 안에만 유지하세요. 각 발견 사항은 제목, 실행한 정확한 명령어, 출력된 결과, 그리고 원래 의도가 요구하는 올바른 출력 결과를 포함해 보고하세요. 직접 실행해 보지 않은 것은 모두 제외하세요. 스타일, 네이밍, 구조, 그리고 미래에 다른 변경이 일어나야만 문제가 되는 가정적 위험 요소들은 모두 제외 대상입니다. 발견 사항이 전혀 없는 것(No findings)도 유효한 결과입니다.

## 검증 (Verify)

arena의 Phase F에 따라 각 발견 사항의 명령어를 직접 재실행하여 검증합니다. 출력 결과가 실제로 실패를 보여주고 그 실패가 원래 의도를 깨뜨릴 때만 해당 발견 사항을 유지합니다. 나머지는 모두 버리세요. 근본 원인이 같은 발견 사항들은 하나로 병합합니다.

arena의 Phase C, D, E는 건너뜁니다. 적대자마다 서로 다른 실패를 찾아내므로, 최종 판정에는 특정 적대자 하나의 목록이 아니라 검증을 통과한 모든 발견 사항을 남깁니다.

## 출력 (Output)

- **의도 (Intent)**: 자신의 말로 다시 서술한 의도.
- **발견 사항 (Findings)**: 검증된 각 발견 사항에 대해 실행 명령어, 출력 결과, 의도를 어떻게 깨뜨리는지, 그리고 이를 찾아낸 적대자들을 기재합니다. 살아남은 발견 사항이 하나도 없다면 "검증된 발견 사항 없음(no verified findings)"이라고 적으세요.
- **제외된 항목 (Dropped)**: 각 적대자별로 제외된 발견 사항의 개수와 그 이유.
