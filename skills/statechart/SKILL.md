# Statechart

이 차트는 시스템이 상태 사이를 어떻게 이동하는지를 차트를 읽는 사람의 언어로 보여줍니다. 그 독자가 동작이 올바른지 여부를 판단합니다.

## 실행 (Run)

저장소 외부의 임시(scratch) 폴더에서 작업하세요. TLA+ 명세(spec)와 설정 파일을 작성한 뒤 다음을 실행합니다:

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts`는 TypeScript 파일이므로 TypeScript를 실행할 수 있는 런타임으로 실행하세요.

첫 실행 시에는 mise를 통해 TLC와 Java를 설치하므로 네트워크 연결이 필요합니다.

## 명세 작성하기 (Write the spec)

- 독자가 동의하는 각 규칙을 INVARIANT로 작성하세요. 규칙은 화면, 결과, 저장된 값 또는 메시지에 관한 것일 수 있습니다. 모델에 해당 규칙을 표현할 변수가 없다면 변수를 추가하세요. 규칙이 성립하도록 만들기 위해 규칙을 약화시키지 마세요.
- `Next`는 `YouPressPlay \/ YouPressStop`처럼 액션들의 논리합(disjunction)으로 작성하세요. 그렇지 않으면 TLC가 모든 단계의 이름을 `Next`로 붙입니다.
- 빠져나가는 단계가 없는 상태는 올바른 종료 상태일 때조차도 `NoDeadlock`을 위반합니다. 이미 그 이름을 가진 INVARIANT나 PROPERTY가 있을 때 해당 규칙의 이름은 `CHECK_DEADLOCK`이 됩니다. `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`처럼 종료 상태에서만 참이고 아무것도 변경하지 않는 액션을 `Next`에 추가하고, `step()`에서 라벨을 부여하세요.

## 차트 구성하기 (Pick the chart)

판단이 필요한 작업은 당신이 수행합니다: 각 상태와 화살표에 적힐 단어, 단계(phase)와 그 색상, 제목, 그리고 독자에게 전달할 보고서입니다. 이 작업 내용을 뷰(view) 모듈에 담고 `--view` 옵션으로 전달하세요.

독자의 언어로 보여주기 위해 뷰 모듈은 `state(vars)`를 내보냅니다(export). `state()`가 반환하는 값에 따라 차트의 형태가 결정됩니다:

- 문자열은 평면 차트를 만듭니다: `export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 배열은 부모 상태(계층 구조)를 만듭니다: `export const state = (v) => v.main.split(".");`
- 객체는 각 키마다 하나의 병렬 영역(region)을 만듭니다: `export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

각 상태에는 "Paying"이나 "Lease held, write pending"처럼 독자가 볼 수 있거나 신경 쓰는 내용을 라벨로 붙이세요. 변수 이름은 라벨에 넣지 마세요. `vars`에서 TLA+ 시퀀스(sequence)는 1부터 시작하는 키를 가진 객체이므로 `v.pc[1]`이 곧 `pc[1]`입니다. 집합(set)은 배열입니다.

뷰 모듈은 또한 `step(action, from, to)`를 내보낼 수 있습니다. 이 함수는 TLC 액션 이름과 단계 전후의 값들을 인자로 받아 화살표의 라벨을 반환합니다. 각 단계 라벨은 "you press play"나 "the connect fails"처럼 사용자가 실제로 겪는 모습 그대로 작성하세요. 코드 이름이나 TLA+ 액션 이름을 적지 마세요. 차트에서 동일한 결과로 끝나는 두 액션에는 동일한 라벨을 부여하여 하나의 화살표를 공유하도록 만드세요.

어떤 단계가 특정 조건에서만 발생할 수 있을 때는 `you press play [while the file loads]`처럼 독자의 언어로 조건을 대괄호 안에 넣어 라벨 끝에 붙이세요. 영역(regions) 차트에서는 명령어가 다른 영역들의 조건을 해당 영역 라벨의 단어(예: `[when Offline]`)로 화살표에 자동으로 적습니다. 당신이 직접 대괄호를 적으면 자동 생성된 조건을 덮어쓰게 되어, 한 상태에서 나가는 두 화살표가 똑같아 보일 수 있습니다. 따라서 영역 차트에서는 다른 영역에 대한 조건을 대괄호로 직접 적지 마세요. 어떤 라벨에도 표시되지 않는 값이 단계의 목적지를 결정할 때는 "the roster read fails"처럼 그 결과를 라벨에 명시하세요.

뷰 모듈은 다음 항목들도 내보낼 수 있습니다:

- `group(vars)`는 단계(phase)의 이름을 반환합니다. 각 차트 상태는 자신이 속한 그룹의 색상을 얻습니다. 하나의 차트 상태 이면에 있는 모델 상태들이 서로 다른 그룹에 속해 있으면 그 상태는 색상을 갖지 않습니다.
- `colors`는 각 그룹 이름에 색상 클래스를 부여합니다.
- `title`은 차트 상단에 표시되는 문자열입니다.

명령어는 각 모델 상태마다 `state()`와 `group()`을 최대 한 번씩 호출하고, 각 단계마다 `step()`을 최대 한 번 호출합니다. 차트와 보고서 모두 그 반환값을 사용합니다. 따라서 각 함수가 오직 자신의 인자에만 의존하도록(순수 함수로) 작성하세요.

차트는 동일한 라벨 안에 머무르는 단계(자기 자신으로의 전이)는 그리지 않습니다. 독자가 그러한 단계를 반드시 봐야 한다면 라벨을 분리하세요.

차트가 너무 복잡하면 읽기 어려우므로 화살표 개수는 약 20개 이하를 목표로 하세요. 먼저 `state()`에서 더 굵직한(coarser) 라벨을 반환하게 하세요. 동일하게 동작하는 값들에는 하나의 라벨을 부여하고, 반환 결과가 아무것도 바꾸지 않는 진행 중인 호출처럼 독자에게 필요 없는 세부 사항은 생략하세요. 단, 버그 경로에 속한 각 상태와 각 표시(mark)는 유지하세요. 상태 병합으로 인해 `breaks` 상태가 `mayBreak`로 바뀌면 어디서 규칙이 깨지는지 가려지게 됩니다. 서로 다른 규칙을 위반하는 두 상태는 병합하지 마세요. 병합하면 독자가 어디서 어떤 규칙이 깨지는지 알 수 없습니다. 그렇게 해도 차트가 여전히 너무 복잡하다면, 모든 상태에 공통으로 있는 리셋이나 다른 화살표가 보여주는 내용을 반복하는 화살표처럼 독자에게 필요 없는 단계에 대해 `step()`에서 `null`을 반환하세요. 단계를 숨길 때는 다음 규칙을 따르세요:

- 모든 차트 상태가 시작 상태로부터 화살표를 따라 도달 가능하도록 유지하세요.
- 모델에서 빠져나가는 단계가 있는 각 차트 상태에는 최소 하나의 나가는 화살표를 남겨 두세요.
- 하나의 화살표에 속한 단계들은 전부 숨기거나 전부 남기세요. 일부만 숨기면 조건이 실제보다 좁아집니다.
- 결과를 전달할 때(hand-off) 차트가 어떤 단계들을 숨겼는지 밝히세요.

## 보고서 읽기 (Read the report)

- 차트에서 규칙을 위반하는 상태는 `breaks` 클래스를 가집니다. 그 차트 상태 이면의 모델 상태들 중 일부만 규칙을 위반할 때는 `mayBreak` 클래스를 가집니다. 범례(Legend)는 각 표시에 해당하는 규칙 이름을 보여줍니다. 두 규칙이 깨지면 하나의 표시에 두 이름을 모두 적으므로, 결과를 전달할 때 어떤 상태가 어떤 규칙을 위반하는지 설명하세요. 영역(regions) 차트에서는 특정 영역 상태를 포함하는 모든 영역 상태 조합이 규칙을 위반할 수 있을 때 해당 상태가 표시를 얻습니다. 어떤 조합이 규칙을 위반할 수 있는데 그 안의 어떤 상태도 표시를 얻지 못한 경우, 그 조합에 속한 모든 상태가 표시를 얻습니다.
- TLC는 규칙을 위반하는 상태를 지나쳐서도 탐색을 계속하므로, 차트는 버그 이후의 상태들도 보여줍니다.
- TLC가 버그를 지나쳐 계속 진행하기 때문에 상태 수 제한이 없는 모델은 끝없이 실행될 수 있습니다. 상수를 작게 유지하거나 CONSTRAINT를 추가하세요.
- VIEW나 SYMMETRY를 사용하면 TLC는 동일하게 취급하는 상태들을 하나의 상태로 세며, 차트도 그 하나의 상태만 그립니다. 화살표가 단계가 도달한 원래 상태 대신 그 대표 상태로 이어질 수 있으며, 보고서에 그 사실이 명시됩니다.
- TLC는 CONSTRAINT나 ACTION_CONSTRAINT를 넘어선 각 상태에서도 규칙을 검사하지만, 그 상태를 더 탐색하거나 데드락 여부를 검사하지는 않습니다. 어떤 규칙에 대한 TLC의 최단 경로가 그러한 상태에서 끝나면 차트는 그 상태를 그리고 보고서는 그 경로를 제공합니다. 차트는 경계(bound) 너머의 다른 상태들은 그리지 않습니다. 그러한 상태에서 발생하는 데드락은 표시되지 않습니다. 또한 TLC는 ACTION_CONSTRAINT가 제외한 각 단계 이후에도(다른 경로로 다음 상태에 도달하는 경우를 포함하여) 규칙을 검사합니다. 어떤 규칙에 대한 TLC의 최단 경로가 그러한 단계로 끝나면 차트는 그 단계를 그립니다.
- 명령어는 작성된 설정 그대로 워커 1개를 사용해 TLC로 규칙들을 검사합니다. 규칙 하나가 깨지면 명령어는 그 규칙을 제거하고 더 이상 깨지는 규칙이 없을 때까지 TLC를 다시 실행합니다. 첫 번째 위반 이후의 각 실행은 대규모 모델이 끝없이 실행되지 않도록 고유 상태 100,000개에서 멈춥니다. 실행이 그 한계에 도달하거나 에러로 멈추면 보고서는 검사하지 못한 규칙들을 "Rules not checked" 아래에 나열하며 차트에는 표시하지 않습니다. 검사되지 않은 규칙은 성립할 수도 있고 깨질 수도 있습니다. 이를 검사하려면 설정에서 깨진 규칙들을 제거하거나 모델을 더 작게 만드세요. 상태 수 제한은 TLC의 변수 순서를 바꾸는 모듈을 추가하므로, 속성(property) 검사 시 제한 없이 실행했을 때와 다른 반례(counterexample)를 찾을 수 있습니다.
- `tlc.out`은 작성된 설정 그대로 TLC가 출력한 내용입니다. 깨진 규칙의 버그 경로가 차트에 표시되지 않을 때, 이를 찾아낸 실행에서 TLC가 출력한 내용은 `tlc-RULE.out`에 담깁니다. TLC가 첫 번째 경고를 반복할 때 일반 TLC는 이를 두 번 출력하지만, 이 명령어가 읽는 출력에서는 TLC가 두 번째 복사본을 제외하므로 `tlc.out`에는 한 번만 나타납니다. 이는 Java가 `-XX:+UseParallelGC`로 실행될 때만 발생하는데, 그렇지 않으면 TLC의 첫 번째 경고는 해당 플래그를 전달하라는 권장 메시지이고 이는 한 번만 출력되기 때문입니다.

## 차트 보여주기 (Show the chart)

사용자에게 `chart.mmd`를 `mermaid` 코드 블록으로 보여주세요. 차트의 예산은 작성된 설정으로 TLC가 센 기준 500개 상태입니다. 이를 초과하면 차트는 규칙을 위반하는 상태에 이르는 경로들만 그리며, 깨지는 규칙이 하나도 없으면 명령어는 `chart.mmd`를 생성하지 않습니다. 이 경우에도 모든 규칙을 검사하며 보고서는 상태 수와 각 버그 경로를 제공합니다. 전체 그래프를 보려면 모델을 더 작게 만드세요.

Pele을 사용해 차트를 렌더링하세요. 사용자가 이미지를 요청하거나 차트가 텍스트로 읽기에는 너무 클 때는 `references/render.md`를 따르세요. 사용자가 요청하지 않는 한 다른 렌더러를 사용하지 마세요.

## 결과 전달하기 (Hand off)

결정을 내려야 하는 사람에게 각 차트와 그 Mermaid 텍스트를 전달하세요. 각 버그마다 한 줄씩 추가하여 규칙 이름, 그 규칙을 설명하는 독자 눈높이의 문장, 그리고 보고서에 번호가 매겨진 경로를 적으세요. 모델이 생략한 부분도 밝히세요. 새로운 `--out` 폴더를 지정해 파일들을 다시 생성할 수 있는 명령어도 함께 제공하세요.

모델이 실제 코드를 기술하는 경우, 각 버그 경로를 실제 코드에 대해 테스트나 라이브 재현(repro) 형태로 액션당 한 단계씩 재현해 보세요. 만약 실제 코드에서 버그가 발생하지 않는다면, 모델이 틀리지 않았음을 입증하기 전까지는 모델이 틀렸다고 생각하세요.
