# 도메인을 모델링하라 (Model the Domain)

실제 도메인을 조건문들에 흩뿌리는 대신 데이터 구조 안에 인코딩하세요. 도메인과 부합하는 구조는 유효하지 않은 상태를 표현 불가능하게 만들고 분기문을 제거합니다. 코드를 처음 작성할 때 올바른 구조를 선택하는 비용은 저렴하지만, 나중에 바로잡으려 하면 리팩터링으로 여겨져 뒤로 미뤄지게 됩니다.

다음과 같은 구조를 적극 활용하세요:

- 흩어진 불리언(boolean) 변수들, 단계(phase) 변수, 수명주기 체크 대신 **상태 머신(state machine)**
- 느슨한 파라미터나 반복되는 데이터 형태 가정 대신 **타입이 지정된 모델(typed model)**
- 여러 파일에 퍼져 있는 분기문 대신 **맵(map), 레지스트리, 룩업 테이블, 또는 구별된 유니온(discriminated union)**
- 즉흥적인 상태 변경(ad hoc mutation) 대신 **리듀서(reducer) 또는 커맨드/이벤트 모델**
- `load`, `validate`, `transform`, `save` 같은 실행 순서가 아니라 **하나의 도메인 지식 체계를 중심으로 조직된 모듈** (실행 순서는 소유권의 기준이 아닙니다)
- 반복되는 동작, 소유권, 불변식을 한곳으로 모으는 **작은 모듈 경계**
- 접근 패턴이 요구하는 경우 **큐, 캐시, 인덱스, 그래프, 트리, 또는 정규화된 컬렉션**
- 그 밖에 도메인에 꼭 맞는 구조. 마땅한 것이 없다면 코드가 절대 허용해서는 안 되는 조건이 무엇인지, 그리고 데이터가 어떻게 읽히는지를 먼저 파악한 다음 정확히 그것을 인코딩하는 구조를 찾으세요.

억지로 추상화를 강제하지는 마세요. 현재 형태가 이미 명확하고 국소적이며 앞으로 복잡해질 가능성이 낮다면 평범하고 지루한 코드를 선호하세요. 분기문, 중복된 규칙, 유효하지 않은 상태, 또는 수명주기 위험을 제거하지 못하면서 간접 참조만 늘리는 추상화는 경계하세요.

이 원칙을 건너뛰었다는 신호는 새 기능을 추가할 때 기존 `if/else` 체인에 분기를 하나 더 늘리고 있거나, 첫 번째 불리언 변수와 동기화를 유지해야 하는 두 번째 불리언 변수를 추가하고 있는 것입니다. 시간 순서에 따른 분해(temporal decomposition) 역시 또 다른 신호입니다. 단계(phase) 이름으로 지어진 모듈들은 여러 단계에 걸쳐 동일한 도메인 규칙을 반복하게 됩니다.
