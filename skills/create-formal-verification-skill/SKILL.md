# 정형 검증 스킬 생성 (Create a formal verification skill)

테스트는 누군가 미처 생각해서 작성한 케이스만 검사합니다. 반면 정형 검증(formal verification)은 명시된 범위 내의 모든 케이스(모델 내 가능한 모든 실행 순서, 특정 상한(bound)까지의 모든 입력, 또는 아예 모든 입력)를 빠짐없이 검사합니다. 이 스킬은 저장소에서 정형 검증이 가장 절실한 부분을 찾아내고, 그 코드의 핵심 속성(property) 하나를 검증한 뒤, 다음 에이전트가 코드 변경 시 해당 속성을 깨뜨리지 않았는지 검사할 수 있게 해주는 프로젝트 로컬 스킬을 남깁니다. 이 스킬은 당신의 작업을 본 적이 없고 변경 작업 도중 처음 문서를 읽게 될 다음 에이전트를 위해 작성하세요. 또한 사용자는 정형 검증 언어를 새로 배우지 않고도 결과를 신뢰하고 그에 따라 행동할 수 있어야 합니다.

## 코드에서 검증 대상(target) 선택하기

코드베이스를 직접 분석해 답을 찾고, 직접 관찰할 수 없는 사항만 사용자에게 질문하세요. 사용자가 특정 영역이나 버그를 지목했다면 그곳에서 시작합니다.

좋은 검증 대상은 코드가 보장하는 약속 중 깨졌을 때 사용자에게 실질적인 피해를 주지만 일반 테스트로는 그 파손 케이스에 좀처럼 도달하기 어려운 부분입니다. 검증하기 가장 쉬운 대상이 아니라, 저장소 내에서 이러한 기준에 가장 부합하는 강력한 대상을 선택하세요.

## 질문이 도구를 선택하게 하세요

질문에 가장 낮은 비용으로 답할 수 있는 도구를 고르세요: 모델 체커(model checker), 증명 보조기(proof assistant), SMT 기반 검증기(verifier), 또는 기타 적합한 도구입니다. 이벤트들이 잘못된 순서로 얽혀 발생할 수 있는지를 묻는 문제에는 대개 설계의 작은 모델 위에서 모델 체커를 돌리는 것이 적합하며, 이 경우 언어를 불문하고 TLA+가 기본 선택지입니다. 메모리 안전성, 오버플로, 자료구조 불변식처럼 코드 자체가 모든 입력에 대해 올바르게 동작하는지를 묻는 문제에는 대개 실제 코드 위에서 직접 실행되는 검증기가 적합합니다. 만약 해당 언어에서 실행 가능한 검증기가 없다면 그 사실을 명시하고, 함수를 손으로 모델링하는 대신 생성된 입력(generated inputs)으로 실제 코드를 테스트하세요. 특정 상한(bound)만으로는 부족하고 모든 크기에서 항상 성립해야 하는 속성이라면 수학적 증명(proof)이 필요할 수 있습니다. 저장소 개발자들이 실제로 설치하고 실행할 수 있는 도구를 선호하고, 왜 그 도구를 선택했는지 사용자에게 설명하세요.

## 좋은 정형 검증의 조건 (What makes it good)

- **코드에 충실함 (True to the code).** 모델이나 증명의 모든 부분은 리뷰어가 실제로 열어볼 수 있는 실제 코드를 가리켜야 합니다. 검증에서 더 이상 쪼갤 수 없는 하나의 단계(indivisible step)로 취급하는 것은 실제 코드에서도 하나의 불가분한 단계여야 합니다. 이름들도 이 저장소의 실제 명칭에서 가져옵니다.
- **실패할 수 있음 (Able to fail).** 실패하는 모습을 한 번도 본 적 없는 검사는 아무것도 증명하지 못합니다. 검사 항목을 제거하거나 실행 순서를 바꾸는 등, 보호 대상 코드를 일부러 망가뜨린 변형(broken variant)에서 각 속성이 실제로 실패하는 모습을 확인하세요.
- **발견된 결함은 결함으로 유지 (Findings stay findings).** 현재 코드가 속성을 위반한다면 그 반례(counterexample)를 코드의 용어로 풀어서 보고하세요. 검사가 통과할 때까지 속성이나 모델을 임의로 약화시키지 마세요. 또한 사용자가 요청하지 않는 한 제품 코드를 직접 수정하지 마세요.
- **범위에 대한 정직함 (Honest about scope).** 어떤 상한(bounds)과 가정 아래에서 무엇이 검증되었고 무엇이 제외되었는지 명확히 밝히세요. 검증 통과는 해당 모델이나 상한 범위를 보증할 뿐 시스템 전체를 보증하는 것이 아닙니다.
- **도구 없이도 읽을 수 있음 (Readable without the tool).** 검증하는 속성과 위반 시 발생하는 피해를 각각 평이한 한 문장으로 서술하세요. 반례는 코드의 용어를 사용한 짧은 단계별 실행 순서로 설명하세요.
- **재실행 비용이 저렴함 (Cheap to rerun).** 단일 명령어, 재현 가능한 도구 버전, 그리고 다음 에이전트가 관련 변경을 할 때마다 부담 없이 실행할 수 있을 만큼 충분히 짧은 실행 시간을 갖추어야 합니다.
- **코드와 보조를 맞춤 (Kept in step with the code).** 각 검사가 어떤 파일과 함수를 포괄하는지, 그리고 검증 내용이 해당 코드를 정확히 기술하고 있음을 마지막으로 확인한 커밋(sync commit)이 무엇인지 기록하세요. 그 커밋 이후에 대상 코드가 변경되면 다음 에이전트는 검증을 다시 점검해야 함을 즉시 알 수 있습니다.

## 검증 스킬(verify skill) 생성하기

대상 영역의 이름을 짓고 언제 사용해야 하는지 명시한 frontmatter를 갖춘 프로젝트 로컬 스킬을 작성하세요. frontmatter가 없으면 스킬이 등록되지 않습니다. 다음 에이전트는 오직 이 스킬 문서만 읽고도 자신의 변경사항이 검증 대상 코드를 건드리는지 판단하고, 검사를 실행하며, 실제 버그와 모델링 오류를 구분하고, 의도된 변경일 때 검증 모델을 업데이트할 수 있어야 합니다. 스킬 안에 커버리지 기록과 동기화 커밋(sync commit)을 기재하고, 다음 에이전트에게 새 커밋의 코드를 검증 모델이 정확히 반영하고 있음을 확인한 뒤에만 동기화 커밋을 앞으로 이동시키라고 지시하세요. 이 저장소의 실제 명령어, 경로, 명사를 사용하고 플레이스홀더(placeholder)를 남겨두지 마세요.

검사가 TLA+ 모델인 경우, 다음 에이전트에게 모든 결과를 pstack의 [`/statechart`](../statechart/SKILL.md) 스킬로 읽으라고 지시하세요. 이 스킬은 체커가 찾아낸 각 불변식 위반을 평이한 단어로 된 최단 경로로 보여줍니다. 검사가 통과할 때 `/statechart`는 시스템이 상태 간에 어떻게 전이하는지 차트로 그려줍니다. `/statechart`는 이름으로만 참조하세요. 그 명령어, 옵션, 파일 경로는 릴리스와 머신마다 달라지므로 생성된 스킬이나 스크립트 안에 직접 복사해 넣지 마세요.

## 인계하기 전에 직접 증명하기

다음 에이전트가 할 것처럼 생성된 스킬의 지침을 그대로 따라, 실제 코드에서 속성을 깨뜨리는 임시 변경(scratch change)을 만든 뒤 한 번 실행해 보세요. 검사는 반드시 그 파손을 잡아내야 합니다. 그런 다음 임시 변경을 버리고 검사가 원래 상태(통과하거나, 당신이 보고할 기존 발견 사항에서만 실패하는 상태)로 돌아오는지 확인하세요. 한 번도 실행해 보지 않은 검증 스킬은 초안일 뿐입니다. 스킬이 파손을 놓치거나 특정 단계가 실행되지 않는다면 임시 변경이 아니라 스킬이나 검증 모델을 고치세요.

## 인계 (Hand off)

무엇을 검증했는지, 어떤 도구를 왜 사용했는지, 설정한 상한(bounds)은 무엇인지, 검사가 무엇을 발견했는지(평이한 언어로), 어떻게 실행하는지, 그리고 무엇은 다루지 않는지를 사용자에게 보고하세요. 두 번째 검증 대상은 아주 밀접한 후보를 발견했을 때만 제안하세요. 검증을 재실행하지 않은 채 코드가 변경된 이후에 검증 모델을 다시 코드와 일치시키려면 `/maintain-formal-verification-skill`을 사용하면 된다고 사용자에게 안내하세요.
