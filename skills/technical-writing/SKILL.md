# Technical writing

지친 엔지니어가 한 번 읽고 바로 이해할 수 있도록 작성하세요. 네 가지 계층을 모두 적용합니다.

세 가지 규칙이 모든 계층 위에 자리합니다:

- **아무 일도 하지 않는 단어는 모두 덜어내세요.** 그 단어가 없어도 문장이 성립한다면 그 단어는 빼야 합니다. "In order to(~하기 위해서)"는 "to"입니다. "It is important to note that(~라는 점에 유의하는 것이 중요하다)"은 아무 의미도 없습니다.
- **짧고 일상적인 단어를 사용하세요.** "utilize" 대신 "use"를, "facilitate" 대신 "help"를, "perform" 대신 "do"를 쓰세요. 긴 단어는 그 길이만큼의 정밀함을 제공할 때만 쓸 자격이 있습니다.
- **규칙을 따랐더니 문장이 더 나빠진다면, 다른 방식으로 문장을 고치거나 그대로 두세요.** 모든 규칙을 따랐지만 기계가 쓴 것처럼 들리는 문장은 실패한 문장입니다.

코드베이스가 곧 단어장입니다. 동의어나 풀어서 쓴 설명 대신 실제 심볼, 파일, 플래그 또는 명령어 이름을 그대로 적으세요.

전문 용어(jargon)를 새로 지어내지 마세요. 개발자가 소리 내어 말할 법한 단어를 쓰세요: "evacuate", "ratchet", "endgame" 대신 "move(이동)", "delete(삭제)", "a budget that only decreases(줄어들기만 하는 예산)"라고 쓰세요. 이름이 붙은 패턴은 문서에서 처음 등장할 때 그 의미를 설명한다면 사용해도 괜찮습니다. 새로운 위반 단어와 그 대체어를 발견하면 `unslop` 스킬을 직접 수정하지 말고, 응답에서 `unslop`의 추상적 은유(abstract-metaphor) 규칙에 추가할 제안으로 diff와 함께 제시하세요.

## 리듬에 변화 주기 (Vary the rhythm)

문서가 모든 계층의 규칙을 준수하더라도 모든 문장이 짧게 잘려 있고, 관점도 없으며, 구체적인 내용도 없다면 여전히 기계가 쓴 것처럼 읽힙니다.

- 의도적으로 문장 길이를 섞으세요. 짧은 문장은 요점을 꽂아 넣습니다. 긴 문장은 사실과 그 조건 또는 결과를 함께 실어 나릅니다.
- 한 문장에 하나의 생각만 담는다는 것이 모든 문장의 길이를 똑같이 맞추라는 뜻은 아닙니다. 두 가지 생각을 담은 문장은 쪼개세요. 하나의 생각을 담은 긴 문장은 그대로 유지하세요.
- 문서 모드가 허용하는 곳에서는 관점을 가지세요. 설명(Explanation) 문서는 트레이드오프를 저울질하는 자리이므로 단순히 장단점을 나열하는 대신 그에 대한 판단을 말하세요. 레퍼런스(Reference) 문서는 건조하게 유지합니다.
- 무균실처럼 메마른 문장보다 구체적인 문장을 택하세요. "스키마 변경은 문제를 일으킬 수 있습니다"가 아니라 "열 이름을 바꾸면 빌드가 실패합니다"라고 쓰세요.

## 먼저 모드 선택하기 (Diátaxis)

하나의 문서에는 하나의 모드만 사용합니다. 두 가지 질문으로 모드를 결정합니다: 내용이 행동(하기)을 안내하는가 이해(생각하기)를 돕는가, 그리고 학습에 쓰이는가 실무에 쓰이는가?

- 행동 + 학습: **튜토리얼 (tutorial)**.
- 행동 + 실무: **하우투 가이드 (how-to)**.
- 이해 + 실무: **레퍼런스 (reference)**.
- 이해 + 학습: **설명 (explanation)**.

문서 전체 또는 문장 하나에 이 나침반을 적용하세요.

**튜토리얼 (Tutorial): 해보며 배우기.** 학습자의 성공은 학습자가 아니라 당신의 책임입니다. 학습자가 무엇을 "배울지"가 아니라 무엇을 "만들지" 말하며 시작하세요. 모든 단계는 초반부터 자주 눈에 보이는 결과를 만들어내야 합니다. 예상 출력, 프롬프트 변화, 로그 줄처럼 학습자가 보게 될 모습을 알려주세요. 설명은 절 하나와 링크 하나로 줄이세요. 구체성을 유지하세요. "우리(we)"를 주어로 하여 명령문으로 작성하세요: "먼저 x를 하세요. 이제 y를 하세요."

**하우투 가이드 (How-to): 목표에 도달하는 단계.** 기계가 수행할 수 있는 작업이 아니라 사람이 겪는 문제를 해결하세요. 독자가 기본 역량을 갖추고 있다고 가정하고 가르치려 들지 마세요. 오직 행동만 다룹니다: 곁가지 이야기, 배경 설명, 완전성을 위한 완전성은 배제하세요. 그런 내용은 대신 링크로 연결하세요. 분기와 판단을 허용하세요: "x를 원한다면 y를 하세요." 가이드 이름은 작업으로 붙이세요: "레이더 배열 보정"이 아니라 "레이더 배열을 보정하는 방법"으로 쓰세요.

**레퍼런스 (Reference): 조회를 위한 사실.** 오직 기술(describe)만 하세요. 지시도, 설득도, 의견도 넣지 마세요. 건조하고 완전하며 확실하게 작성하세요. 유보적인 표현 없이 사실, 옵션, 한계, 에러를 진술하세요. 코드와 문서를 함께 탐색할 수 있도록 기술 대상의 구조를 그대로 반영하세요. 독자가 예상하는 위치에 자료를 배치하세요. 가능한 경우 코드에서 자동 생성하세요.

**설명 (Explanation): 이해와 이유(why).** 제품을 떠나서도 읽을 수 있는 경계가 명확한 하나의 주제를 다룹니다. 각 제목은 앞에 암묵적으로 "~에 대하여(About...)"를 붙여도 자연스러워야 합니다. 실제 '왜(why)'라는 질문에 닻을 내리세요. 설계 결정, 역사, 제약 조건, 대안 같은 맥락을 제공하세요. 오직 이 모드에서만 의견 제시가 허용됩니다.

모드를 섞지 마세요: 튜토리얼 안에 레퍼런스 표를 넣지 말고, 레퍼런스 안에 튜토리얼식 친절한 안내를 넣지 말고, 하우투 가이드 안에서 논쟁하지 마세요. 대신 문서를 분리하고 링크로 연결하세요.

## 독자에게 말 건네듯 문장 쓰기 (Google developer style)

- 독자를 "당신(you)"으로 부르며 현재 시제로 말하세요. 미래 시제("will")는 실제로 나중에 일어나는 일에만 사용하세요.
- 누가 무엇을 하는지 밝히세요: "검사됩니다(is checked)"가 아니라 "컴파일러가 검사합니다(the compiler checks)"라고 쓰세요. 수동태는 행위자를 알 수 없거나 행위자가 핵심이 아닐 때만 괜찮습니다.
- 지시문은 명령형으로 작성하세요: "**Submit**을 클릭하세요." 사실은 평이하게 진술하세요. 절대 "수행되어야 합니다(should be done)"처럼 쓰지 마세요.
- 지시문 앞에 조건을 먼저 두세요: "문서를 삭제하려면 **Delete**를 클릭하세요."
- 일반적인 경우를 먼저 두고 예외 사항은 뒤에 두세요.
- 잘 아는 친구처럼 말하세요. 유행어(buzzwords)나 비유적 표현을 쓰지 말고, 지시문에 "부디(please)"를 넣지 않으며, 절차 설명에 절대 "단순히(simply)", "쉽게(easy)", "빠르게(quickly)"를 쓰지 마세요. 그 일이 단순했다면 독자는 이 문서를 읽고 있지도 않았을 것입니다.
- 미리 예고하지 말고("곧 지원할 예정입니다..."), 연속된 문장을 똑같은 구절로 시작하지 마세요.
- 링크 텍스트는 페이지 제목이나 짧은 설명처럼 링크가 어디로 연결되는지 알려주는 단어로 작성하세요. 절대 "여기를 클릭하세요(click here)"라고 쓰지 마세요. 외부 링크로 내보내기보다 페이지 안에 맥락을 설명하는 한 문장을 적는 편을 선호하세요.
- 헤딩에는 단순한 주제가 아니라 핵심 요점을 담으세요("모드"가 아니라 "먼저 모드 선택하기"). 문장형 대소문자 표기(sentence case)를 사용하세요. 작업 헤딩은 동사구("인스턴스 생성하기")로, 개념 헤딩은 명사구로 작성합니다. 페이지당 h1은 하나만 두고 헤딩 단계를 건너뛰지 마세요.
- 순서가 있는 절차에는 번호 매기기 목록을, 그 외의 모든 경우에는 불릿 목록을 사용하세요. 완전한 문장으로 목록을 시작하고 항목들의 문법적 형태를 병렬로 맞추세요.
- 코드는 코드 글꼴로, UI 요소는 **굵은 글씨(bold)**로 표기하세요. 옥스퍼드 쉼표(serial comma)를 사용하세요. "등(etc.)"을 빼고 목록이 일부만 나열한 것임을 앞부분에 먼저 밝히세요.

## 문장이 한 번에 하나씩 읽히게 만들기 (STE rules)

- 지시문은 한 문장에 하나씩만 담으세요. 그 외의 문장도 한 문장에 하나의 생각만 담으세요.
- 약 20단어를 넘는 지시문과 약 25단어를 넘는 일반 문장은 쪼개세요.
- 경고나 조건은 그것이 보호하는 단계보다 앞에 두세요: "뜨거운 기름이 피부에 닿으면 화상을 입을 수 있습니다."
- 관사("the", "a")를 생략하지 마세요: "Remove backup file"은 두 가지 의미로 읽히지만 "Remove the backup file"은 한 가지로만 읽힙니다.
- 각 단어에 하나의 의미와 하나의 역할만 부여하고 일관되게 유지하세요. "check"를 '점검하다(inspect)'라는 뜻으로 썼다면 '억제하다(restrain)'라는 뜻으로 겸용하지 마세요.
- 동작당 하나의 단어를 선택해 끝까지 고수하세요: 여기서는 "start"라고 쓰고 저기서는 "initiate"라고 쓰지 말고 모두 "start"로 통일하세요.
- 절차는 서술형이나 수동태가 아니라 직접적인 명령문으로 작성하세요: "컴포넌트가 설치되어야 합니다"가 아니라 "컴포넌트를 설치하세요"라고 쓰세요.
- 가능한 한 "-ing" 형태의 단어를 피하세요.

## 두 가지 의미로 읽힐 여지 없애기 (Global English)

- "only"나 "not" 같은 수식어는 그것이 수식하는 단어 바로 옆에 두세요: "only fails on growth"와 "fails only on growth"는 서로 다른 뜻입니다.
- 길게 늘어선 명사 연쇄(noun strings)를 풀어쓰세요: "the proto import budget check script"는 "the script that checks the proto-import budget(프로토 임포트 예산을 검사하는 스크립트)"으로 바꿉니다.
- 모든 대명사("it", "they", "this")가 명백한 단 하나의 대상을 가리키게 하세요. 의심스러울 때는 명사를 반복하세요. 절 전체를 가리키기 위해 "this"나 "which"를 절대 사용하지 마세요.
- 동사를 생략하지 마세요: "Phase 1 moves the converters and Phase 2 the runtime"에서는 Phase 2에 동사가 빠져 있습니다. 동사를 넣어주세요.
- "Ensure that the switch is off"의 "that"처럼 문장 구조를 보여주는 작은 단어들을 유지하세요. 단어 수를 줄이겠다고 명확성을 희생하지 마세요.
- 나열된 항목이 서로 다른 두 대상일 때 오독을 막기 위해 관사를 반복하세요: "the client and host"가 아니라 "the client and the host"라고 쓰세요.
- 문장이 두 가지 방식으로 묶일 수 있을 때는 "and"나 "or"가 어떤 부분들을 연결하는지 명확히 하세요. "Both...and", "either...or", "if...then"을 활용하면 모호함을 비용 없이 없앨 수 있습니다.
- 세미콜론(;) 대신 마침표를 사용하세요. 줄표(em dash)는 새로운 문장으로 바꾸세요.
- 괄호 안의 텍스트는 완전한 문법 단위이거나 독립된 문장으로 만드세요. 복수형을 만들기 위해 끝에 "(s)"를 붙이지 마세요.
- 슬래시(/)를 쓰지 마세요: "a/b"나 "and/or" 대신 "a, b, 또는 둘 다(a, b, or both)"라고 쓰세요.
- 모든 곳에서 하나의 대상은 하나의 이름으로만 부르세요. 동일한 대상을 두고 어떤 곳에서는 "게이트(the gate)", 어떤 곳에서는 "래칫(the ratchet)", 또 어떤 곳에서는 "예산 검사(the budget check)"라고 부르는 문서는 독자에게 세 가지 다른 대상을 가르치는 셈입니다. 바뀌지 않은 것을 괜히 다른 말로 바꾸지 마세요.
- 관용구, 구어체 속어, 라틴어 약어(e.g., i.e. 등), 은유를 피하세요.

## 어조 및 저장소별 세부 규칙

- 이 스킬이 다루는 모든 문서에 **unslop** 스킬을 적용하세요. AI 특유의 어휘, 군더더기, 유보적 표현, 서식 습관 등 슬롭(slop) 패턴 카탈로그는 해당 스킬이 소유합니다.
- PR 설명과 커밋 메시지도 글쓰기입니다. Diátaxis를 제외한 모든 계층이 동일하게 적용됩니다. PR 본문은 리뷰어가 1분 안에 읽을 수 있는 브리핑이어야 합니다. 스웜 로그, SHA 목록, 메트릭 표를 본문에 직접 붙여넣지 말고 링크로 연결하세요.
- 제품 UI 문자열은 문서가 아닙니다. UI 문자열에는 제품의 카피라이팅 가이드라인을 따르세요.
- 코드 스니펫은 탭(tab)으로 들여쓰기하세요. 실제 경로를 적으세요. 개수나 트리 구조에 대한 모든 주장은 그것이 반영되는 커밋 시점에 참이어야 하며, 이를 다시 생성하는 명령어를 함께 포함하세요.

## 교정 예시 (Worked example)

수정 전 (Before):

> Configuration of the proto import ratchet budget script parameters is performed via budget.json. Note that it's important to remember that running with --write, which updates the committed budget to reflect the current count, should only be done when lowering it. If exceeded, CI fails.

수정 후 (After):

> `budget.mjs` reads the committed budget from `budget.json` and counts the files that import protos. If the count exceeds the budget, CI fails. Run `budget.mjs --write` only to lower the budget.
> (`budget.mjs`는 `budget.json`에서 커밋된 예산을 읽고 프로토를 임포트하는 파일 수를 셉니다. 파일 수가 예산을 초과하면 CI가 실패합니다. 예산을 낮출 때만 `budget.mjs --write`를 실행하세요.)
