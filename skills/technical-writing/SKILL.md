# Technical writing

지친 엔지니어가 처음 읽자마자 이해할 수 있도록 작성하세요.

- 아무 일도 하지 않는 단어는 모두 덜어내세요.
- 짧고 일상적인 단어를 사용하세요: "utilize" 대신 "use"를 쓰세요.
- 규칙을 따랐더니 문장이 더 나빠진다면, 다른 방식으로 문장을 고치거나 그대로 두세요.
- 동의어나 풀어서 쓴 설명 대신 실제 심볼, 파일, 플래그 또는 명령어 이름을 적으세요.
- 전문 용어(jargon)를 새로 지어내지 마세요. 개발자가 소리 내어 말할 법한 단어를 쓰세요. 이름이 붙은 패턴은 처음 등장할 때 그 의미를 설명하세요.

## 리듬에 변화 주기 (Vary the rhythm)

- 문장 길이를 섞으세요. 두 가지 생각을 담은 문장은 쪼개세요. 하나의 생각을 담은 긴 문장은 그대로 유지하세요.
- 설명(explanation)에서는 관점을 드러내세요. 레퍼런스(reference)는 건조하게 유지하세요.
- 구체적으로 쓰세요. "스키마 변경은 문제를 일으킬 수 있습니다"가 아니라 "열 이름을 바꾸면 빌드가 실패합니다"라고 쓰세요.

## 먼저 모드 선택하기 (Diátaxis)

하나의 문서에는 하나의 모드만 사용합니다. 모드를 섞지 말고 문서를 나누어 링크하세요.

- **튜토리얼 (Tutorial): 해보며 배우기.** 학습자가 무엇을 만들지 말하세요. 모든 단계는 눈에 보이는 결과를 만들어내야 하며, 학습자가 무엇을 보게 될지 알려주세요. 설명은 절 하나와 링크 하나로 줄이세요.
- **하우투 (How-to): 목표에 도달하는 단계.** 독자의 문제를 해결하세요. 기본 역량을 갖추고 있다고 가정하고 행동만 다룹니다. 갈래(fork)를 허용하세요. 과제 이름으로 가이드 제목을 지으세요.
- **레퍼런스 (Reference): 찾아보기 위한 사실.** 오직 사실만 기술하세요. 건조하고, 완전하며, 단호하게 작성하세요. 설명하는 대상의 구조를 그대로 반영하세요.
- **설명 (Explanation): 이해와 이유.** 경계가 명확한 하나의 주제를 다룹니다. 맥락(설계 결정, 히스토리, 제약 조건, 대안)을 제공하세요. 의견(opinion)은 오직 이곳에서만 허용됩니다.

## 독자에게 직접 문장 쓰기 (Google developer style)

- 현재 시제를 사용하여 독자를 "당신(you)"으로 지칭하며 말하세요.
- 누가 무엇을 하는지 명시하세요. 수동태는 행위자를 알 수 없거나 본질과 무관할 때만 허용됩니다.
- 지시문은 명령형으로 작성하세요. 조건을 지시문 앞에 두고, 일반적인 경우를 먼저 제시하세요.
- 유행어, 비유적 표현, "please"를 쓰지 말고, 절차 안에서 절대 "simply", "easy", "quickly"를 쓰지 마세요.
- 앞으로 나올 내용을 미리 예고(pre-announce)하지 말고, 연속된 문장을 같은 구절로 시작하지 마세요.
- 링크가 어디로 이어지는지 알 수 있는 단어로 링크를 거세요.
- 헤딩에는 문장형 대소문자 표기(sentence case)로 핵심 요점을 담으세요. 페이지당 h1은 하나만 두고, 헤딩 레벨을 건너뛰지 마세요.
- 순서가 있는 절차는 번호 매긴 목록으로, 나머지는 모두 불릿 목록으로 작성하세요. 목록을 시작할 때는 완전한 문장으로 도입하고, 항목들의 문법 구조를 병렬로 맞추세요.
- 코드는 코드 폰트(``)로, UI 요소는 굵은 글씨(**bold**)로 표기하세요. 옥스퍼드 쉼표(serial commas)를 사용하고 "etc."는 빼세요.

## 한 번에 하나의 진술만 담기 (STE rules)

- 지시문은 문장당 하나의 지시만, 그 외의 모든 곳에서는 문장당 하나의 생각만 담으세요.
- 약 20단어가 넘는 지시문과 약 25단어가 넘는 일반 문장은 쪼개세요.
- 경고나 조건은 그것이 보호하는 단계 앞에 두세요.
- 관사 "the"와 "a"를 생략하지 말고 유지하세요.
- 각 단어에 하나의 의미만 부여하고, 동작당 하나의 단어만 선택하세요.
- 절차는 서술이나 수동태가 아니라 직접적인 명령문으로 작성하세요.
- 가능한 한 "-ing" 형태의 단어를 피하세요.

## 두 가지 의미로 읽힐 여지 없애기 (Global English)

- "only"나 "not" 같은 단어는 그것이 수식하는 단어 바로 옆에 두세요.
- 길게 늘어선 명사 연쇄(noun strings)를 풀어쓰세요.
- 모든 "it", "they", "this"가 명백한 단 하나의 대상을 가리키게 하세요. 절 전체를 가리키기 위해 "this"나 "which"를 절대 사용하지 마세요.
- 동사나 문장 구조를 보여주는 작은 단어("that" 등)를 생략하지 마세요.
- 오독을 막아준다면 나열된 항목마다 관사를 반복하세요. "and"나 "or"가 어떤 부분들을 연결하는지 명확히 드러내세요.
- 세미콜론(;)이나 줄표(em dash) 대신 마침표를 사용하세요. 슬래시(/)와 "(s)"를 쓰지 마세요. 괄호 안의 텍스트는 완전한 문법 단위로 만드세요.
- 모든 곳에서 하나의 대상은 하나의 이름으로 부르세요.
- 관용구, 구어체 속어, 라틴어 약어, 은유를 건너뛰세요.

## 어조 및 저장소별 세부 규칙

- 이 스킬이 다루는 모든 문서에 **unslop** 스킬을 적용하세요. AI 어휘, 군더더기, 유보적 표현, 서식 습관 등 슬롭(slop) 패턴 카탈로그는 해당 스킬이 소유합니다.
- PR 설명과 커밋 메시지도 글쓰기입니다. Diátaxis를 제외한 모든 계층이 동일하게 적용됩니다. PR 본문은 리뷰어가 1분 안에 읽을 수 있는 브리핑이어야 합니다. 스웜 로그, SHA 목록, 메트릭 표를 직접 붙여넣지 말고 링크하세요.
- 제품 UI 문자열은 문서가 아닙니다. UI 문자열에는 제품의 카피라이팅 가이드라인을 따르세요.
- 코드 스니펫은 탭(tab)으로 들여쓰기하세요. 실제 경로를 적으세요. 개수나 트리 구조에 대한 모든 주장은 그것이 반영되는 커밋 시점에 참이어야 하며, 이를 다시 생성하는 명령어를 함께 포함하세요.
