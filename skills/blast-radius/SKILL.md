# 폭발 반경 (Blast radius)

변경사항이 출하되기 전에 다른 어딘가를 깨뜨리지 않는지 찾아냅니다. "X의 폭발 반경(blast radius of X)", "이게 뭘 깨뜨릴 수 있을까(what could this break)", 또는 아직 신뢰하기 어려운 작은 diff를 리뷰할 때 사용하세요.

`how` 및 `why`와 짝을 이루는 스킬입니다. `how`는 코드가 무엇을 하는지 알려줍니다. `why`는 코드가 왜 그런 형태를 띠고 있는지 알려줍니다. `blast-radius`는 그 변경이 다른 어딘가에서 무엇을 깨뜨리는지 알려줍니다.

단순히 호출자(caller) 목록을 나열하는 것은 이 스킬의 본분이 아닙니다. 에이전트는 grep으로 1초 만에 호출자를 찾을 수 있습니다. 진짜 할 일은 grep이 보여주지 않는 파손(breakage)을 찾아내는 것입니다.

## 스스로 작성한 분석 글만 믿지 마세요

그럴듯하게 들리는 폭발 반경 보고서는 아무 가치가 없습니다. 사실이든 아니든 읽는 사람에게는 설득력 있게 보이기 때문입니다. 그러니 글로 된 보고서만 덜컥 내밀지 마세요. 전체 안전성이 의존하는 한두 가지 핵심 사실을 찾아내고, 실제 코드를 실행해 그것을 증명하세요.

### 얼마나 확신하는가

변경사항의 안전성이 의존하는 각 사실에 대해, 비용이 저렴한 선에서 아래 목록의 최대한 깊은 단계까지 내려가고 어디까지 도달했는지 명시하세요.

1. 그냥 그렇다고 말함. 그 자체로는 무가치합니다.
2. 코드 줄을 가리킴. 실제 `file:line`, 또는 라이브러리 자체 소스 코드입니다.
3. 문제 상황이 발생할 수 없음을 보임. 실패 경로를 단계별로 따라가며 도달 불가능함을 확인했습니다.
4. 직접 실행함. 실제 코드를 호출하고 당신의 가정이 틀렸을 때 크게 실패(fail loud)하는 스크립트나 테스트를 돌렸습니다.
5. 실행 중인 앱에서 직접 재현함.

4단계는 대개 앱이 출하하는 것과 동일한 라이브러리를 임포트하여 우려되는 바로 그 함수를 호출해 보는 작은 스크립트 하나면 충분합니다.

## 단계 (Steps)

1. 변경사항을 읽습니다. diff 자체, 추가·변경·삭제되는 심볼, 그리고 diff에 명시적으로 적혀 있지 않은 부분까지 포함해 이제 무엇이 다르게 동작하는지 파악하세요. `why`의 2단계를 사용해 PR과 커밋들을 가져오세요.
2. 안전함을 보장하는 단 하나의 사실(the one fact)을 찾습니다. 위험해 보이는 대부분의 변경사항은 "이 호출은 이미 죽은 캐시 항목만 제거하고 다른 일은 전혀 하지 않는다"와 같은 단 하나의 사실 덕분에 안전합니다. 바로 그 사실을 찾으세요. 그 사실이 성립하면 위험해 보이던 대부분의 케이스가 한 번에 해소됩니다. 긴 추측성 목록(maybes)을 늘어놓는 대신 여기에 시간을 쓰세요.
3. grep이 멈추는 지점 너머를 보십시오. 호출하는 라이브러리의 소스 코드를 읽고, 고정된(pinned) 버전과 로컬 패치 여부를 확인하세요. 코드가 언제 실행되는지 따져보세요: 마이크로태스크(microtasks), 언마운트 및 티어다운(teardown), Solid 대 React의 차이 등. 심볼 검색이 놓치는 것들을 끝까지 추적하세요: API가 반환하는 JSON, DB 컬럼, 와이어 포맷, 동일한 바이트를 읽는 다른 언어의 코드, 피처 플래그, 세 홉(three hops) 하류에 있는 코드까지 살펴야 합니다.
4. 각 위험 요소에 대해 정직하게 평가하세요. 실제로 발생할 확률과 발생했을 때의 실질적인 피해 비용을 제시하세요. 확인된 위험 요소만 남기고, 점검 후 안전하다고 판명된 항목들은 별도로 분리해 나열하세요. `why`와 동일한 규칙을 따릅니다. 실제 `file:line`을 인용하고, 검색 결과가 없다는 사실 자체도 유의미한 답으로 기록하며, 절대 존재하지 않는 호출자나 API를 지어내지 마세요.
5. 단 하나의 사실을 증명하세요. 실제 코드를 실행하는 스크립트나 테스트를 작성해 돌리고, 그 실행 결과를 그대로 붙여넣으세요.
6. 규모가 크거나 영향 범위가 넓은 변경사항의 경우 `arena`로 실행하세요. 둘 이상의 모델에게 동일한 질문을 던지고 답을 병합하세요. 서로 다른 모델은 서로 다른 실제 버그를 잡아냅니다.

## 반환할 내용 (What to hand back)

- **무엇을 하는가 (What it does).** 자명하지 않은 부분까지 포함해 무엇이 바뀌었는지 설명합니다.
- **안전함을 보장하는 단 하나의 사실 (The one fact it's safe because of).** 그 사실을 명시하고, 위 확신 단계 중 몇 단계까지 도달했는지 밝힌 뒤 증명을 제시하세요. 증명하지 못했다면 미증명(unproven)이라고 적으세요.
- **위험 요소 (Risks).** 각각 어떻게 깨지는지, 관련 `file:line`, 발생 가능성과 심각도, 그리고 확인 방법을 명시합니다. 중요한 위험 요소에 대해서는 증명 결과를 붙여넣으세요.
- **해소된 항목 (Cleared).** 무엇을 점검했고 왜 안전한지 적습니다.
- **머지 전 조치 (Before you merge).** 당신이 작성한 스크립트를 포함해, 실제 버그를 잡아낼 수 있는 가장 저렴한 테스트나 재현 방법입니다.

`unslop`을 거쳐 문장을 다듬고, 실제 코드를 인용하며, 외부에 공개되기 전에 비공개 정보는 모두 제거하세요.

**응답(Reply):** 단 하나의 안전성 사실이 증명되었거나 미증명(unproven)으로 표시된 위 보고서.
