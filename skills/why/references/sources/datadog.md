# Datadog 텔레메트리 (Datadog Telemetry)

## 이 소스에 담긴 내용 (What this source contains)

Datadog은 무엇이 계획되었거나 논의되었는지가 아니라, 프로덕션에서 실제로 무슨 일이 일어났는지를 담은 런타임 기록을 보관합니다.

- **메트릭 (Metrics).** 팀이 계측한 카운터, 게이지, 히스토그램. 메트릭이 *존재한다는 것* 자체가 누군가 그 수치를 지켜볼 가치가 있다고 생각했다는 근거입니다.
- **모니터 및 알림 (Monitors & alerts).** 팀이 누군가를 깨울 만한 가치가 있다고 결정한 조건들. `rate_limit_hit > 10/min`에서 발생하는 모니터는 팀이 해당 임계값을 우려했다는 직접적인 근거입니다.
- **대시보드 (Dashboards).** 팀이 서브시스템에서 중요하다고 여기는 항목들을 큐레이션한 뷰.
- **APM 트레이스 및 스팬 (APM traces & spans).** 요청 수준의 런타임 데이터로, "왜 이렇게 느리지?" / "왜 여기에 타임아웃이 있지?" 같은 질문에 답합니다.
- **로그 (Logs).** 대용량 이벤트 기록으로, 방어적 코드의 동기가 된 에러 조건들을 담고 있는 경우가 많습니다.
- **인시던트 (Incidents).** 타임라인과 연결된 포스트모템을 포함한 공식 인시던트 기록.
- **노트북 (Notebooks).** 팀의 탐색적 조사 기록으로, 가설과 분석이 담겨 있는 경우가 많습니다.

## 검색 방법 (How to search it)

Datadog MCP를 사용하세요. 넓게 시작한 뒤 점차 좁혀 나가세요.

1. **소유 서비스(owning service) 식별하기.**

   ```
   search_datadog_services (이름 또는 팀으로 필터링)
   search_datadog_service_dependencies (업스트림/다운스트림 확인)
   ```

2. **대시보드와 모니터를 먼저 확인하기.**

   ```
   search_datadog_dashboards (쿼리: 기능 이름, 서비스 이름, 심볼)
   search_datadog_monitors   (동일한 쿼리)
   ```

   대시보드나 모니터가 대상 코드를 다루고 있다면, 그 쿼리와 감시 중인 임계값을 기록하세요. 임계값은 종종 "왜 이 값이 N으로 고정(clamp)되어 있지?"에 대한 답이 됩니다.

3. **대상 주변의 메트릭 확인하기.**

   ```
   search_datadog_metrics (이름 패턴으로 검색, 예: 기능 또는 심볼)
   get_datadog_metric_context (메타데이터: 설명, 단위, 태그)
   get_datadog_metric (시계열; "PR 날짜 무렵에 스파이크가 있었나?")
   ```

   메트릭의 궤적을 대상 코드의 추가/변경 날짜와 연관 짓는 것은 강력한 뒷받침 근거가 됩니다: "`payment_timeout` 메트릭이 2023-11-03에 치솟았고, 재시도 로직이 2023-11-06에 머지되었습니다."

4. **로그. 덤프하지 말고 좁혀서 검색하기.**

   ```
   search_datadog_logs (대상 주변의 원시 로그 패턴, use_log_patterns=true 설정)
   analyze_datadog_logs (SQL 스타일 집계, 카운트가 필요할 때만 사용)
   ```

   심볼, 에러 문자열, 또는 기능 이름으로 검색하세요. **시간 범위가 지정된 쿼리를 강력히 권장합니다** (예: 변경 전후 30일).

5. **APM 스팬 및 트레이스.**

   ```
   aggregate_spans    (통계: "이 엔드포인트가 얼마나 자주 실패하나?")
   search_datadog_spans (개별 스팬 검사)
   get_datadog_trace  (특정 트레이스 ID 조회)
   ```

   타임아웃, 재시도, 느린 경로(slow paths), 서비스 간 동작을 파악하는 데 유용합니다.

6. **인시던트.**

   ```
   search_datadog_incidents (제목, 팀, 날짜 범위로 검색)
   get_datadog_incident     (특정 인시던트의 전체 상세 정보)
   ```

   대상 코드가 방어적 코드로 보인다면, 그 코드가 추가된 시점 전후의 인시던트를 검색하세요. 타임라인에 "X에 대한 방어적 체크 추가"가 포함된 인시던트는 직접적 근거에 준합니다.

## 좋은 근거의 모습 (What good evidence looks like here)

- 쿼리와 임계값이 코드가 강제하는 제약 조건과 일치하는 모니터 (코드가 100으로 값을 제한하고, 모니터가 요청이 100/min을 초과할 때 알림을 발생시키는 경우)
- 대상 코드의 작성자가 만든 대시보드에 코드가 측정하거나 방어하는 대상과 일치하는 위젯이 있는 경우
- 코드가 머지되기 직전에 프로덕션 스파이크를 보여주고, 머지 이후 안정된 값을 보여주는 메트릭
- 대상 코드, 동일한 심볼, 또는 동일한 에러 문자열을 참조하는 인시던트 기록
- 변경 이전 시간 창에 타임스탬프가 찍혀 있으며, 해당 방어적 코드가 방지할 수 있는 특정 에러 패턴을 보여주는 로그

## 흔한 함정 (Common pitfalls)

- **상관관계는 인과관계가 아닙니다.** PR 이전의 스파이크와 이후의 안정화는 시사적일 뿐 결정적이지 않습니다. 같은 기간에 다른 변경 사항이 함께 배포되었을 수 있기 때문입니다. 주변 PR들을 함께 확인하세요.
- **찾아낸 차트에 과적합(overfitting)하기.** 차트는 작성자의 프레이밍을 반영합니다. "재시도 성공률"이라는 이름의 차트는 팀이 재시도 성공에 관심을 가졌다는 근거이지, 특정 코드 줄이 존재하는 이유에 대한 근거는 아닙니다.
- **사라진 텔레메트리.** 메트릭은 이름이 바뀌거나 삭제되거나 보존 기간이 짧을 수 있습니다. 해당 시간 창의 데이터를 찾을 수 없다면 그것은 결과가 없는 것(null result)이 아니라 공백(gap)입니다.
- **대규모 환경의 노이즈.** 서비스, 태그, 시간 창으로 로그 검색 범위를 적극적으로 좁히세요. 원시 로그를 덤프하기보다 `analyze_datadog_logs`를 사용해 집계하세요.
- **계측됨 != 원인.** 메트릭은 누군가 무언가를 측정할 만큼 신경 썼다는 것을 보여줄 뿐, 코드가 그 메트릭 *때문에* 추가되었다는 것을 보여주지는 않습니다. 커밋/PR 날짜와 교차 검증하세요.

## 반환할 내용 (What to return)

관련된 각 항목에 대해:
- 유형 (대시보드 / 모니터 / 메트릭 / 로그 패턴 / 트레이스 / 인시던트 / 노트북)
- 제목 또는 이름
- 링크 또는 식별자 (대시보드 ID, 모니터 ID, 메트릭 이름, 인시던트 ID)
- 소유자/작성자 및 생성일/수정일
- 질문과 관련된 구체적인 조건, 쿼리, 또는 인용구 (가능한 한 원문 그대로)
- 관련성: 이것이 대상 코드에 대해 무엇을 시사하는지, 그리고 연결 고리가 얼마나 강한지
