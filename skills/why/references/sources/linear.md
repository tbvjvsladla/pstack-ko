# Linear 티켓 (Linear Tickets)

## 이 소스에 담긴 내용 (What this source contains)

- 기능, 버그 및 그 동기를 설명하는 이슈들
- 이슈에 첨부된 프로젝트 문서 (주로 PRD나 스펙 문서)
- 상위/하위 이슈 관계 (더 넓은 이니셔티브 → 구체적인 티켓)
- 이슈에 달린 댓글 (명확화, 범위 변경, "왜 우리가 이 작업을 하는지"에 대한 근거)
- 동기의 유형을 알려주는 라벨 (예: `compliance`, `customer-request`, `perf`)
- 범위 변경을 설명하는 상태 업데이트
- 첨부 파일 및 연결된 GitHub PR

Linear는 제품/비즈니스 맥락이 살아 숨 쉬는 곳입니다. 즉, "고객 X가 요청해서 이 작업을 합니다"라든가 "이것은 3분기 컴플라이언스 이니셔티브를 위한 것입니다" 같은 계층의 정보가 담겨 있습니다.

## 검색 방법 (How to search it)

Linear MCP를 사용하세요.

1. **연결된 티켓부터 시작하세요.** 시드 커밋이나 PR이 티켓 ID(예: `ENG-1234`, `[BUG-567]`)를 참조한다면 `get_issue`로 해당 티켓부터 먼저 가져오세요. 댓글을 포함해 이슈 전체를 읽으세요.
2. **키워드로 관련 이슈 목록을 조회하세요.** 기능 이름, 핵심 심볼, 또는 비즈니스 용어로 텍스트 검색을 하여 `list_issues`를 사용하세요. 여러 가지 표현을 시도해 보세요.
3. **이슈 트리를 따라 올라가세요.** 하위 이슈(sub-issue)에 도달했다면 그 상위 이슈(parent)를 가져오세요. 하위 이슈는 전술적인 내용을 담고 있고, 상위 이슈가 "왜(why)"를 담고 있는 경우가 많습니다.
4. **프로젝트 문서를 읽으세요.** 이슈가 특정 프로젝트에 속해 있다면 `get_project`를 사용하고 첨부된 문서들을 확인하세요. 프로젝트 수준 문서는 스펙과 설계 근거가 가장 흔하게 기록되는 곳입니다.
5. **라벨과 마일스톤을 확인하세요.** 라벨은 동기의 카테고리(고객 요청, 인시던트 후속 조치, 컴플라이언스)에 대한 힌트를 줍니다. 마일스톤은 작업을 마감일과 연결해 주며, 이는 종종 동기를 드러냅니다.

## 좋은 근거의 모습 (What good evidence looks like here)

- 비즈니스 문제를 명시하는 이슈 설명: "고객사 Acme가 SOC2 감사 때문에 X 기능을 필요로 합니다"
- 의사결정을 기록한 댓글: "접근법 A는 과금 서비스를 건드려야 해서 접근법 B로 가기로 결정했습니다"
- 이니셔티브 형태의 제목을 가진 상위 이슈: "3분기 엔터프라이즈 준비 태세(Q3 Enterprise Readiness)" 또는 "결제 실패율 감소"
- 첨부된 PRD 또는 스펙 문서
- `customer:acme`, `incident-followup`, `compliance`, `perf-regression` 같은 라벨

## 흔한 함정 (Common pitfalls)

- **범위 드리프트 (Scope drift).** PR이 참조하는 티켓이 닫혔다가 다른 범위로 다시 열렸을 수 있습니다. 히스토리 전체를 읽으세요.
- **기계적인 템플릿 (Mechanical templates).** 일부 팀은 "Why" 섹션을 필수로 요구하지만 상투적인 문구(boilerplate)로 채우곤 합니다. 일반적인 문구("사용자 경험 개선")는 진짜 답이 아닐 가능성이 높습니다.
- **오래된 티켓 (Stale tickets).** 오래된 티켓은 변경되기 전 버전의 계획을 반영하는 경우가 많습니다. 날짜를 확인하고 코드의 실제 배포 날짜와 교차 검증하세요.
- **중복으로 닫힌 사슬 (Closed-as-duplicate chains).** 중복(duplicate-of) 관계를 따라 정본(canonical) 티켓까지 거슬러 올라가세요.
- **비공개 워크스페이스 콘텐츠 (Private workspace content).** 이슈에 접근할 수 없다면 추측하지 말고 공백(gap)으로 기록하세요.

## 반환할 내용 (What to return)

관련된 각 티켓에 대해:
- 티켓 ID 및 제목
- 설명이나 댓글에서 인용한 문제/동기 (패러프레이즈하지 마세요. 통합자가 인용할 수 있도록 정확한 원문 텍스트가 필요합니다)
- 라벨, 상위 이슈, 프로젝트
- 작성자, 생성일, 완료일(closed date)
- 가능한 경우 티켓 링크
