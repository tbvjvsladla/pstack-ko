# Ketchup

사용자가 `/ketchup` 직전에 작성한 마지막 메시지 이후로 이 채팅에서 무엇이 바뀌었는지 따라잡게 해주고, 단순히 현재 어디까지 왔는지뿐만 아니라 각 변경사항의 내용을 이해할 수 있도록 돕습니다. 그런 다음 사용자의 결정을 기다리는 모든 사안(calls)을 정리하여 사용자가 당신의 응답만 읽고도 즉시 결정을 내릴 수 있게 만드세요. 시스템 알림이나 서브에이전트 결과는 사용자의 메시지가 아닙니다. 사용자는 자신이 보낸 마지막 메시지만 기억하고 그 이후의 일은 전혀 모른다고 가정하세요.

[`/bro`](../bro/SKILL.md)의 과제가 아니라 그 목소리(voice)를 빌려 쓰세요: 한 사람이 다른 사람에게 근황을 알려주듯 평이한 단어, 짧은 문장, 전문 용어 배제(no jargon) 원칙을 지킵니다. 당신이 어떻게 작업했는지가 아니라 사용자 입장에서 무엇이 바뀌었는지를 말하세요. "CI가 그린이다" 대신 "테스트가 통과한다"라고 말하세요. 사용자가 행동을 취하는 데 꼭 필요한 경우가 아니라면 해시값, 파일 경로, 명령어, 빌드 번호, 테스트 개수는 모두 빼세요. 각 PR, 브랜치, 에이전트는 당신이 임의로 붙인 라벨이 아니라 사용자가 알아볼 수 있는 이름으로 부르세요. 어떤 사실을 이해하는 데 맥락이 필요하다면 맥락을 함께 제시하거나 아예 그 사실을 빼세요.

## 무엇이 바뀌었는지 수집하기 (Gather what changed)

이번 턴은 읽기 전용(read-only)으로 유지하세요. 이미 가지고 있는 자료만으로 시각 자료를 만드세요: 코드를 변경하거나, 앱이나 작업을 시작하거나, 외부에 무언가를 게시하지 마세요. 사용자의 마지막 메시지 이후 당신이 수행한 작업, 서브에이전트들의 보고, 그리고 이 채팅에 참여한 다른 주체들의 메시지를 수집합니다. 이 채팅이 건드린 각 PR, CI 실행, 에이전트의 현재 상태를 확인하세요. 제시할 모든 수치를 원래의 사실 데이터와 대조해 검증하고, 수치를 바로잡은 경우에는 그 사실을 명시하세요.

액션 아이템(action item)은 제품 선택, 승인, 되돌릴 수 없는 비가역적 조치, 또는 당신에게 없는 접근 권한처럼 오직 사용자만이 내릴 수 있는 결정이나 조치입니다. 사용자의 마지막 메시지 이전에 제기되었더라도 여전히 사용자를 기다리고 있는 사안이라면 모두 포함하세요. 당신이 스스로 더 진행할 수 있는 작업은 액션 아이템이 아닙니다. 응답을 채우기 위해 결정 사안을 억지로 만들어내지 마세요. 사용자가 요청하지 않았고 작업에도 필요하지 않은 단계는 액션 아이템이 아닙니다(단, 되돌릴 수 없고 사용자를 기다리고 있는 사안이라면 예외적으로 시각 자료 없이 한 줄로만 적으세요).

하나의 결정 사안(call)이 머지를 대기 중인 여러 PR 묶음처럼 여러 항목을 포괄할 수도 있습니다. 각 항목에 대해 링크, 사용자 입장에서 무엇이 바뀌는지, 당신의 추천(pick)을 뒷받침하는 근거, 위험도, 그리고 당신의 추천을 수집하세요. 결정에 필요한 사실 중 당신이 모르는 것은 "알 수 없음(unknown)"이라고 적으세요. 없는 링크는 생략합니다.

## 응답 작성하기 (Write the reply)

장황한 작업 무용담(story)이 아니라 결정 사안(calls)에 단어를 쓰세요. 일어난 일에 대한 설명은 그림을 제외하고 100단어 미만으로 유지하며, 일어난 일이 적다면 더 짧게 쓰세요. 사용자 입장에서 아무것도 바꾸지 못한 작업은 빼세요. 각 항목에는 약 30단어 정도를 할애합니다. 전체 응답 길이는 항목 수에 비례해 늘어납니다: 항목이 2개라면 그림을 제외하고 전체 150단어보다 훨씬 적어야 하고, 항목이 30개라면 훨씬 더 길어져야 합니다. 단어 수 제한에 맞추려고 항목을 삭제하거나 내용을 부실하게 줄이지 마세요: 목록 대신 개수만 적지 말고, 항목 설명 대신 링크만 달랑 걸지 마세요. 링크는 깊이를 더해줄 수 있지만, 오직 응답 본문만 읽고도 결정을 내릴 수 있어야 합니다.

사용자를 기다리는 사안이 무엇인지 알려주거나(또는 기다리는 사안이 없다고 말하는) 짧은 한 문장으로 서두를 여세요. 구체적인 내용은 액션 아이템 섹션에서 다룹니다. 만약 아무 일도 일어나지 않았고 사용자를 기다리는 사안도 없다면 그렇다고 말하고 즉시 멈추세요.

그다음 일어난 일을 보여주되, 그림을 먼저 배치합니다. 작업 과정에서 생성된 스크린샷과 비디오를 인라인으로 삽입하고, 이어서 변경사항을 설명하는 다이어그램을 넣습니다. 그런 다음 사용자가 요청했던 사항별로 짧은 불릿 하나씩으로 요약합니다: 결과가 어떻게 되었는지, 그리고 완료되었는지, 실행 중인지, 실패했는지, 미확인 상태인지 적습니다. 각 줄은 소리 내어 말하듯 자연스럽게 쓰세요: "Search review: done"이나 "Slow search: missing index" 대신 "인덱스가 빠져 있어서 검색이 느렸습니다(Search was slow from a missing index)"처럼 씁니다. 진행 도중 발견해 수정한 버그도 언급하세요. 각 줄은 그 줄만 단독으로 읽어도 사실이어야 합니다. 아직 사용자를 기다리고 있는 항목을 완료로 표시하지 말고, 아래 액션 아이템에서 다룰 내용은 요약에서 빼세요. 요약 아래에는 사용자가 알고 있는 사실이나 해야 할 일을 바꾸는 핵심 내용만 최대 세 줄 이내로 짧게 덧붙입니다. 그다음 당신이 스스로 처리할 수 있는 남은 작업을 한 줄로 적으세요.

그다음 액션 아이템을 나열합니다. 머지, 승인, 선택 등 사용자가 내려야 할 결정을 묻고 당신의 추천(pick)을 제시하세요. 당신이라면 가장 먼저 취할 단계가 곧 당신의 추천에 들어갑니다. 가장 먼저 일어나야만 하는 일과 되돌릴 수 없는 일도 마찬가지입니다. 여러 선택지 중 하나를 고르는 결정을 포함해, 결정 사안이 다루는 각 PR, 이슈, 에이전트의 번호나 링크를 제시하세요.

결정의 성격에 맞게 형태를 맞추세요. 단일 항목에 대한 결정은 불릿 하나로 씁니다: 항목 이름을 한 번만 적고 결정 내용, 당신의 추천, 사용자 입장에서 바뀌는 점, 추천 근거, 위험도를 적습니다. 여러 항목이 하나의 결정을 공유할 때는 결정 내용과 당신의 추천을 먼저 한 번만 적고, 가장 위험한 항목부터 순서대로 각 항목에 개별 불릿을 부여합니다: 링크와 이름, 사용자 입장에서 바뀌는 점, 추천 근거, 위험도를 적습니다. 개별 항목의 추천은 전체 결정의 추천과 다를 때만 명시하세요. 위험도가 낮더라도 각 항목의 위험도를 반드시 적으세요(예: "위험도 낮음: 색상만 바뀝니다"). 기다릴 때 발생하는 비용은 마감 기한이나 데이터 유실처럼 단순 지연 이상의 피해가 있을 때만 적으세요.

여러 선택지 중 하나를 고르는 결정에서는 작업 과정에서 저울질했던 모든 선택지를 제시하되, 각 선택지가 사용자에게 주는 이득과 치러야 할 비용, 그리고 현재 상태(있는 경우)를 함께 적으세요. 그 비용들이 곧 해당 결정의 위험도이므로 별도의 위험도 줄은 추가하지 마세요. 위쪽의 스크린샷들이 각 선택지를 보여주고 있다면 각 스크린샷 바로 아래에 해당 선택지의 이득과 비용을 적으세요.

## 시각 자료 (Visuals)

시각 자료란 스크린샷, 비디오, Mermaid 다이어그램, `/visualize`로 만든 차트나 다이어그램, 또는 생성된 이미지 같은 그림을 뜻합니다. 마크다운 표는 전후 비교 컬럼이 있더라도 시각 자료가 아닙니다.

문장보다 그림으로 파악하기 쉬운 내용이라면 직접 그리세요: 설계나 시스템의 동작 방식, 각 PR의 상태가 표시된 PR 스택이나 의존성 체인, 수정 전후 비교, 나란히 놓인 선택지들입니다. 단순 상태 목록, 액션 아이템 목록, 또는 서로 아무런 연결선도 없는 상자들은 절대 그림으로 그리지 마세요. 텍스트에서든 시각 자료들 사이에서든 동일한 사실을 두 번 반복해 제시하지 마세요.

각 시각 자료는 한눈에 읽힐 만큼 작게 유지하세요: 상자는 최대 6개, 각 상자 안의 단어는 최대 8단어 이내로 제한합니다. 라벨은 "Tests: pass" 같은 태그가 아니라 사람이 실제로 말할 법한 평이한 단어로 쓰세요. 문장 전체가 필요한 사실은 본문 텍스트에 들어가거나 아예 빼야 합니다.

눈에 보이는 변경사항이 있을 때는 스크린샷과 비디오를 단순 링크가 아니라 본문에 인라인으로 삽입하세요. 눈에 보이는 변경사항인데 스크린샷이 없다면 요약 줄에 "아직 스크린샷 없음(No screenshot yet)"이라고 표시하고 화면에서 무엇이 바뀌었는지 그곳에 적으세요. 다이어그램과 차트는 당신이 확보한 사실만을 바탕으로 그리세요: 요소들의 연결 구조에는 Mermaid 다이어그램을, 수치 데이터에는 `/visualize` 차트를 사용합니다. 수치를 지어내지 말고, 직접 캡처하지 않은 화면을 그리거나 생성하지 마세요. 실제로 존재하는 아티팩트만 링크하세요.
