# 공유 상태는 직렬화하기 전에 먼저 분리하라 (Separate Before Serializing Shared State)

동시에 실행되는 액터들이 가변 상태를 공유할 가능성이 있다면, 먼저 그들이 정말로 동일한 가변 객체를 필요로 하는지 질문하세요. 그렇지 않다면 공유 자체를 제거하세요. 공유가 불가피한 실제 요구사항일 때만 락 파일, 순차적 단계, 배타적 소유권 등을 통해 구조적으로 직렬화를 강제하세요. 지침이나 관례는 동시성 제어가 아닙니다.

**이유:** 공유 상태에 대한 동시 쓰기는 간헐적이고 재현하기 어려우며 디버깅 비용이 막대한 경쟁 조건(race condition)을 만들어냅니다.

**패턴:**
1. **공유 가변 상태를 식별하세요** (양쪽이 읽고 쓰는 파일, 양쪽이 푸시하는 브랜치, 양쪽이 정의하고 소비하는 API).
2. **기본 대응: 공유 쓰기 대상을 제거하세요.** 질문하세요: 이 액터들에게 하나의 정본(canonical) 객체가 필요한가, 아니면 각자 독립적인 사실을 발행하고 있는가? 각 액터에게 고유하게 소유한 파일, 키, 브랜치, 또는 상태 디렉터리를 부여하고, 읽기/보고 경계에서만 병합(merge)하세요. 두 워커가 하나의 `state.json` 안에 각자의 `lastX` 필드를 쓰는 것은 여전히 공유 가변 상태입니다. 반면 `indexer-state.json` + `metrics-state.json`으로 나누면 공유 변이가 아닙니다.
3. **단일 공유 쓰기 대상이 진짜 불변식일 때만 접근을 구조적으로 직렬화하세요** (락 파일, 순차적 단계, 단일 작성자 액터, 또는 원자적 CAS(compare-and-swap)). "락이 필요하다"는 생각이 들면 이를 기본 해답이 아니라 점검해 봐야 할 설계 냄새(design smell)로 취급하세요.
