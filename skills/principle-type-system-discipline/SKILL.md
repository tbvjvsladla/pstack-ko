# 타입 시스템 규율 (Type System Discipline)

컴파일러가 불가능한 상태, 잘못 짝지어진 원시 값, 처리되지 않은 변형(variant)을 거부하도록 만드세요. 에러 처리기와 예외 케이스 분기를 끝없이 늘리는 것보다, 애초에 에러와 특수 케이스가 존재할 수 없도록 타입으로 정의해 제거하는 쪽을 선호하세요. TypeScript 문법에 관해서는 `typescript-best-practices` 스킬을 참고하세요.

- **의미를 가진 원시 타입에 브랜드(brand)를 부여하세요.** `UserId`와 `OrderId`는 둘 다 내부적으로는 문자열이지만 서로 바꿔 쓸 수 없어야 합니다. TypeScript의 브랜드 교차 타입(branded intersection)이나 다른 언어의 뉴타입(newtype)처럼 각각에 고유한 타입을 부여하세요. 생성 시점에 한 번만 유효성을 검사하고, 하위 경로에서는 타입을 신뢰하세요. 두 인자가 동일한 원시 타입을 공유하지만 의미가 다르다면 브랜드를 부여하세요.
- **외부 데이터는 파싱되기 전까지 타입이 없는 것입니다.** RPC 페이로드, JSON, IPC 메시지, CLI 인자, 설정 파일, 환경 변수, 데이터베이스 행(row) 등이 모두 해당됩니다. 모든 시스템 경계에 파싱 함수를 두어 비구조화된 입력을 타입이 지정된 모델로 변환하세요. 유효성 검사를 어디에 두어야 하는지는 **boundary-discipline** 원칙 스킬에서 다룹니다.
- **권위 있는(authoritative) 스키마로부터 타입을 파생시키세요.** 프로토콜 버퍼, OpenAPI 명세, GraphQL 스키마, 데이터베이스 마이그레이션, 디자인 토큰 파일 등이 데이터 형태(shape)의 소유권을 가지고 있다면, 별도의 타입을 수작업으로 중복 정의하지 말고 해당 스키마로부터 파생시키세요. **encode-lessons-in-structure** 원칙 스킬을 참고하세요.
