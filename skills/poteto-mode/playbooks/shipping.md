### 배포 및 머지 (Shipping)

**무엇이 머지될지(land)에 대한 소유권은 당신에게 있습니다. 각 PR을 독립적으로 검증하고, 루트부터 연속으로 검증된 구간만 머지한 뒤, 스택에서 손을 떼세요.**

1. **포지(forge)를 결정한 다음, 머지하기 전에 각 PR을 독립적으로 검증하세요.** 기본값은 GitHub CLI(`gh`)입니다. `command -v origin`이 성공하고 Origin이 저장소를 확인할 수 있다면 모든 PR 작업에 `origin pr`을 사용하세요. 그렇지 않으면 `gh`를 유지하고 폴백을 기록하세요. Graphite(`gt`)를 필수로 요구해서는 절대 안 됩니다. PR당 한 명의 검증기(각각 Cursor 클라우드 에이전트)가 해당 표면의 제어 스킬(`cursor-team-kit`의 `control-ui` 또는 `control-cli` 등)을 사용하여 실제 사용자가 쓰는 방식 그대로 부모 브랜치 대비 헤드의 변경사항을 실행해 보고, 해당 PR에 `PASS`, `PASS+NOTES`, 또는 `FAIL`을 게시합니다. 작성자는 자신이 만들고자 의도했던 것만 확인하기 마련이므로, 코드를 작성하지 않은 에이전트가 내린 판정만 인정됩니다. 그린 CI와 봇의 승인 리뷰는 실제 사용자처럼 변경사항을 실행해 보지 않으므로 판정이 아닙니다.
2. **바닥(루트)에서부터 이어지는 연속으로 검증된 구간(contiguous verified run)만 머지하세요.** 가장 아래의 미머지 PR에서부터 위로 올라가며 `PASS` 또는 `PASS+NOTES`가 없는 첫 번째 PR에서 멈추세요. 그 아래의 PR들이 이번에 머지할 구간(run)이며, 그중 가장 위쪽 PR이 상한선(ceiling)입니다. 검증되지 않은 PR 위에 있는 검증된 PR은 아래쪽 코드 없이는 머지될 수 없으므로 대기합니다. 단, 브랜치가 아래쪽 코드를 포함하지도 않고 필요로 하지도 않는 PR은 트렁크로 이동시켜 독자적으로 머지할 수 있습니다. 이 경우 기존 판정은 아래쪽 코드가 깔린 상태에서 실행된 것이고 트렁크에는 그 코드가 없으므로 먼저 새로운 판정을 받아야 합니다.
3. **판정이 여전히 현재 코드를 설명하는지 다시 확인하세요.** 하나의 판정은 하나의 패치를 커버하며, 체인 리베이스는 어떤 체크도 실패시키지 않은 채 상위 PR들을 모두 새로운 SHA로 이동시킵니다. 이전 판정을 신뢰하기 전에 판정 시점 SHA의 `git patch-id`와 현재 헤드의 `git patch-id`를 비교하세요. 패치의 차이가 테스트, 문서, 또는 린트 설정뿐일 때는 레인이 실행한 대상이 노이즈를 제외하고 두 SHA에서 동일하게 빌드된다면 기존 레인의 결과가 유효합니다. 노이즈란 판정 SHA를 두 번 빌드했을 때도 나타나는 차이나 내장된 커밋 SHA를 말합니다. 독자가 판단을 검증할 수 있도록 각 노이즈의 종류와 해당 파일들을 보고하세요. 단, 변경된 부분 자체는 기존 판정이 본 적이 없으므로 새로운 체크와 리뷰를 받아야 합니다. 개발 서버처럼 빌드 산출물이 없는 레인은 이를 증명할 수 없으므로 다시 실행하고, 그 외에 드리프트한 모든 것도 다시 검증하세요.
4. **아래에서 위로(bottom-up), 한 번에 하나의 PR씩 머지하세요.** 항상 구간의 가장 아래쪽 미머지 PR을 `origin pr merge <pr>` 또는 `gh pr merge <pr> --squash`로 머지합니다. Origin에서는 기본 명령어가 지정한 PR 아래의 모든 PR도 함께 머지하며, GitHub에서는 베이스가 여전히 부모 브랜치인 PR을 머지하면 트렁크가 아니라 부모 브랜치로 머지됩니다. 머지 명령어는 머지 큐에 PR을 넣기만 했을 때도 성공으로 보고할 수 있고 자동 머지(auto-merge) 요청은 실제 머지가 아니므로, 반드시 PR을 다시 읽어들여(`origin pr view <pr>` 또는 `gh pr view <pr> --json state,mergedAt,baseRefName`) 결과를 확인하세요. 제대로 반영(land)된 PR은 부모 브랜치가 아니라 트렁크를 베이스로 하여 merged 상태로 조회됩니다. `--auto`(Origin의 merge-when-ready 또는 GitHub의 auto-merge)는 준비된 헤드가 무엇이든 그대로 머지해 버리므로, 판정이 현재 헤드를 커버하고 있는 PR에만 무장(arm)하세요. 머지가 반영된 후에는 베이스가 방금 머지된 브랜치였던 다음 PR의 타겟을 트렁크로 변경(`origin pr edit <pr> --base <trunk>` 또는 `gh pr edit <pr> --base <trunk>`)하고, 패치를 머지 결과 위로 옮긴 뒤 `--force-with-lease`로 푸시하세요. 판정은 커밋이 아니라 패치를 커버하므로 3단계의 patch-id 규칙이 판정의 유효성 유지 여부를 결정합니다. 체크가 통과하고 판정이 유효하게 유지되면 해당 PR을 머지하세요.
5. **스택이 머지되는 동안에는 스택을 건드리지 마세요.** 머지는 판정 여부와 무관하게 그 순간 브랜치와 베이스에 담겨 있는 내용을 그대로 반영해 버리므로, 브랜치나 베이스에 가하는 변경은 4단계에서 다음 PR을 이동시키는 작업뿐이어야 합니다. GitHub에서는 `playbooks/babysit.md`의 큐 워처(`scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>`)를 `/loop` 아래에서 실행하여 상한선(ceiling)에서 `COMPLETE`가 보고될 때까지 감시하세요. Origin에서는 `origin pr checks <pr> --watch`가 반환될 때마다 `origin pr view <pr> --checks`로 현재 PR을 다시 읽으며 상한선이 merged로 조회될 때까지 반복하세요. 부모가 머지될 때 베이스가 트렁크로 이동하는 것은 정상적인 동작이지 수리해야 할 손상이 아닙니다. 머지가 정체되면 무언가를 바꾸기 전에 먼저 왜 정체되었는지 원인을 파악하세요.
6. **상한선(ceiling)에서 멈추세요.** 구간을 더 연장하려면 새로운 판정이 필요하므로 1단계부터 새로운 패스를 시작해야 합니다.

**응답(Reply):** 검증된 구간과 그 상한선, 각 PR의 판정 결과와 판정을 내린 주체, 머지된 항목과 이를 확인한 방법, 그리고 다음 공백(gap)을 메우기 위해 필요한 사항.
