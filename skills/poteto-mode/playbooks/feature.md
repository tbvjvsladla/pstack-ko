### 기능 개발 (Feature)

**설계에 대한 소유권은 당신에게 있습니다. 계획하고, 리뷰하고, 검증하세요.** 구현은 위임하고 당신은 주도를 유지하세요.

1. 영향을 받는 서브시스템에 대해 `how`를 실행하세요.
2. 병렬 설계 탐색을 위해 `architect`를 실행하세요.
3. 처리량 체크포인트(throughput checkpoint)를 네 개의 할 일(todo) 항목으로 작성하세요. 단일 파일 수정이나 팬아웃 없음 등 실제로 해당하지 않는 차원은 항목을 삭제하지 말고 `n/a: <reason>`과 함께 남겨 두세요:
   - **블로킹 선행 단계 (Blocking first steps).** 게이트는 팬아웃 전에 실행됩니다.
   - **독립적인 워크스트림 (Independent workstreams).** 겹치지 않는 파일, 서비스, 또는 계층은 병렬로 처리합니다. 공유 쓰기는 직렬화합니다.
   - **공유 가변 상태 (Shared mutable state).** 기본적으로 대상을 분할합니다(**separate-before-serializing-shared-state** 원칙 스킬). 실제 불변식(invariant)이 있을 때만 직렬화하세요.
   - **가장 작은 안전한 분해 (Smallest safe decomposition).** 단일 워커가 최선이라면 그 이유를 명시하세요.
4. 구체적인 범위(파일 경로, **principle-model-the-domain**에 따른 명명된 데이터 형태와 그 조직화 구조 — 흩어진 불리언 대신 상태 머신, 분기문 대신 테이블/레지스트리, 반복되는 형태 가정 대신 타입 모델 — 를 위임 에이전트가 로직을 작성하기 전에 먼저 선택하고, 성공 기준을 함께 명시)를 지정하여 설정된 feature 모델(기본값 `grok-4.7-xhigh-fast`)을 사용하는 서브에이전트에 코드 작성을 위임하세요. 서브에이전트(Subagents) 섹션에 따라 작업에 맞게 각 서브에이전트의 추론 수준과 빠른(fast) 또는 표준(standard) 속도를 선택하세요. 에러 처리, 추상화 계층, 테스트 구조 등 구현이 여러 유효한 형태를 허용할 때는 주자(runner)들이 대안을 수면 위로 올리고 교차 심사위원(cross-judge)이 선택을 검증하도록 **arena** 스킬을 통해 위임하세요. 이는 필수 사항입니다: 사유를 적어 건너뛰는 우회(skip-with-reason)는 허용되지 않으며, Laziness Protocol로도 이를 오버라이드할 수 없습니다(얻는 이득은 절약된 코드 줄 수가 아니라 리뷰 분리이기 때문입니다). 하위 에이전트 생성이 금지된 서브에이전트는 동일한 리뷰 분리를 유지한 채 직접 diff를 소유함으로써 이 요건을 충족합니다. 중첩된 에이전트를 기다리는 "대기 중(standing by)" 응답은 하지 마세요. 주석은 **주석(Comments)** 섹션 규칙을 따릅니다. 외과수술처럼 정밀하게 수정(surgical edits)하고, 업스트림에서 파생된 파일은 원본 소스에 다시 근거를 두세요. 공유 프리미티브(shared-primitive) 개선사항은 모든 소비자에 이식하고 각각을 검증하세요. 자주 커밋하세요.
5. 해당 표면에서 검증하세요. "결론 내릴 수 없음(Inconclusive)"이나 다른 표면에서의 확인은 통과가 아닙니다. 이를 명확히 표시하세요.
6. 작고 순서가 정돈된 커밋들로 리베이스하세요. 후속 작업은 스택으로 쌓으세요.
