### 프로토타입 (Prototype)

**당신은 코드가 아니라 설계 결정(design decision)을 소유합니다. 프로토타입은 일회성 도구입니다. 실제 빌드는 Feature 플레이북을 따릅니다.**

Laziness Protocol의 "가장 작은 변경" 원칙과 검증 기준이 정반대로 뒤집히는 유일한 플레이북입니다. 완성도(polish)보다 속도가 우선이며, 코드 품질은 중요하지 않고 계획도 세우지 않습니다. 엄격함은 올바른 설계를 저렴하게 선택하는 데 있습니다. 사용자가 요청하지 않은 변형(variation)도 제안하고, 한 접근법을 과감히 버리고 다른 접근법을 시도하세요.

1. 프로토타입이 내리고자 하는 결정의 범위를 정의하세요: 어떤 레이아웃인지, 어떤 인터랙션인지, 어떤 밀도(density)인지, 또는 경험적 갈림길의 경우 어떤 동작, 타이밍, 접근법인지 명확히 합니다. 내릴 결정이 없다면 프로토타입도 없습니다. Feature로 라우팅하세요.
2. 설계 공간이 열려 있을 때는 레퍼런스를 수집하세요. 선행 사례(prior art)를 검색하고 테마, 팔레트, 레이아웃의 무드보드를 요약한 뒤 빌드하기 전에 사용자가 방향을 고르게 하세요. 방향이 이미 정해져 있다면 건너뜁니다.
3. 프로덕션 소스와 분리된 격리된 스크래치 디렉터리에 일회성으로 빌드하세요. 시각적 결정의 경우 바닐라 HTML/CSS/JS 또는 아이디어를 렌더링할 수 있는 가장 가벼운 스택, CDN 의존성, 핫 리로드가 되는 개발 서버를 사용합니다. 동작이나 타이밍 결정의 경우 해당 질문을 시험해 볼 수 있는 가장 작은 스크립트를 작성합니다. 프로덕션 프레임워크도, 테스트도, 추상화도 사용하지 마세요.
4. 대안들을 비교할 때는 각 변형에 라벨을 붙이고 하나의 스위처(버튼이나 키 입력) 뒤에서 전환할 수 있게 빌드하세요. 이것이 **exhaust-the-design-space** 원칙 스킬을 저렴하게 구현하는 방법입니다.
5. 해당 표면에서 검증하세요. 시각적 결정의 경우 제어 스킬을 통해 각 변형의 스크린샷을 찍고 인터랙션을 구동해 보세요. 동작이나 타이밍 결정의 경우 타이밍을 로깅하거나 출력을 인쇄하거나 렌더링을 관찰하여 결정하려는 대상을 직접 관찰하세요. 여기서는 단언문(assertion)이 아니라 관찰 자체가 테스트입니다.
6. 대안, 트레이드오프, 그리고 추천안을 제시하세요. 산출물은 배포 가능한 코드가 아니라 결정 사항과 일회성 산출물입니다. 실제 빌드를 위해 선택된 방향을 **Feature**(또는 형태 설계를 위해 `architect`)로 넘기세요.

**응답(Reply):** 탐색한 변형들, 증거(시각적 결정의 경우 스크린샷, 동작 결정의 경우 관찰된 출력이나 타이밍), 트레이드오프, 당신의 추천안, 그리고 스크래치 경로. 프로토타입이 일회성(throwaway)임을 평이한 말로 명확히 밝히세요.
