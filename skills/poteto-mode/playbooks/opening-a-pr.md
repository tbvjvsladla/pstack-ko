### PR 열기 (Opening a PR)

다른 모든 플레이북의 마지막에 호출됩니다.

**워크트리 (Worktree).** `main`에서 분기한 git 워크트리에서 작업하세요. 서브에이전트들은 이를 상속받습니다. 동일한 브랜치에 대한 여러 `Task` 호출은 각각 자체 워크트리를 갖거나 호출 사이에 `git fetch && git reset --hard origin/<branch>`를 수행합니다. 무관한 작업이 섞여 더러워진 브랜치는 패치로 추출한 뒤 새 워크트리를 만들어 적용하세요. 엉켜버린 워크트리는 `main`에서 리셋하고 최소한으로 다시 작업하세요.

**커밋 (Commits).** 자주 커밋하세요. PR을 열기 전에 작고 순서가 정돈된 커밋들로 리베이스하세요. 각 커밋은 미래의 PR입니다: 단독으로 반영 가능(landable)하고 스토리를 전달하도록 순서가 잡혀 있어야 합니다. 수정사항이 방금 만든 커밋에 속한다면 amend하세요. 분리 가능하다면 새 커밋으로 만드세요. 커밋 본문은 제목(subject)을 반복해서 서술하지 않습니다.

**PR.** 커밋 전에 diff에 대해 `cursor-team-kit`의 `/deslop`을 실행하고, 리뷰 전에 `/no-comments`를 실행하세요. 모든 PR 제목, 설명, 커밋 본문은 `/technical-writing`(Diátaxis를 제외한 모든 계층을 적용하고 STE 어휘 규칙 적용: 동작당 하나의 단어, 관사 유지, 가능한 곳에서는 `-ing` 형태 대신 평이한 동사 사용)으로 작성한 다음 `/unslop`을 적용하세요.

**제목 (Titles).** Conventional Commits 형식인 `type(scope): subject`를 따르며 끝에 마침표를 찍지 않습니다. 타입은 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf` 등을 사용합니다. 범위(scope)는 `pstack`이나 `poteto-mode` 같은 영역입니다. 제목(subject)은 짧고 명령조(imperative)로 작성하며, 특정 심볼이 변경의 핵심을 담당할 때는 `fix(pstack): retarget opening-a-pr babysit trigger`처럼 실제 심볼 이름을 명시하세요.

**설명 (Descriptions).** PR 본문은 diff를 앞에 두고 있는 리뷰어를 위한 1분 브리핑이지 실험 노트가 아닙니다. 왜 이 변경이 존재하는지, 무엇을 제외했는지, 무엇을 깨뜨릴 수 있는지, 그리고 어떻게 동작을 증명했는지를 말합니다. 식별자를 최소화하여 짧고 단순한 문장으로 작성하고, 텍스트의 벽(walls of text)을 만들지 마세요. 본문은 스쿼시(squash) 커밋 본문이 되므로 약 40줄 이내로 유지하세요. 굵은 글씨 도입부 대신 아래 순서대로 `##` 헤딩을 사용하고, 할 말이 없는 섹션은 생략하세요:

- `## Why`: 문제와 접근법, 1~3개의 짧은 문장. SHA, 리베이스 계보, 또는 "based on main" 같은 서두는 적지 마세요.
- `## What changed`: 1~3개의 짧은 불릿. 실제 심볼이나 경로는 변경의 핵심을 담당할 때만 명시하세요. 이름 변경(rename)이나 타겟 변경(retarget)은 전후 양쪽을 모두 명시하세요.
- `## Scope`: 항상 작성합니다. 다루는 범위와 의도적으로 제외한 항목(후속 작업, 알려진 공백)에 대한 1~3개의 짧은 항목. 심볼, 경로, 또는 파일별 장문 나열은 금지합니다.
- `## Tradeoffs`: 리뷰어가 그렇지 않으면 물어볼 법한 기각된 대안들만 적습니다. 실질적인 선택의 기로가 없었다면 생략하세요.
- `## Blast Radius`: 누구 혹은 무엇에 영향을 미치며 왜 안전하거나 위험한지 1~2문장으로 적습니다. `main`이 레드 상태라면 레드 상태로 방치할 때의 비용을 명시하세요.
- `## Verification`: 1~3개의 불릿으로, 각각 실제 실행 경로와 그 결과를 적습니다. 성능(Perf)의 경우 단위가 포함된 핵심 수치 하나, `before → after`, 그리고 나머지를 확인할 수 있는 arena 또는 swarm 디렉터리 링크를 적습니다. 샘플 크기 방법론, 스웜 과정 나열, 지표 표는 본문에 넣지 마세요.

섹션들 아래에는 주장을 증명하는 비디오나 스크린샷이 있을 때 첨부하세요. 전체 SHA, 스웜이나 아레나 레인 상세 내역, 지렛대 수정 에세이, 파일별 체크리스트, "CLEAN" 판정 내역은 본문이 아니라 링크된 산출물에 넣으세요.

**포지 (Forge).** 첫 번째 PR 작업 전에 포지를 결정하고 생성, 편집, 조회, 감시, 머지에 그 선택을 일관되게 유지하세요. 기본값은 GitHub CLI(`gh`)입니다. `command -v origin`이 성공하고 Origin이 저장소를 확인할 수 있다면 `origin pr ...`을 우선 사용하세요. Origin이 없거나 저장소를 확인할 수 없다면 `gh`를 유지하고 폴백을 기록하세요. Graphite(`gt`)를 필수로 요구하지 마세요.

**내장 PR 도구 (Built-in PR tool).** 실행 환경이 내장 PR 도구를 제공할 때는 포지 CLI가 아니라 반드시 내장 도구를 통해 생성, 편집, 타겟 변경(retarget), 준비 완료 표시(mark ready)를 수행하세요. CLI로 만든 PR은 내장 도구가 추적하는 정보를 놓치게 됩니다. 내장 도구가 다루지 않는 작업, 그리고 내장 도구가 없는 실행 환경에서의 모든 PR 작업에는 결정된 포지를 사용하세요.

**크기 및 스택 (Size and stacks).** 하나의 거대한 PR보다 다섯 개의 좁은 PR을 선호하세요. 스택은 베이스 브랜치 사슬(chain)입니다. 루트 PR은 트렁크를 타겟으로 삼습니다. 각 자식 브랜치는 부모의 정확한 최신 팁(tip) 위로 리베이스하며 자식 PR은 부모 브랜치를 타겟으로 삼습니다. 부모가 머지되면 `playbooks/shipping.md` 4단계에 따라 자식을 트렁크 위로 이동시키세요. 내장 PR 도구가 없다면 결정된 포지에 따라 `origin pr create --status open --base <parent-branch>` 또는 `gh pr create --base <parent-branch>`로 자식 PR을 생성하고, `origin pr edit <pr> --base <parent-branch>` 또는 `gh pr edit <pr> --base <parent-branch>`로 타겟을 변경하세요. 독립적인 작업일 때만 트렁크에서 분기하세요. 대규모 스택 작업 전에는 트렁크 위로 리베이스하세요.

**준비 상태 (Readiness).** 모든 PR은 초안(draft)이 아니라 즉시 리뷰 가능한 준비 완료(ready) 상태로 여세요. 내장 PR 도구는 기본값이 draft일 수 있으므로 모든 생성 호출에 `draft: false`를 설정하세요. Origin에서는 `--status open`을 전달하세요. `gh`에서는 `--draft`를 생략하세요. 만약 그래도 PR이 초안으로 열린다면 PR 도구를 통해 준비 완료로 표시하거나 결정된 포지에 따라 `origin pr ready <number>` 또는 `gh pr ready <number>`를 실행하세요. PR 상태를 언급하기 전에는 반드시 `origin pr view <number>` 또는 `gh pr view <number>`를 실행하세요.

**베이비시팅 (Babysit).** PR을 열었다고 해서 베이비시팅이 시작되지는 않습니다. URL을 게시하고 계속 빌드하세요. 단계나 스택을 먼저 끝내세요. 전체 스택이 만들어진 후 사용자가 요청할 때만 별도의 베이비시팅 패스를 실행하세요. 새 PR마다 베이비시팅을 하면 빌드가 지체되고 이후 웨이브에서 어차피 재시작될 커밋들에 체크 자원을 낭비하게 됩니다. 피드백이 원래 의도에서 벗어나면 반론을 제기하세요.

PR을 여는 서브에이전트는 `/deslop`과 `/no-comments`를 실행하고 URL을 게시합니다. 해당 서브에이전트가 Autopilot-full 또는 Autopilot-stack 소유자가 아니라면 베이비시팅을 하지 않고 부모에게 복귀합니다. 오토파일럿 소유자의 브리핑에는 베이비시팅 루프가 할당되어 있으며 그것이 곧 `playbooks/babysit.md`가 기다리는 사용자 요청 역할을 합니다. 소유자는 준비 완료(code-ready) 보고 후 루프를 시작하고 머지 준비 완료(merge-ready)를 보고하며, 전체 스택이 빌드될 때까지 베이비시팅을 보류하라는 이곳 및 `playbooks/babysit.md`의 규칙에서 면제됩니다.
