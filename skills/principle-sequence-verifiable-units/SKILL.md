# 검증 가능한 단위로 작업 순서를 배치하라 (Sequence work into verifiable units)

작업을 각각 확인 가능한 상태로 끝나는 작은 단위들의 연속으로 배치하고, 현재 단위가 통과(green)하기 전에는 다음으로 넘어가지 마세요.

**이유:** 문제를 일으킨 바로 그 단위에서 잡힌 깨짐(break)은 원인을 국소화하기 매우 저렴합니다. 반면 일괄 처리 후에 발견된 깨짐은 어디서 잘못되었는지 파묻혀 버리며, 이미 망가진 기반 위에 추가 작업까지 쌓아 올린 뒤가 됩니다. 이 동일한 단위들을 리뷰어가 그대로 재생해 볼 수 있는 전달 순서로 배열하면 "저를 믿으세요"가 "실패(red)했다가 통과(green)하는 과정을 직접 보세요"로 바뀝니다.

**실행(Execution).** 일괄 수정(sweep), 마이그레이션, 또는 유사한 편집의 연속 작업을 수행할 때는 다음 변경을 시작하기 전에 각 변경을 검증하세요. 각 단위는 전후 괄호(before/after bracket) 구조를 가집니다: 정상으로 확인된 상태 → 단일 변경 → 검증 실행 → 다음으로 진행. 모든 검증이 실제 베이스라인을 기준으로 측정되도록 먼저 깨끗한 트렁크(trunk)에 리베이스하세요. 지렛대(스크립트 등)가 편집을 수행할 때는 단위별 검증 비용이 거의 무료에 가깝습니다. 반드시 실행하세요.

**전달(Delivery).** 작업을 증명하는 순서대로 커밋과 PR을 쌓으세요(stack). 가장 표준적인 형태는 실패하는 테스트를 먼저 두고 그 위에 수정 커밋을 올리는 것입니다. 그 밖의 서사 구조로는 형태 변경 전에 불필요한 코드를 먼저 덜어내기(뺄셈), 처치 적용 전에 베이스라인 먼저 캡처하기, 기능 추가 전에 스캐폴드 먼저 구축하기 등이 있습니다. 각 커밋은 그 자체로 온전히 성립해야 하며, 커밋들의 연속은 하나의 논증(argument)처럼 읽혀야 합니다.

각 검증을 실제 산출물 기반으로 유지하는 **prove-it-works** 원칙 스킬, 그리고 단위별 검증 비용을 저렴하게 만드는 **build-the-lever** 원칙 스킬과 짝을 이루는 순서 배치 원칙입니다.
