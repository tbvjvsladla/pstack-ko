# 프롬프트 작성법 (Word the prompt)

프롬프트는 의도와 완료 확인 기준(check for done)을 명시합니다. 구체적인 실행 단계는 플레이북이 제공하므로, 장황한 명세서보다 평이한 몇 문장이 훨씬 더 효과적입니다.

## 포함해야 할 것 (Put in)

- 목표(The goal). 무엇이 잘못되었는지 또는 사용자가 무엇을 원하는지 말하세요.
- 완료 확인 기준(The done check). 통과하거나 실패할 수 있는 기준이어야 합니다. "더 좋게 만들어 줘"나 단순 실행 시간은 확인 기준이 아닙니다.
- 제시할 증명(The proof to show). 실제 명령어 출력, 실행 흐름을 담은 비디오, 저장된 값, 또는 변경 전후 비교 수치를 요구하세요.
- 사용자가 이미 알고 있는 정보. 증상, 재현 단계, 로그, 또는 링크를 알려주면 에이전트가 헤매는 시간을 아낄 수 있습니다.
- 실질적인 제약 조건. "repro first(재현부터 먼저)", "don't change any code yet(아직 코드는 건드리지 마)", "zero behavior change(동작 변경 없음)", "let me review before proceeding(진행하기 전에 내가 먼저 리뷰하게 해 줘)" 같은 문구는 각각 에이전트의 행동을 직접적으로 바꿉니다.

## 빼야 할 것 (Leave out)

- 구체적인 방법(The how). 무엇을 달성해야 하는지만 말하고, 에이전트가 더 나은 방법을 찾을 수 있도록 여지를 남겨 두세요.
- 스킬이나 단계의 나열. 손으로 직접 적은 실행 순서는 플레이북이 원래 유지하는 중요 단계를 빠뜨리거나 순서를 뒤섞게 만듭니다. 특정 선택을 명시적으로 덮어쓸(override) 때만 스킬 이름을 지정하세요.
- 원인에 대한 사용자의 추측(에이전트가 문제를 자신의 말로 다시 서술하기 전까지). 섣불리 제시된 추측은 탐색 범위를 좁혀버립니다.

## 컨텍스트 먼저 로드하기 (Load the context first)

- 노이즈가 많은 리포트의 경우, 에이전트가 다른 일을 시작하기 전에 먼저 근본 문제를 자신의 말과 평이한 언어로 다시 서술하게 하세요. 코드를 한 줄도 쓰기 전에 오해를 바로잡을 수 있습니다.
- 새 채팅창에서는 `/recall`로 해당 주제에 대한 이전 작업 내역을 불러오세요. 이전 채팅에는 새 에이전트가 모르는 귀중한 맥락이 담겨 있습니다.
- 익숙하지 않은 코드를 변경하기 전에는 `/how`로 동작 메커니즘을 묻고 `/why`로 설계 이유를 물으세요. 추적된 멘탈 모델이 없는 에이전트는 가장 그럴듯해 보이는 첫 번째 지점에서 증상만 덧대어 고칩니다.
- "증상이 아니라 근본 원인을 고친 것임을 나에게 납득시켜 봐(convince me it fixes the cause and not the symptom)"처럼 `/teach`에게 특정 선택의 논거를 대보라고 요청하세요. 단순 요약보다 논거가 검증하기 훨씬 쉽습니다.

## 계획보다 설계가 먼저 (Design before the plan)

- 절대 첫 번째 설계를 그대로 채택하지 마세요. 몇 가지 선택지에 대한 프로토타입(UI의 경우 스크린샷이나 비디오 포함)을 요청하고 실제 근거를 보며 고르세요.
- 프로토타입이 미해결 질문들에 답하게 하세요. 추상적인 계획서를 놓고 적대적 리뷰를 하지 마세요. 리뷰어들이 실제로는 절대 일어나지 않을 가상 위험 요소들을 지어내게 됩니다.
- 공유 패키지나 API의 경우 README나 튜토리얼부터 먼저 작성하게 한 뒤 거꾸로 코드를 향해 작업하게 하세요. 그 문서가 에이전트가 스스로를 검증하는 기준점이 됩니다.
- 계획(plan)은 설계가 확정된 후에만 요청하세요. 계획의 각 단계는 반드시 검증(check)으로 끝나야 합니다.

## 후속 지시는 짧게 (Follow up short)

- 일단 채팅이 과업 맥락을 잡고 나면 "do it(해)", "continue(계속해)", "keep going until done(끝날 때까지 계속 진행해)" 한 마디면 완전한 프롬프트로 충분합니다.
- 주제가 바뀔 때는 "new task(새 작업)"로 시작하세요. 그렇지 않으면 모드가 새 메시지를 이전 과업의 다음 단계로 취급합니다.

## 자리를 비우기 전에 (Before stepping away)

- 에이전트가 질문을 멈추도록 "im going to bed(나 자러 간다)" 또는 "im stepping away(자리 비운다)"라고 말하세요.
- 완료 조건을 매 반복(iteration)마다 실행할 수 있는 검사들로 정의하고, `/loop`에 그 술어(predicate)를 넘겨주세요.
- 지정된 베이스 브랜치에서 분기한 새 워크트리에서 작업하라고 지시하세요.
- "커밋하기 전에 나한테 물어보지 마(don't ask me before committing)"처럼 에이전트가 멈춰서 물어볼 만한 사항들에 미리 답을 주세요.
- 나중에 감사할 수 있도록 의사결정 로그(decision log)를 남기라고 요청하세요.
- 탈출 조건을 주세요: "몇 시간 후에도 정말로 막혀 있다면 멈추고 왜 막혔는지 적어 놔(if you're truly stuck after a few hours, stop and write up why)".

## 한 줄로 방향 조종하기 (Steer in one line)

- 목표 재확인: "i said the goal is to repro. i did not ask for a fix yet. (목표는 재현이라고 했지, 아직 고쳐 달라고 하지 않았다.)"
- 원칙 이름 지목: "apply prove it works. show me the real output, not the build log. (prove-it-works 원칙을 적용해. 빌드 로그 말고 실제 출력을 보여줘.)"
- 에이전트가 이미 원칙 규칙을 읽었기 때문에 원칙 이름만 대도 즉시 작동합니다. 에이전트의 다음 응답에는 해당 규칙이 어떤 결정을 바꾸었는지 명시됩니다.
