# 검증 스킬 생성 (Create a verification skill)

모든 진지한 프로젝트에는 실제 앱을 구동하고 동작을 증명할 수 있는 스크립트화된 방법이 필요합니다: 앱을 실행하고, 사용자가 하는 방식 그대로 기능을 조작해 보고, 근거(evidence)를 캡처하는 것입니다. 이 스킬은 그것을 저장소에 맞춤화된 프로젝트 로컬 스킬(`.cursor/skills/verify-<app>/`)로 생성합니다. 생성기의 산출물은 인간이 아니라 다음 에이전트를 위해 작성합니다. 이 문서는 앱을 한 번도 본 적이 없는 에이전트가 작업 도중 사전 맥락 없이(cold) 읽게 될 것입니다.

## 1. 사용자가 아니라 저장소를 인터뷰하세요

코드베이스에서 다음 질문들의 답을 찾고, 직접 관찰할 수 없는 것만 사용자에게 질문하세요:

- **표면 (Surface):** 사용자가 실제로 무엇을 만집니까? 웹 UI, CLI/TUI, 데스크톱 앱, API, 모바일 앱, 라이브러리? 저장소에 여러 개가 있을 수 있으니 주된 표면 하나를 고르고 나머지는 기록해 두세요.
- **실행 (Run):** 로컬에서 앱을 어떻게 시작합니까? 저장소 자체에 문서화된 개발 명령어(package scripts, Makefile, README quickstart)를 우선하세요. 포트, 환경변수, 시드 데이터, 인증 방식을 기록하세요.
- **구동 (Drive):** 에이전트가 프로그래밍 방식으로 앱과 어떻게 상호작용할 수 있습니까? 기존 하네스를 가장 먼저 찾으세요(Playwright/Cypress 스펙, expect 스크립트, PTY 헬퍼, curl 호출 가능한 엔드포인트, 디버그 포트). 기존 하네스가 없을 때만 일반적인 레시피를 선택합니다: 웹 및 Electron은 브라우저/CDP, CLI/TUI는 tmux/PTY 하네스, 서비스는 일반 HTTP를 사용합니다.
- **관찰 (Observe):** 어떤 근거를 캡처할 수 있습니까? 스크린샷, 터미널 트랜스크립트, 응답 본문, 로그, 종료 코드, DB 상태 등입니다.
- **격리 (Isolate):** 두 개의 인스턴스를 나란히 실행할 수 있습니까(포트, 데이터 디렉터리, 프로필 분리)? 불가능하다면 생성된 스킬에 그 사실을 명시하세요. 공유 인스턴스를 중복 구동해 사용자의 세션을 망가뜨리는 것보다 구동을 거부하는 편이 낫습니다.

현재 체크아웃된 코드가 있는 그대로 빌드되거나 시작되지 않는다면, 스킬을 생성하기 전에 먼저 그 문제를 고치거나(또는 정확히 보고하거나) 하세요. 깨진 기반 위에서 작성된 스킬은 잘못된 절차를 가르치게 됩니다. 만약 API가 실제로 서빙하지도 않는 정적 디렉터리나 샘플 설정 파일처럼 본질과 무관한 누락 자산 때문에 시작이 막힌다면, 생성된 스킬이 이를 검증용 스캐폴딩으로 명확히 표시하여 생성하고 정리(cleanup) 단계에서 제거하도록 구성할 수 있습니다.

## 2. 스킬 생성하기

YAML frontmatter(`name: verify-<app>` 및 앱 이름, 표면, 언제 이 스킬을 찾아야 하는지를 명시한 `description` 포함 — frontmatter가 없으면 스킬이 절대 등록되지 않습니다)와 아래 섹션들을 갖춘 `.cursor/skills/verify-<app>/SKILL.md`를 작성하세요. 각 섹션은 플레이스홀더 없이 1단계 코드베이스 조사에서 실제로 확인한 내용에 기반해야 합니다:

- **Launch (실행):** 검증을 위해 앱을 시작하는 정확한 명령어와, 앱이 준비되었음을 확인하는 방법(특정 로그 줄, 프롬프트 등)입니다. Launch는 마이그레이션과 시드 데이터를 포함하여 빈 데이터 디렉터리에서 출발해 실제로 사용 가능한 상태에 도달해야 합니다. 준비 완료(Ready)란 단순히 프로세스가 응답하는 것이 아니라 실제로 사용 가능한 상태를 뜻합니다. 데이터베이스 헬스 체크는 초기화 스크립트가 아직 실행 중일 때도 통과할 수 있습니다. 종료(teardown) 방법도 포함하세요. 짧게 실행되고 끝나는 CLI나 TUI의 경우 계속 살려둘 서버가 없으므로, launch는 바이너리 빌드(또는 의존성 설치)를 한 번 수행한 뒤 각 구동을 격리된 고유 PTY나 tmux 세션에서 시작하는 것을 의미합니다.
- **Doctor (상태 점검):** "이 인스턴스를 구동할 가치가 있는가?"에 답하는 단일 읽기 전용 검사입니다 — 프로세스 실행 여부, 올바른 버전/빌드 여부, 포트가 우리 소유인지, 인증이 유효한지 확인합니다. 에이전트는 무언가 이상해 보일 때마다 이 명령을 가장 먼저 실행합니다.
- **Drive (구동):** 가상의 예시가 아니라 이 저장소의 실제 셀렉터/명령어를 사용한 하네스 레시피입니다. 좌표나 탭 순서보다 안정적인 핸들(ARIA 라벨, data 속성, 프롬프트 문자열, 라우트 경로)을 선호하세요.
- **Evidence (근거):** 증명을 위해 무엇을 캡처하고 어디에 저장할지 정의합니다. 증명 기준을 명시하세요: 내부 세터(setter)나 테스트 전용 엔드포인트가 아니라 실제 사용자 경로를 실행할 것; 최종 화면뿐만 아니라 수행한 액션과 그 결과 상태를 함께 캡처할 것; 눈에 보이는 화면과 더불어 부수 효과(기록된 파일, 삽입된 행, 전송된 메시지)를 검증할 것; 목(mock)은 프로덕션 경계가 이미 외부 시스템을 격리하고 있는 곳에서만 사용할 것. 안전한 경로가 드라이런(dry-run)이나 테스트 모드일 때는 이름만 믿지 말고 실제로 무엇을 건너뛰는지(파일, 네트워크, git ref) 직접 관찰하여 검증하세요. 어떤 드라이런은 여전히 네트워크에 접근하거나 브라우저를 엽니다.
- **Cleanup (정리):** 실행 과정에서 생성한 인스턴스를 내리는 방법입니다. 절대 프로세스 이름으로 종료(kill)하지 말고, 당신이 직접 시작한 프로세스만 종료하세요. Cleanup은 인스턴스와 임시(scratch) 상태만 제거하며 절대 근거 자료를 지우지 않습니다. 증명 아티팩트는 스킬이 지정한 위치에 그대로 보존되어야 합니다.
- **Helpers (헬퍼):** 스킬과 함께 제공되는 모든 스크립트는 실행 가능(executable)해야 하며, 스킬 본문에 호출 방법이 명시되어야 합니다. 읽는 사람이 역공학(reverse-engineer)해야 하는 헬퍼는 헬퍼가 아닙니다.

## 3. 기능 맵(feature map) 시드 생성하기

`.cursor/skills/verify-<app>/features/README.md` 파일과 함께, 식별 가능한 사용자 대면 기능별로 파일을 하나씩 생성하세요(라우트, 명령어, 메뉴, 문서 등을 바탕으로 상위 3~5개 기능부터 시작하는 것을 목표로 합니다). README 인덱스와 기능별 파일 하나로 구성된 [`references/feature-map-example/`](references/feature-map-example/)의 형태를 따르세요. 각 파일은 사용자의 관점에서 다음 질문에 답합니다: 이 기능은 무엇인가, 어떻게 도달하는가, 하네스로 어떻게 구동하는가, 그리고 어떤 관찰 가능한 최종 상태가 정상 동작을 증명하는가. 네 개의 H2 헤딩은 `Sub-features`, `How to get to it (user POV)`, `Driving it with <harness>`, `Gotchas`입니다. 만약 시드 데이터에 특정 사용자 여정(journey)이 필요로 하는 전제 조건이 빠져 있다면, 여정은 실패를 보고해야 하며 그 원인은 해당 기능의 `Gotchas`에 기록합니다. 통과시키기 위해 여정을 임의로 약화시키지 마세요. 기능 맵은 저장소에서 유지관리되는 검증 원천입니다. 맵에 다른 진입점들이 나열되어 있는데 편리한 진입점 하나만 구동한 증명은 불완전한 증명입니다.

## 4. 인계하기 전에 생성된 스킬 직접 증명하기

생성된 스킬의 지침을 처음부터 끝까지 직접 한 번 실행해 보세요: launch, doctor, 매핑된 기능 중 **하나** 구동(하나면 충분합니다. 나머지 기능들은 이후 실행에서 다룰 수 있도록 맵이 존재하는 것입니다), 근거 캡처, cleanup 순으로 진행합니다. cleanup 이후에는 지정된 위치에 근거 아티팩트가 여전히 남아 있는지 확인하세요 — 증명 자료까지 지워버리는 cleanup은 이 단계를 통과하지 못합니다. 실패하는 부분은 수정하고, 실패한 반복 시도 직후에도 생성된 cleanup을 매번 실행하여 실패한 시도가 프로세스나 포트를 고아 상태로 남겨두지 않게 하세요. 한 번도 실행되지 않은 생성 스킬은 초안이지 산출물이 아닙니다. 만약 실제 타깃 대신 대역 환경(새 VM 대신 컨테이너, 원격 스택 대신 로컬 스택 등)에서 증명했다면, 실제 타깃에서는 자동으로 수행되지 않는 대역 환경의 설정 단계들을 모두 나열하세요. 해당 단계들은 실제 타깃에서 실행해 보기 전까지는 미검증 상태로 남습니다.

## 5. 유지보수 루프 안내하기

앱이 변경됨에 따라 기능 맵을 최신 상태로 정직하게 유지할 수 있도록 사용자에게 `/maintain-verification-skill`을 안내하세요. 실행 주기는 사용자가 물어볼 때만 제안합니다.
