# 정형 검증 스킬 유지보수 (Maintain a formal verification skill)

정형 검사는 자신이 기술하는 대상의 속성을 증명합니다. 코드는 바뀌었는데 검증 모델이 바뀌지 않으면, 검사는 더 이상 존재하지 않는 옛날 코드를 기술하면서 계속 통과(pass)할 수 있습니다. 바로 그 통과가 가장 위험한 케이스인데, 겉보기에는 완벽한 증명처럼 보이기 때문입니다. 이 스킬은 `/create-formal-verification-skill`이 생성한 검증 스킬, 또는 지정된 코드를 대상으로 모델 체커, 증명기(prover), 코드 수준 검증기를 실행하는 모든 프로젝트 로컬 스킬을 위한 유지보수 루프입니다. 에이전트가 해당 검증 스킬을 사용하면서 변경을 가할 때는 프로젝트 로컬 스킬이 직접 처리를 담당합니다. 반면 이 스킬은 검증 스킬을 건너뛴 변경들(머지, 스킬 없이 이루어진 편집, 여러 커밋에 걸쳐 누적된 드리프트)을 처리합니다.

## 결과 분류 (Outcomes)

각 검사에 대해 아래 결과 중 하나를 부여하고 무엇인지 명시하세요:

- **in sync (동기화 상태)**: 마지막 동기화 이후 검사가 기술하는 내용을 바꾸는 변경이 없었으며, 검사가 통과합니다.
- **updated (업데이트됨)**: 코드가 변경되었고, 이제 검증 모델이 새 코드를 기술하며, 검사가 통과합니다.
- **bug (버그 발견)**: 검증 모델이 현재 코드를 정확히 기술하고 있으며, 현재 코드가 속성을 위반합니다. 이는 드리프트가 아니라 실제 코드에 대한 결함 발견(finding)입니다.
- **blocked (차단됨)**: 검사를 코드와 다시 일치시킬 수 없었거나 실행할 수 없었습니다. 정확한 이유를 밝히세요.

하나의 검사가 **updated**이면서 동시에 **bug**일 수 있습니다: 업데이트를 통해 검증 모델이 다시 현재 코드를 정확히 기술하게 되었고, 그 상태에서 속성이 실패하는 경우입니다.

## 편집 범위 (Edit scope)

오직 검증 자산(모델, 하네스, 속성 파일, 검증 스킬 문서 자체)만 편집하세요. 사용자가 명시적으로 요청하지 않는 한 실행 도중 제품 코드를 절대 편집하지 마세요. 현재 코드에서 속성이 실패할 때 통과시키기 위해 속성이나 모델을 임의로 약화시키지 마세요. 실패를 있는 그대로 보고하세요.

## 수행 절차 (Pass)

1. **검사 찾기.** 검증 스킬에는 고정된 이름이 없으므로 수행하는 역할로 찾으세요: 지정된 코드를 대상으로 모델 체커, 증명기, 또는 다른 검증기를 실행하는 프로젝트 스킬입니다. 발견한 각 스킬(또는 사용자가 지목한 스킬)을 읽으세요. 각 검사에 대해 검증하는 속성, 커버하는 코드 범위, 상한(bounds) 및 가정, 실행 명령어, 그리고 해당 검사가 코드를 정확히 기술하고 있음을 마지막으로 확인한 커밋(sync commit)을 수집합니다. 검증 스킬이 존재하지 않으면 작업을 멈추고 `/create-formal-verification-skill`을 안내하세요. 스킬에 동기화 커밋이 기록되어 있지 않다면 검증 파일들을 마지막으로 변경한 커밋을 대신 사용하고, 그렇게 했다고 밝히세요.

2. **현재 상태 그대로 실행하기.** 무언가를 변경하기 전에 각 검사를 있는 그대로 한 번 실행하고 결과를 기록하세요. 여기서 통과했다고 해서 현재 코드가 올바르다는 뜻은 아닙니다. 단지 이전 기술(description)이 그 자체로 성립한다는 뜻일 뿐입니다. 여기서 발생한 실패는 드리프트일 수도 있고 실제 버그일 수도 있습니다. 5단계에 도달하기 전까지는 둘 중 무엇인지 성급히 단정하지 마세요.

3. **커버리지 대상 코드의 모든 변경사항 읽기.** 동기화 커밋부터 현재 커밋까지 커버리지 대상 파일들의 diff를 확인하고 각 커밋 메시지를 읽으세요. 이동한 코드도 놓치지 마세요: 이름이 바뀌었거나, 쪼개졌거나, 다른 파일로 옮겨진 함수도 여전히 커버리지 대상 코드입니다. 또한 동일한 필드에 쓰기 작업을 하는 새 함수처럼 검사가 보호하는 상태를 건드리는 새로운 코드도 찾으세요. 각 변경사항에 대해 다음 네 가지 중 무엇에 해당하는지 판단합니다:
   - **영향 없음 (No effect).** 포맷팅, 주석, 또는 검증이 다루지 않는 코드 경로처럼 검증이 기술하는 내용을 전혀 바꾸지 않는 변경입니다. 커밋 메시지만 믿지 말고 실제 모델이나 하네스와 대조해 확인하세요.
   - **검증이 더 이상 코드를 기술하지 않음 (The verification no longer describes the code).** 원래 하나의 불가분한 동작(indivisible action)이었던 단계가 둘로 쪼개졌거나, 분기가 추가·제거되었거나, 검사 위치가 이동했거나, 보호 대상 상태에 도달하는 새 경로가 생겼거나, 값의 범위가 달라진 경우입니다. 모델이나 하네스를 변경해야 합니다.
   - **약속이 의도적으로 변경됨 (The promise changed on purpose).** 변경사항이 코드가 보장하는 약속 자체를 바꾸었으며, 변경 내의 근거(문서화 주석, 테스트, 체인지로그, 커밋 메시지)가 그것이 의도된 것임을 명확히 보여주는 경우입니다. 속성을 변경해야 하며, 반드시 해당 근거를 인용해야 합니다.
   - **약속이 깨졌을 가능성 있음 (The promise may be broken).** 코드는 바뀌었지만 약속 자체가 바뀌었다는 근거는 없는 경우입니다. 이어지는 실패는 실제 버그 후보로 취급합니다.

4. **실행 결과가 아니라 코드로부터 업데이트하기.** 변경된 각 부분이 다시 리뷰어가 열어볼 수 있는 실제 코드를 가리키도록 모델이나 하네스를 수정하고, 코드에서의 불가분한 한 단계를 검증에서도 한 단계로 유지하세요. 재실행하기 전에 실제 코드를 보고 업데이트를 작성하며, 검사를 통과시키는 방향으로 업데이트를 끼워 맞추지 마세요. 속성은 오직 약속이 의도적으로 변경된 경우에만 수정합니다. 이전 문구, 새 문구, 그리고 근거를 함께 기록하세요. 코드 변경으로 인해 기존 상한(bounds)이 틀리게 된 경우가 아니라면 상한을 그대로 유지하세요. 어쩔 수 없이 상한을 줄여야 한다면 보고서에 그 사실을 명시하세요.

5. **재실행 및 각 결과 판정하기.**
   - **통과 (Pass):** 업데이트된 기술이 실패할 수 있는 능력 자체를 잃어버려 엉터리로 통과했을 수도 있습니다. 새 검사를 제거하거나 새 단계의 순서를 바꾸는 등 속성이 방어하려는 방식대로 새 코드를 일부러 망가뜨려 보고, 검사가 그 파손을 잡아내는지 확인하세요. 확인 후 망가뜨린 코드는 원래대로 되돌립니다.
   - **실패 (Fail):** 반례(counterexample)를 실제 코드 위에서 단계별로 재현(replay)해 보세요. 만약 어떤 단계가 실제 코드에서는 일어날 수 없는 일이라면 검증 모델이 틀린 것입니다. 검증 모델을 고치고 무엇이 틀렸었는지 밝히세요. 반대로 모든 단계가 실제 코드에서 일어날 수 있는 일이라면 실제 버그입니다. 버그를 도입한 커밋을 지목하고, 반례를 코드 자체의 용어를 사용한 단계별 순서로 설명하며, 발생하는 피해를 한 문장으로 서술하세요. 실제 코드를 대상으로 한 저렴한 테스트나 재현 스크립트로 버그를 보여줄 수 있다면 근거로서 보고서에 추가하세요. 단, 제품 코드에 이를 커밋하지는 마세요.

6. **검증 스킬 업데이트하기.** 각 검사가 커버하는 코드 범위, 실행 명령어, 상한, 가정, 그리고 동기화 커밋(sync commit)을 업데이트합니다. 동기화 커밋은 당신이 확인을 마친 커밋으로 설정하세요. 차단된(blocked) 검사에 대해서는 동기화 커밋을 이동시키지 말고 보고서에 그 사실을 알리세요. 그런 다음 다음 에이전트가 할 것처럼 검증 스킬의 지침을 한 번 그대로 따라가 보며 모든 단계가 여전히 잘 실행되는지 확인하세요.

## 보고 (Report)

각 검사에 대해 사용자에게 다음 사항을 보고하세요:

- 판정 결과(outcome)와 당신이 읽은 커밋들;
- 검증에서 무엇이 왜 바뀌었는지(코드의 형태가 바뀌었는지, 아니면 의도적으로 약속이 바뀌었는지 각 변경에 대한 짧은 이유와 근거 포함);
- 재실행 결과와, 업데이트된 검사가 여전히 실패할 수 있음을 입증하기 위해 사용했던 고의 파손(break) 내용;
- 발견된 각 버그에 대한 평이한 설명: 코드의 용어로 된 단계별 반례, 피해 내용, 버그를 도입한 커밋;
- 마땅히 커버해야 하지만 아직 커버하지 못하고 있는 새 코드를 포함해, 검증이 여전히 다루지 않는 영역.

어떤 실패가 검증 모델의 드리프트였고 어떤 실패가 실제 코드의 버그였는지 명확히 구분해 말하세요. 업데이트 전에는 통과했다가 업데이트 후에 실패한 검사의 경우, 이전의 통과는 낡은 기술(stale description) 위에서의 가짜 통과였다고 분명히 밝히세요.

검증 업데이트는 제품 코드 수정과 분리하여 별도의 독립된 변경으로 묶으세요.
