# 독자의 인지 부하를 최소화하라 (Minimize Reader Load)

유지보수성이란 코드를 이해하기 위해 읽는 이(독자)가 해야 하는 노동의 양입니다. 두 가지 축을 추적하세요: **추적해야 할 계층**(질문과 답 사이의 간접 참조 단계)과 **머릿속에 유지해야 할 상태**(독자가 기억하고 있어야 하는 숨겨진 혹은 가변적인 컨텍스트)입니다. 코드 줄 수(LOC), 순환 복잡도(cyclomatic complexity), "클린 아키텍처"는 대리 지표(proxy)일 뿐입니다. 정말로 중요한 것은 독자의 인지 부하입니다. 이 두 축은 서로 독립적입니다. 전역 변수 50개가 있는 평평한 파일 하나는 6계층짜리 어댑터 스택만큼이나 추론하기 어렵습니다. 두 축을 모두 방어하세요. 이는 [컨텍스트 윈도우를 사수하라](../principle-guard-the-context-window/SKILL.md)의 인간 버전입니다. 코드를 읽는 사람의 작업 기억(working memory) 역시 유한합니다.

- 절약해 주는 것보다 비용이 더 많이 드는 **계층을 허무세요(collapse)**: 호출자가 하나뿐인 래퍼, 두 번째 구현체가 없는 어댑터, 결국 필요 없었던 추측성 간접 계층 등이 그 대상입니다. 인라인(inline)으로 합치세요.
- **인접한 계층은 추상화 수준을 바꾸어야 합니다.** 동일한 메서드와 인자를 그대로 반복 전달하기만 하는 계층은 정보 압축 없이 독자의 부하만 늘립니다. 단순 통과(pass-through) 계층을 허무세요.
- **인터페이스 압축을 요구하세요.** 복잡성을 거의 숨기지 못하는 넓은 인터페이스는 독자로 하여금 인터페이스 표면과 내부 구현 양쪽을 모두 학습하게 만듭니다. 의미 있는 결정들을 캡슐화하여 숨기는 경계를 선호하세요.
- **상태의 범위를 축소하세요:** 가변(mutation)보다 반환값을 쓰는 순수 함수를, 필드보다 지역 변수를, 모듈 상태보다 필드를, 전역 상태보다 모듈 상태를 선호하세요. 상태를 동기화하려 하지 말고 필요할 때 파생(derive)시키세요.
- 모든 소비자 코드마다 반복하지 말고 **경계에서 불변식(invariant)에 이름을 붙이세요.** 그래야 독자가 한 번만 배우면 됩니다.
- 계층이나 상태를 하나 추가하기 전에 자문하세요: 이것이 다른 곳에서 줄여주는 독자의 부하가 최소한 이만큼 이상인가?

**판단 기준:** 코드를 처음 읽는 사람이 "X는 어디서 오는가?"와 "무엇이 X를 바꿀 수 있는가?"라는 질문에 30초 안에 답할 수 있는가? 그렇지 않다면 계층을 줄이거나 상태를 줄이세요.
