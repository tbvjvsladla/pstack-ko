# No comments

Comment Sicko를 띄웁니다. 수용된 발견 사항에 따라 조치를 취합니다.

Comment Sicko의 신선한 관점을 존중하세요.

## 범위 (Scope)

호출자가 지정한 파일이나 diff를 사용합니다. 별도 지정이 없다면 베이스 브랜치(기본값 `main`) 대비 워킹 트리를 포함한 현재 diff를 사용합니다.

## 단계 (Steps)

1. `subagent_type: "comment-sicko"`로 `Task`를 띄웁니다. 범위를 전달하세요. **poteto-mode** 스킬의 Subagents 섹션에 따라 작업에 맞게 각 서브에이전트의 추론 수준과 속도(fast 또는 standard)를 선택하세요. Comment Sicko의 자체 규칙을 프롬프트에 다시 장황하게 되풀이하지 마세요.
2. 보고서와 diff를 검사합니다. 애플리케이션 코드 편집, 범위 이탈(scope escapes), 예외 규칙으로 보호되는 주석의 삭제, 잘못 진술된 `MUST KILL` 사유, 그리고 의도적으로 유지된 정상 코드를 유죄로 취급하는 플래그들은 기각(reject)하세요. 우리 코드의 기이한 동작(our-code surprises)에 대한 재구성(reshape) 플래그는 유효한 조치 대상으로 남깁니다. 그런 주석들은 복원하지 마세요. 유지(keep) 판정은 오직 우리가 변경할 수 없는 외부 요인에 대한 주석이라는 증명이 있을 때만 살아남습니다. 범위 내에서 누락된 린트 및 TypeScript 억제(suppression) 주석이 없는지 감사하세요. 정합성(correctness)이나 안전성 관련 억제는 조치해야 할 `MUST KILL`로 유지됩니다. 삭제된 주석은 정확한 예외 사유와 범위 내 증명이 있을 때만 복원하세요. 근거가 빈약한 `IMPORTANT` 또는 `do not remove` 주석의 삭제(kill)나 유지(keep)를 수용하기 전에, 해당 심볼에 대해 `/how` 또는 `/why`를 실행하세요. 삭제 판정이 모호하더라도 주석을 복원하지 마세요. 유지 판정이 반박되거나 여전히 모호하다면 해당 주석을 삭제하세요. 기각된 보고서는 실패 사유를 명시하여 변경을 되돌린(revert) 뒤 한 번 재실행합니다. 두 번째 보고서마저 기각되면 미해결(open)로 보고하고 `/no-comments`를 실패 처리합니다.
3. 사소하게 수용된 플래그들은 죽은 경로(dead path) 삭제, 불필요한 매개변수 제거, 또는 실제 API 사용을 통해 직접 수정합니다. 만약 어떤 수정에 구조적 설계(shape)가 필요하다면, 수용된 항목 묶음과 주변 코드를 대상으로 `/architect`를 한 번 실행하세요. 스케치 단계에서 멈춥니다. Architect는 형태를 잡고, 4단계가 구현합니다.
4. 범위 내에서 가장 작은 근본 원인(root-cause) 수정을 구현합니다. 지목된 모든 우회책(workaround)을 제거하세요. 만약 근본 원인이 범위를 벗어나 있다면, 범위 내에서 가능한 가장 작은 수정을 반영하고 나머지는 미해결(open)로 보고하세요. **principle-fix-root-causes** 및 **principle-redesign-from-first-principles** 스킬은 의도의 방향만 안내할 뿐입니다. 두 스킬 모두 작업 울타리(fence)를 임의로 넓히거나 범위 밖의 사례들까지 고칠 권한을 부여하지 않습니다. 절대 증상만 가리는 임시 방어 코드(symptom guards)를 덧대지 마세요.
5. 제약 조건 주석(constraint comments)은 `do not remove`, `do not change wording`, 또는 `talk to X before changing` 같은 문구를 담고 있습니다. 우리가 변경할 수 없는 외부 요인에 대한 유지(keep) 주석은 그대로 두세요. 그 외에는 범위 내에서 가장 저렴한 타입, 런타임, 테스트, 또는 CI 린트 인코딩 방안을 제안하고 대화형 승인을 기다리세요(무인 실행 및 평가 모드에서는 호출자의 사전 승인이 필요합니다). 승인되면 코드로 인코딩한 뒤 주석을 삭제합니다. 승인되지 않으면 주석을 삭제하고, 해당 제약 조건을 미해결로 보고한 뒤 범위 밖 후속 작업을 스케치하세요.
6. 삭제된 주석 수, 복원된 주석, 재실행 내역, architect 스케치, 수정 내역, 인코딩 제안, 실제 적용된 인코딩, 강제되지 않은 제약 조건, 그리고 기타 미해결 작업을 보고합니다.
