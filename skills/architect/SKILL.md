# Architect

`not implemented` 본문과 의사코드를 사용해 타입, 함수 시그니처, 클래스 형태, 모듈 경계를 스케치합니다. 여러 모델의 관점을 종합(synthesize)한 뒤, 선택된 스케치를 기준으로 실제 코드를 채워 넣습니다.

## 시작

시작하기 전에 단계별로 항목이 하나씩 들어간 할 일 목록(todolist)을 엽니다.

1. 기반 파악(Ground)
2. 스케치(Sketch)
3. 합의(Agree)
4. 구현(Implement)
5. 폐기 및 재설계(Scrap)

## Phase A: 문제 기반 파악 (Ground the problem)

새 코드가 건드리는 모든 시스템에 대해 실질적인 멘탈 모델을 구축합니다. 관련 서브시스템 전반에 걸쳐 **how** 스킬을 실행하세요. 단순히 파일 이름을 나열하는 것은 기반 파악이 아닙니다. `how`가 규정하는 아키텍처 설명을 작성하세요. 만약 설계가 소유권(ownership)이나 계층 구조(layering)를 재정의한다면, 기존 형태에 대해 **why** 스킬도 함께 실행하여 기존 설계 근거가 추측이 아닌 제약 조건으로 작동하게 만드세요.

주변에 통합할 시스템이 전혀 없는 순수 그린필드(greenfield) 작업일 때만 Phase A를 건너뜁니다.

## Phase B: 스케치 (Sketch)

설계 스케치 과제와 Phase A의 기반 파악 산출물을 가지고 **arena** 스킬을 실행합니다. 각 러너(runner)의 프롬프트로 `references/runner-prompt.md`를 전달하세요.

러너 목록은 `pstack-models.mdc` 규칙의 `arena runners` 줄 대신 `architect runners` 줄에서 가져옵니다. 해당 규칙 파일이나 해당 줄이 없다면 `claude-opus-5-5-xhigh`와 `grok-4.7-xhigh-fast`를 사용합니다. 별칭(alias) 및 거부된 항목 처리는 **arena** 스킬 Phase A의 러너 규칙을 따릅니다.

두 번 설계하세요(Design it twice). 첫 번째 설계가 충분해 보이더라도 종합 단계로 넘어가기 전에 구조적으로 구별되는 최소 두 개 이상의 후보를 요구해야 합니다. 이는 **exhaust-the-design-space** 원칙 스킬을 구체화한 것입니다. 하나의 형태 안에서 부분 수정만 하는 것이 아니라 전체 형태에 대한 대안을 탐색해야 합니다.

종합하기 전에 모든 후보를 [`references/design-red-flags.md`](references/design-red-flags.md)에 비추어 검증하세요. 다음 기여자가 자신이 열어본 파일만 보고, 가장 가까운 예제를 복사하며, 컴파일되는 가장 짧은 경로를 택하는 에이전트라고 가정하세요. 한 파일에서 보기에 올바른 변경이 저장소 전체에서도 올바른 결과가 되도록 만드는 설계를 선호하세요.

유효한 후보들을 인터페이스 깊이(interface depth) 기준으로 비교하세요. 더 작고 단순한 공개 표면(public surface) 뒤에 더 많은 복잡성을 숨기는 설계를 선호하세요. 풍부한 인터페이스는 기능을 여러 계층에 흩뿌리는 대신 한곳에 집중시켜 호출 체인을 짧게 유지할 수 있습니다.

Arena는 종합된 단일 설계 패키지를 반환합니다. 이 종합 결정 내용은 설계 근거 문서의 "Synthesis decision" 섹션을 채웁니다.

## Phase C: 합의 (Agree - 선택 사항)

기본값: 인간 체크포인트 없이 종합된 설계를 바탕으로 곧바로 구현으로 진행합니다.

호출자가 "/architect with checkpoint", "구현하기 전에 멈추고 보여줘(stop and show me before implementing)" 등 명시적으로 요청한 경우에만 체크포인트를 활성화합니다. 이 경우 종합된 설계를 제시하고 승인을 받을 때까지 일시 중지합니다.

어느 쪽이든 종합된 스케치는 **foundational-thinking** 원칙 스킬의 "스캐폴드 우선(scaffold first)" 모드에 따라 그 자체로 별도의 커밋으로 먼저 출하될 수 있습니다. 본문을 채워 넣는 동안 발생하는 계획되고 범위가 제한된 파손(breakage)은 **outcome-oriented-execution** 원칙 스킬에 따라 허용됩니다. 구현에 앞서 설계에 적대적 압박(adversarial pressure)을 가해 검증하려면 종합된 스케치에 대해 **interrogate** 스킬을 실행하세요.

만약 인간이 (체크포인트에서든 사후에든) 설계 형태에 이의를 제기하면, 이를 Phase A의 새로운 근거 데이터로 취급하세요. 코드를 더 작성하기 전에 기반을 다시 파악(Re-ground)하고 Phase B를 재실행하세요.

## Phase D: 스케치에 맞춘 구현 (Implement against the sketch)

`not implemented` 본문을 실제 코드로, 의사코드를 실제 로직으로 교체합니다. 종합된 스케치는 곧 계약(contract)입니다. 스케치에서 벗어나는 편차는 조용히 흡수할 마찰이 아니라 수면 위로 드러내야 할 신호입니다. 만약 어떤 함수에 스케치가 예상하지 못한 매개변수가 필요하다면, 스케치가 틀렸던 것인지, 요구사항을 놓친 것인지, 아니면 구현이 범위를 넘어선 것인지 자문해야 합니다.

## Phase E: 아키텍처가 틀렸을 때의 폐기 (Scrap when the architecture is wrong)

구현 과정에서 스케치가 흡수할 수 없는 마찰이 계속해서 발생한다면 스케치를 과감히 버리세요. **redesign-from-first-principles** 및 **fix-root-causes** 원칙 스킬에 따라, 잘못된 설계 위에 임시방편 수정을 덧대지 마세요.

신호는 단일 사례가 아니라 *패턴*으로 나타납니다. 주요 징후는 다음과 같습니다:

- 서로 무관한 코드 전반에서 동일한 형태의 우회책(workaround)이 반복해서 등장함.
- 서로 무관한 여러 엣지 케이스가 모두 특수 분기(special-case branches)를 필요로 함.
- 컴파일을 위해 타입에 탈출구(`any`, 타입 캐스트, 실제로는 항상 설정되지만 선택적으로 선언된 필드 등)가 필요함.
- 스케치에서는 상태가 공유되지 않는다고 했는데 구현 중 "락(lock)이 필요하다"는 반사 반응이 나옴.
- 호출자가 추상화를 사용하기 위해 그 내부 규칙까지 알아야 함.
- 구현 전반에서 동일한 형태의 독립적인 Phase D 편차가 두 번 이상 발생함.

판단력을 발휘하세요. 몇 개의 엣지 케이스가 있다고 해서 아키텍처 전체가 틀린 것은 아닙니다. 어떤 문제는 본질적으로 복잡합니다. 데이터 자체의 복잡성은 설계의 복잡성과 다릅니다.

폐기할 때는 다음 절차를 따릅니다:

1. 지금까지 구축된 결과물에 대해 **how** 스킬을 다시 실행합니다.
2. **redesign-from-first-principles**에 따라, 새로 드러난 제약 조건들이 첫날부터 주어진 가정이었던 것처럼 재설계합니다.
3. **subtract-before-you-add** 원칙 스킬에 따라, 추가하기 전에 먼저 덜어냅니다. 새 스케치는 다시 커지기 전에 기존 스케치보다 작아야 합니다.
4. Phase B로 돌아가 arena를 재실행합니다.

## 산출물 (Outputs)

호출자의 사용 예제(usage)를 먼저 작성하고 그로부터 타입 스케치를 도출합니다. 작은 변경사항은 새 타입과 시그니처를 담은 단일 파일로 작성합니다. 규모가 큰 작업은 모듈 맵과 타입 정의들을 작성합니다. 설계 근거 문서는 `references/rationale-template.md` 형식에 맞추어 사용 스케치와 종합 결정을 포함해 함께 출하됩니다.
