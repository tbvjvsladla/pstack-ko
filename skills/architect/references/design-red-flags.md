# 설계 위험 신호 (Design red flags)

종합(synthesis) 전에 모든 후보를 이 기준으로 점검하세요. 위험 신호가 발견되면 설계 형태를 수정하거나 기각해야 합니다.

## 얕은 모듈 (Shallow module)

얕은 모듈은 넓은 인터페이스를 노출하면서 정작 숨기는 복잡성은 거의 없습니다. 모듈의 깊이는 공개 표면(public surface)의 크기 대비 그 뒤에 숨겨진 기능과 정책의 양으로 판단하세요. 실질적인 동작이 뒷받침되는 단순한 인터페이스를 선호하세요.

깊은 모듈(deep module)을 깊은 호출 체인(deep call chain)과 혼동하지 마세요. 깊은 호출 체인은 이해해야 할 내용을 여러 계층에 흩뿌립니다. 반면 깊은 모듈은 하나의 인터페이스 뒤에 기능을 집중시킵니다.

다음과 같은 징후를 살피세요:

- 호출자가 하나의 작업을 완료하기 위해 여러 메서드를 직접 조율해야 함.
- 공개 옵션이 내부 실행 단계나 구현 선택지를 그대로 노출함.
- 인터페이스를 배워도 구현 내부를 공부해야 하는 부담이 줄어들지 않음.

## 정보 누수 (Information leakage)

정보 누수는 여러 모듈이 동일한 내부 결정에 의존하게 만듭니다. 표현 방식, 정책, 또는 프로토콜 세부사항이 한 곳 이상에 나타나므로 이를 변경하려면 여러 곳을 동시에 수정해야 합니다.

전송(transport) 타입이나 와이어(wire) 타입을 공개 API로 재내보내기(re-export)하는 것은 정보 누수입니다. 외부 데이터는 인터페이스 뒤에서 도메인 타입으로 파싱하세요. 스토리지 스키마, 프레임워크 객체, 프로토콜 세부사항은 비공개로 유지하세요.

## 시간적 분해 (Temporal decomposition)

시간적 분해는 모듈이 소유한 지식이 아니라 실행 순서에 따라 모듈을 조직합니다. 로드(load), 검증(validate), 변환(transform), 저장(save) 단계를 별도 모듈로 나누면 하나의 표현 방식과 그 불변식이 여러 경계에 걸쳐 반복되기 쉽습니다.

도메인 지식과 소유권을 중심으로 코드를 그룹화하세요. 서로 다른 시점에 실행되는 메서드라도 동일한 결정을 보호한다면 하나의 모듈에 속할 수 있습니다.

## 패스스루 메서드 (Pass-through method)

패스스루 메서드는 동일한 형태의 다른 메서드에 동일한 인자를 그대로 전달하기만 합니다. 이는 복잡성을 숨기지 못한 채 계층만 하나 더 늘립니다.

이러한 메서드는 제거하거나, 실제로 작업을 완료할 수 있는 모듈로 책임을 이동시키세요. 전달 경계는 정책, 적응(adaptation), 또는 뚜렷이 구분되는 추상화를 추가할 때만 유지하세요.

## 분할 소유권 (Split ownership)

둘 이상의 모듈이 동일한 상태에 쓰기 작업을 하거나 각자 복사본을 유지하는 경우입니다. 한 작성자(writer) 모듈만 편집하는 에이전트는 다른 모듈을 볼 수 없으므로 규칙이 서로 어긋나게 됩니다.

각 상태 조각에는 단 하나의 소유자만 부여하세요. 다른 모듈은 상태를 읽기만 하거나 소유자에게 변경을 요청해야 합니다.

## 하나의 작업을 수행하는 두 가지 방법 (Two ways to do one task)

설계가 동일한 작업을 수행하는 방법을 둘 이상 지원하는 경우입니다. 에이전트는 가장 먼저 발견한 방식을 복사하므로, 모든 방식에 호출자가 계속 늘어나게 됩니다.

단 하나의 방법만 유지하세요. 동일한 변경 내에서 기존 호출자들을 다른 방식에서 이전시키고 이전 방식들은 삭제하세요.

## 임포트 가능한 내부 구현 (Importable internals)

호출자가 모듈의 내부 구현을 직접 임포트할 수 있는 경우입니다. 에이전트는 컴파일되는 가장 짧은 경로를 택하므로 내부 구현을 직접 임포트하게 되고, 결국 그것이 실질적인 인터페이스의 일부로 굳어집니다.

모듈 외부에서는 내부 구현에 접근할 수 없도록 차단하여, 외부에서 임포트를 시도하면 빌드가 실패하게 만드세요.

## 수동 동기화 목록 (Hand-synced list)

두 곳 이상에서 동일한 항목들의 목록을 나열하고 있어 항목 하나를 추가하려면 모든 목록을 편집해야 하는 경우입니다. 한 목록만 본 에이전트는 그 목록만 업데이트합니다.

단 하나의 목록만 유지하고 나머지 목록은 그로부터 도출(derive)하세요. 도출할 수 없는 경우라면 목록들이 서로 일치하지 않을 때 빌드가 실패하도록 만드세요.
