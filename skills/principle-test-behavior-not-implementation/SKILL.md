# 구현이 아니라 동작을 테스트하라 (Test Behavior, Not Implementation)

테스트는 코드가 사용자(호출자, 최종 사용자, 또는 다른 서비스)를 위해 무엇을 해주는지에 대한 주장입니다. 동작(behavior)이란 그 사용자들이 자신이 사용하는 인터페이스를 통해 관측할 수 있는 것입니다. 여기에는 반환값, 에러, 다시 읽어 들일 수 있는 상태, 그리고 전송된 요청이나 기록된 DB 행, 발행된 메시지처럼 코드 바깥의 시스템에 미치는 효과가 포함됩니다. 반면 구현(implementation)은 사용자가 관측할 수 없는 것입니다: 비공개 헬퍼 함수, 내부 호출 순서, 중간 단계 데이터, 그리고 어느 내부 협력 객체(collaborator)가 작업을 수행했는지 등입니다.

각 테스트를 두 가지 가상의 편집 상황에 비추어 평가하세요:

- **동작을 깨뜨려 보세요.** 코드가 잘못된 값을 반환하게 하거나, 부수 효과를 건너뛰게 하거나, 효과를 두 번 실행하게 만들어 보세요. 그래도 테스트가 여전히 통과한다면 그 테스트는 아무것도 증명하지 못하는 것입니다. 흔한 원인은 계약보다 느슨한 단언문(assertion), 테스트 대상 코드가 직접 계산해 낸 기댓값, 실제 읽는 코드를 실행하지 않은 채 상수나 프롬프트 문자열만 다시 적어놓은 테스트, 그리고 테스트가 스스로 조립한 데이터에 대한 단언문입니다.
- **내부 구현을 바꾸어 보세요.** 관측 가능한 모든 결과는 동일하게 유지한 채 내부 코드 구조만 재구성해 보세요. 이때 테스트가 실패한다면 그 테스트는 내부 구현에 묶여(pinned) 있는 것입니다. 그런 테스트는 리팩터링할 때마다 다시 작성해야 하면서도 정작 버그는 잡아내지 못합니다.

첫 번째 편집은 잡아내고 두 번째 편집에서는 살아남는 테스트만 유지하세요. 나머지는 다시 작성하거나 삭제하세요. 두 가지를 모두 만족하는 테스트를 작성하려면 구체적인 입력값을 사용해 사용자의 인터페이스를 통해 코드를 구동하세요. 기댓값은 코드 실행 결과가 아니라 요구사항으로부터 도출하세요. 계약이 약속하는 바를, 그보다 적지도 많지도 않게 정확히 단언하세요.

단언문의 형태가 아니라 계약이 무엇인가가 기준입니다. "빈 장바구니는 절대 결제되지 않는다"가 약속이라면, 결제 클라이언트가 호출되지 않았음을 확인하는 단언문은 동작을 테스트하는 것입니다. 이때 테스트가 실제로 호출을 감지할 능력이 있음을 보여주기 위해 결제가 일어나는 케이스를 짝지어 함께 구성하세요. 모킹된 외부 서비스가 수신하는 페이로드는 그 외부 서비스가 관측하는 대상이므로 동작입니다. 반면 내부 헬퍼 함수에 대한 호출은 어떤 사용자도 볼 수 없으므로 구현입니다. 빈 리스트는 일치하는 레코드가 없을 때는 정확한 정답이지만, 테스트가 단지 결과의 존재 여부만 확인하려 할 때는 속 빈 검증이 됩니다. 정확한 에러 메시지 문구를 단언하면 어떤 호출자도 읽지 않는 문장 표현에 테스트가 묶이게 됩니다. 호출자가 분기 처리의 기준으로 삼는 에러 타입이야말로 계약입니다.

테스트는 함수 호출 대신 두 테이블에 모두 존재해야 하는 키나 컴파일 타임 타입 체크 같은 불변식(invariant)을 고정할 수도 있습니다. 이때는 불변식이 곧 동작입니다.
