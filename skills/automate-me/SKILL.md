# Automate me

사용자의 작업 관례를 에이전트가 따를 수 있는 스킬로 변환하기 위한 가이드 플로우입니다. 산출물은 사용자에게 맞춤화된 단일 `-mode` 스킬입니다(예: `jay-mode`, `priya-mode`).

이 스킬은 세 가지 다른 요소를 조율(orchestrate)합니다: 인라인 마이닝 패스(1단계 참조), Cursor의 내장 `create-skill`(작성), 그리고 **unslop** 스킬(산문 규율)입니다. 이 스킬은 이들을 순서대로 연결할 뿐 대체하지 않습니다.

## 흐름 (Flow)

### 0. 기존 스킬 존재 여부 확인

사용자의 핸들(handle)과 일치하는 `.cursor/skills/**/*-mode/SKILL.md` 및 `~/.cursor/skills/*-mode/SKILL.md` 파일을 재귀적으로 탐색합니다. 모드 스킬은 최상위 경로뿐만 아니라 개인 카테고리 디렉터리(`.cursor/skills/<handle>/`) 안에도 위치할 수 있습니다. 기존 스킬이 존재한다면 (사용자가 이미 "내 스킬 업데이트해 줘" 등으로 말하지 않은 한) `AskQuestion`으로 의도를 확인하세요:

- 기존 스킬 업데이트 (반복 실행 시 기본값)
- 처음부터 새로 시작 (드문 경우로, 실행 전에 이유를 먼저 물어보세요)

업데이트 모드는 이후의 진행 흐름을 다음과 같이 바꿉니다:
- 1단계에서는 스킬이 마지막으로 편집된 시점(`git log -1 --format=%cI <path>`) 이후의 히스토리만 마이닝합니다.
- 2단계에서는 백지상태에서 무엇을 포착할지가 아니라 무엇이 바뀌었거나 빠졌는지를 질문합니다.
- 4단계에서는 기존 파일을 제자리에서 편집(in-place edit)합니다. 사용자가 반박하지 않은 섹션은 보존하고, 새로운 근거가 있는 섹션은 개정하며, 진정으로 새로운 규칙에 대해서만 새 섹션을 추가합니다.

### 1. 작업 히스토리 마이닝

병렬 탐색(fan out)을 시작하기 전에 현재 활성 워크스페이스의 트랜스크립트 위치를 파악합니다. 시스템 프롬프트에 워크스페이스의 `agent-transcripts/` 디렉터리 경로가 명시되어 있습니다. 오직 그 경로만 사용하세요. `~/.cursor/projects/*/` 전체를 글로빙(glob)하지 마세요. 그렇게 하면 워크스페이스 경계를 넘어 무관한 프로젝트의 비공개 대화를 읽게 됩니다.

해당 범위 내의 최근 에이전트 대화들을 조사하여 반복되는 패턴을 찾습니다. 히스토리 조각(slice)들에 걸쳐 여러 병렬 서브에이전트를 실행하세요(예: 최근 2~4주 분량을 3개의 조각으로 나누어 각 조각에 충분한 자료가 있게 함). **poteto-mode** 스킬의 Subagents 섹션에 따라 작업에 맞게 각 서브에이전트의 추론 수준과 속도(fast 또는 standard)를 선택하세요. 각 조각 마이닝 서브에이전트는 부모가 제공한 워크스페이스 범위 경로에서 트랜스크립트를 읽고, 아래 신호들을 탐색한 뒤, 발견한 패턴과 근거 포인터를 짧은 구조화 목록으로 반환합니다. 기본적으로 탐색할 가치가 있는 신호는 다음과 같습니다:

- 응답 선호도 (길이, 어조, 형식, "쉽게 풀어서 설명해 줘" 같은 교정 지시)
- 위임 습관 (서브에이전트, 모델 선택, 특화된 워크플로, 병렬 실행)
- 검증 태도 ("완료(done)"의 기준, 단위 테스트 대 라이브 재현, 리뷰어 활용)
- 코드 및 산문 규율 (스타일, 인용하는 원칙, 린트/포맷 도구)
- 프로세스 관례 (워크트리, 커밋, PR, 리뷰/머지 도구)
- 메타 선호도 (작업 도중 스킬 수정하기, 새 스킬 제안하기)

신호를 규칙으로 격상하기 전에 조각들 간에 교차 검증을 수행하세요. 2개 이상의 조각에서 관찰된 패턴은 신뢰도가 높습니다. 단 한 번만 나타난 신호는 약한 신호이므로 대개 제외합니다.

### 2. 사용자에게 직접 질문하기

마이닝만으로는 아직 대화에 등장하지 않은 의도를 놓칠 수 있습니다. 사용자에게 처음부터 직접 타이핑하게 하는 대신 `AskQuestion` 도구(구조화된 다지선다)를 사용하세요.

형태: 각각 4~6개의 선택지를 가진 질문 1~2개로 구성하며, 카테고리 질문에는 `allow_multiple: true`를 설정합니다. 폭넓은 질문("어떤 영역이 가장 중요합니까?")으로 시작한 뒤, 선택된 영역에 대해 구체적인 선택지로 후속 질문을 이어갑니다. 구조화된 질문 라운드가 끝난 후에는 자유 형식의 채팅 질문 하나로 선택지가 놓친 내용을 포착합니다.

질문 20개를 한꺼번에 쏟아내지 마세요.

### 3. 발견 사항 클러스터링

결합된 신호들을 섹션별로 그룹화합니다. 일반적인 섹션은 다음과 같습니다(해당되는 것만 사용하세요):

- **Response style (응답 스타일)**: 길이, 어조, 형식.
- **Autonomy (자율성)**: 질문 없이 스스로 처리할 범위, MCP 도구 사용.
- **Understand first (선행 이해)**: 변경 범위를 잡거나 조사할 때 먼저 찾을 스킬.
- **Subagents (서브에이전트)**: 기본값, 병렬성, 작업별 모델 매핑, 특화된 워크플로.
- **Prose / code discipline (산문 / 코드 규율)**: 원칙, 린트 도구, 스타일 가이드.
- **Review and verify (리뷰 및 검증)**: 재현 태도, 검증 스킬, 라이브 테스트 도구.
- **Process (프로세스)**: git worktree, 커밋, PR, 리뷰/머지 도구.
- **Skills (스킬)**: 스킬 작성 습관, 스킬 우선 수정(fix-the-skill-first), 새 스킬 제안.

**poteto-mode** 스킬이 전체적인 형태를 보여줍니다. 세밀도(granularity)를 참고하기 위해 읽어보되, 내용은 복사하지 마세요. 사용자의 규칙은 poteto-mode의 규칙과 같지 않습니다.

### 4. 스킬 초안 작성

Cursor의 내장 `create-skill` 스킬을 사용하여 스킬을 작성합니다. 배치 위치 및 설정:

- 경로(Path): 기존 모드 스킬이 있다면 그 카테고리를 유지합니다. 새로운 모드를 만들 때 저장소에 이미 해당 핸들의 개인 카테고리가 자리 잡고 있다면 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`를 사용합니다. 그렇지 않다면 프로젝트 내 `.cursor/skills/<handle>-mode/SKILL.md`(또는 사용자가 개인 전역 스킬을 선호한다면 `~/.cursor/skills/<handle>-mode/`)를 기본값으로 사용합니다.
- 핸들(Handle): 사용자의 이름(first name) 또는 선택한 식별자.
- Frontmatter `description`: "코드 작성"이나 "PR 리뷰" 같은 일반적인 키워드가 아니라, 사용자의 이름 + `/<handle>-mode` + "그들의 스타일로 작업(work in their style)"에 트리거되도록 작성합니다.
- Frontmatter 포맷팅: `create-skill`의 YAML 규칙을 따릅니다. `description`은 단일 YAML 스칼라로 유지하세요. 문장 부호나 줄바꿈이 필요한 경우 큰따옴표로 감싸거나 들여쓰기된 연속 줄과 함께 `description: >-`를 사용하세요.
- Frontmatter `disable-model-invocation: true`를 기본값으로 설정합니다. 사용자가 자신의 모드를 매 턴마다 자동으로 적용하기를 명시적으로 원할 때만 이를 해제(opt out)합니다.

### 5. 산문 다듬기 (Iterate on prose)

모든 줄에 **unslop** 스킬과 `create-skill`의 작성 가이드라인을 적용합니다.

사용자에게 초안을 보여주고 피드백을 받으세요. 여러 번의 반복 수정을 예상해야 합니다. 가차 없이 덜어내세요. 모드 스킬은 매뉴얼이 아닙니다.

### 6. 반영하기 (Land it)

main에서 분기한 워크트리(worktree)에서 작업합니다. 커밋하고 PR을 여세요. main에 직접 푸시하지 마세요.

## 가드레일 (Guardrails)

- **단 하나의 대화에 과적합(overfit)하지 마세요.** 한 번 언급되었다가 다른 때에는 반박된 선호도는 노이즈입니다. 규칙으로 성문화하기 전에 여러 사례가 있는지 확인하세요.
- **기교를 부리지 마세요.** 다른 스킬의 내용을 다시 서술하거나, 은유를 발명하거나, 에이전트 독자를 위해 "시적인" 문장을 쓰는 것은 실익 없는 비용입니다. 실무적이고 작동 가능한(operational) 문장으로 유지하세요.
- **인라인으로 붙여넣지 말고 참조하세요.** 사용자가 의존하는 다른 스킬들은 발췌문을 붙여넣는 대신 경로 참조로 표시해야 합니다. 사용자가 다른 곳에서 관리하는 원칙 문서들도 마찬가지입니다.
- **섹션을 최소한으로 유지하세요.** 사용자가 해당 영역에 대해 구체적이고 기본값이 아닌 고유 규칙을 가지고 있을 때만 섹션을 추가하세요. "명확하게 소통하라"는 섹션이 될 수 없습니다. "짧은 단락. 선택지를 비교할 때는 표 사용. 항목들이 진정으로 대등할 때만 불릿 사용."은 섹션이 될 수 있습니다.
- **지칭 관례를 일반화하세요.** 명령문에서는 작성자의 이름 대신 "사용자(the user)" 또는 "인간(the human)"을 사용하세요.
- **대칭성을 억지로 강제하지 마세요.** 사용자에게 적어둘 만한 프로세스 규칙이 없다면 Process 섹션 전체를 아예 건너뛰세요.

## 평가 (Evaluation)

`-mode` 스킬은 주관적인 산출물입니다. `create-skill` 스타일의 테스트/반복 벤치마크 루프는 여기서는 유용하지 않습니다. 사용자와 함께 감각 점검(vibe-check)을 수행하세요: 사용자다운 글로 읽히는가? 빠뜨린 것은 없는가? 확인되면 출하합니다.

실제 사용 중에 스킬의 트리거 정확도가 문제로 드러나는 경우에만 설명(description) 최적화 루프를 실행하세요.

## 사용하지 말아야 할 때 (When not to use)

- 사용자가 (작업 관례가 아니라) 특정 과제 전용 스킬을 원할 때: 마이닝 없이 `create-skill`만 단독으로 사용하세요.
- 사용자가 하나의 좁은 워크플로(예: "내가 커밋 메시지를 작성하는 방법")만 포착하고 싶어 할 때: 그것은 모드 스킬이 아니라 일반 스킬입니다.
