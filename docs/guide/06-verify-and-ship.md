# 결과 검증 및 PR 열기

"컴파일됩니다"는 증거가 아닙니다. [Prove It Works 원칙](../../skills/principle-prove-it-works/SKILL.md)은 에이전트가 성공을 보고하기 전에 실제 아티팩트를 확인하게 만들며, 여러분의 역할은 그 "실제 아티팩트"를 확인 가능하게 만드는 것입니다. 이 페이지에서는 완료 조건 명시하기, 측정된 수치 검증하기, 앱용 검증 스킬 생성하기, 일반 테스트가 거의 닿지 못하는 속성을 정형 검증하기, PR 열기, 그리고 머지까지 이끌기를 다룹니다.

대부분의 에이전트 작업에서 가장 느린 단계는 검증인데, 대개 사람을 기다리는 단계이기 때문입니다. 에이전트가 직접 검증할 수 있게 만들면 여러분이 병목이 되는 일이 사라집니다. 반대로 이 과정을 건너뛰면 에이전트를 더 많이 돌릴수록 여러분이 직접 확인해야 할 미검증 작업물만 더 쌓일 뿐입니다.

## 처음부터 완료 조건 명시하기

첫 번째 프롬프트에 완료가 무엇을 의미하는지 편한 말로 적어 넣으세요:

```text
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

이제 에이전트에게는 막연한 기분을 맞추는 대신 직접 실행해 볼 수 있는 세 가지 검사 기준이 생겼습니다. 응답이 돌아올 때는 실행한 정확한 명령어와 출력이 함께 담겨 있어야 합니다. 검사를 실행할 수 없었다면 좋은 응답은 "판단 불가(inconclusive)"라고 말합니다. 증거 없이 자신만만한 응답은 경고 신호입니다.

변경 내용에 맞게 검사 방식을 맞추세요:

- CLI 변경은 실제 명령어를 실행합니다.
- UI 변경은 실행 중인 앱에서 변경된 플로우를 직접 밟아봅니다. 레퍼런스와 픽셀 단위로 정확히 일치해야 할 때는 [Visual parity 플레이북](../../skills/poteto-mode/playbooks/visual-parity.md)이 눈대중으로 판단하는 대신 고정된 베이스라인과 스크린샷 diff를 비교합니다.
- 파서나 마이그레이션은 저장된 입력을 리플레이합니다.
- 성능 변경은 전후 프로파일을 비교합니다.
- 스토리지 변경은 기록된 값을 다시 읽어 확인합니다.

직접 눈으로 검사할 수 있는 아티팩트 형태로 증거를 요청하세요: 먼저 실패하는 테스트와 이어서 통과하는 테스트, 전후 비교 비디오, 트레이스, 스크린샷 등입니다. 수정 사항이 이미 머지되었다면 `main`에서 동일한 검사를 다시 실행해 달라고 요청하세요. 전체 실행을 다시 돌려보지 않고도 이의를 제기할 수 있기 때문에 아티팩트 하나가 그럴듯한 설명 백 마디를 이깁니다.

완전히 신뢰하기 어려운 작은 diff의 경우 [`/blast-radius`](../../skills/blast-radius/SKILL.md)가 다른 어디를 깨뜨릴 수 있는지 찾아냅니다. 변경이 안전하다는 핵심 근거 하나를 찾아내고 말로 주장하는 대신 실제 코드를 실행하여 그 사실을 증명합니다.

## `/benchmark-checklist`로 측정된 수치 검증하기

전후 비교 수치는 실수로 잘못된 증거를 만들기 가장 쉬운 영역입니다. 웜 캐시(warm cache), 한쪽에만 적용된 디버그 빌드, 또는 시간 측정 구간 바깥에서 실행된 작업은 모두 그럴듯한 속도 향상을 만들어낼 수 있습니다. 수치를 보고하거나 그에 따라 행동하기 전에 다음과 같이 입력하세요:

```text
/benchmark-checklist vet the export speedup before it goes in the pr
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md)는 일곱 가지 질문을 던지고 각각에 대해 실제 실행에서 나온 증거를 요구합니다:

1. 무엇이 이 수치를 제한(limit)하며, 왜 두 배 더 빠르지 않은가?
2. 모든 비교 대상이 프로덕션과 동일한 방식으로 튜닝되어 실행되었는가?
3. 결과가 디스크 대역폭이나 코어 수 같은 물리적 한계를 위배하지는 않는가?
4. 에러가 발생하거나 잘못된 출력을 반환한 것은 없는가?
5. 교차 반복 실행(alternating runs)에서도 중앙값과 범위로 재현되는가?
6. 사용자가 기다리는 경로에서 엔드투엔드로 유의미한 차이가 있는가?
7. 해당 작업이 실제로 시간 측정 구간(timed region) 안에서 일어났는가?

판정 결과는 실행 횟수, 범위, 병목 요인(limiter)과 함께 더 빠름(faster), 더 느림(slower), 측정 가능한 차이 없음(no measurable difference), 또는 판단 불가(inconclusive)로 돌아옵니다. 병목 요인을 지목할 수 없거나 어느 한쪽이 튜닝되지 않은 채 실행되었다면 판단 불가로 판정합니다. `/poteto-mode`는 이미 Perf issue 및 Hillclimb 플레이북 내부에서 이 체크리스트를 실행하므로, 그 밖에서 무언가를 측정했거나 다른 사람의 수치가 지나치게 좋아 보일 때 직접 입력하면 됩니다. 이 스킬은 [Explain the Number 원칙](../../skills/principle-explain-the-number/SKILL.md)을 실무용으로 구현한 형태입니다.

## 프로젝트 검증 스킬 생성하기

앞서 언급한 UI 검증 항목에는 중요한 전제 조건이 하나 숨어 있습니다. 에이전트가 앱을 구동할 수 있는 스크립트 수단이 있어야 한다는 점입니다. 프로젝트에 이미 그런 수단이 있다면 훌륭합니다. 없다면 다음을 실행하세요:

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md)은 여러분이 아니라 저장소를 인터뷰합니다. 사용자가 무엇을 건드리는지, 앱이 로컬에서 어떻게 실행되는지, 무엇으로 구동할 수 있는지(기존 하네스 우선, 없으면 브라우저 및 CDP, PTY 또는 일반 HTTP), 어떤 증거가 동작을 증명하는지, 그리고 두 인스턴스를 나란히 실행할 수 있는지를 스스로 파악합니다. 코드만으로 답할 수 없는 것만 여러분에게 묻습니다.

이 스킬은 `.cursor/skills/verify-<app>/`을 작성합니다. 여기에는 정확한 Launch, Doctor, Drive, Evidence, Cleanup 섹션을 갖춘 에이전트용 지침, 함께 제공되는 스크립트를 위한 Helpers 섹션, 그리고 앱이 하는 일과 각 기능이 작동함을 증명하는 결과를 색인한 `features/` 아래의 기능 맵(feature map)이 포함됩니다. 또한 이 스킬은 README 색인과 네 개의 필수 H2 헤딩을 사용하는 기능별 파일로 구성된 [기능 맵 작성 예시](../../skills/create-verification-skill/references/feature-map-example/)를 함께 제공합니다. 생성기는 결과물을 넘겨주기 전에 실행, doctor 점검, 기능 하나 구동, 증거 캡처, 정리(clean up), 그리고 정리 후에도 증거가 잘 남아 있는지 확인하는 엔드투엔드 증명을 1회 수행합니다. 이 증명이 실패하면 출력된 결과물을 사용하지 마세요.

그 이후부터 "앱에서 검증해(verify it in the app)"라는 말은 이 저장소의 어떤 에이전트든 별도의 셋업 대화 없이 바로 실행할 수 있는 단계가 됩니다. 특정 형태의 증거를 원할 때는 프롬프트에 스킬 이름을 직접 적으세요:

```text
/poteto-mode build the bulk-archive action. use /verify-<app> to verify your changes and show me a video and screenshots as proof.
```

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

검증 스킬이 작동하기 시작하면 [`/swarm`](../../skills/swarm/SKILL.md)으로 전체 검증 패스를 기능 맵 항목별로 쪼개어 병렬 실행하고 결과를 집계할 수 있습니다. 또한 검증자 스웜은 충분히 큰 표본에 대해 성능 개선을 확인하거나 PR을 배포하기 전에 회귀 버그를 찾기 위해 앱을 퍼징(fuzz)할 수도 있습니다.

검증 스킬을 일회용품이 아니라 인프라로 취급하세요. 커밋해 두어 팀의 모든 사람과 모든 에이전트가 동일한 방식으로 앱을 구동하게 만드세요. 그런 다음 [지렛대를 구축하세요(build the lever)](../../skills/principle-build-the-lever/SKILL.md). 에이전트들이 앱을 클릭하기 위해 일회용 스크립트를 반복해서 작성하고 있다면, 스킬이 대신 호출할 수 있는 작은 컨트롤 CLI를 만들어 달라고 요청하세요. 에이전트가 소비하는 토큰이 줄어들고 모든 실행이 재현 가능해집니다. 에이전트가 잘 다루는 CLI는 다음과 같은 특징을 가집니다:

- 얇은 명령어 여러 개 대신 각각 실질적인 작업을 수행하는 조합 가능한(composable) 소수의 명령어.
- 파괴적인 작업에 제공되는 `--dry-run` 옵션.
- 모든 기능을 한꺼번에 쏟아내는 대신 점진적으로 기능을 드러내는 서브커맨드.
- 대신 무엇을 해야 하는지 알려주는 에러 메시지.
- 풍부한 `--help` 텍스트.
- JSON과 같은 기계 판독 가능(machine-readable) 출력.

이 작업을 하는 김에 개발 환경 셋업도 재현 가능하게 만드세요: 시드 데이터, 테스트 사용자, 그리고 매번 똑같은 방식으로 환경을 띄우는 단일 명령어를 갖추는 것입니다.

## 검증 스킬을 최신 상태로 유지하기

앱은 계속 바뀌고 기능 맵은 금방 낡습니다. 아무도 일일이 기억할 필요가 없도록 가급적 스케줄링된 자동화를 통해 최소 하루에 한 번은 다음을 실행하세요:

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md)은 생성된 스킬을 감사합니다. 기능당 하나씩 읽기 전용 소스 리더를 병렬로 돌린 다음, 매핑된 모든 기능을 실제로 구동하는 라이브 패스를 1회 실행합니다. 실행은 정확히 세 가지 결과 중 하나로 끝납니다. `clean`은 전체 커버리지가 이상 없고 수정할 것이 없음을 뜻합니다. `changed`는 검증 스킬 자신의 디렉터리 안으로만 한정된, 입증된 수정 사항을 담은 단일 PR을 뜻합니다. `blocked`는 차단 요인을 명시합니다. 이 스킬은 제품 코드를 절대 편집하지 않습니다. 라이브 패스가 제품의 회귀 버그를 잡아내면 문서를 고쳐 이를 숨기는 대신 회귀 버그로 보고합니다.

## 정형 검증 스킬로 속성 증명하기

검증 스킬은 여러분이 구동하는 경로들을 증명합니다. 하지만 어떤 버그들은 아무도 직접 구동해 보지 않는 경로에 숨어 있습니다: 두 재시도가 겹치는 경우, 쓰기 도중 락(lock)이 만료되는 경우, 상태 변경이 순서가 뒤바뀌어 도착하는 경우 등입니다. 일반 테스트는 그런 케이스에 거의 도달하지 못합니다. 이러한 버그의 비용이 큰 코드에는 다음을 실행하세요:

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md)은 코드에서 대상을 고릅니다: 깨졌을 때 사용자에게 피해를 주고 일반 테스트가 깨지는 케이스에 좀처럼 닿지 못하는, 코드가 지켜야 할 약속(promise)입니다. 검증하기 가장 쉬운 대상이 아니라 가장 중요한 대상을 고릅니다. 특정 영역이나 버그에서 시작하고 싶다면 직접 지정하세요:

```text
/create-formal-verification-skill the job lease and retry logic. a job must never run twice at once.
```

질문이 도구를 결정합니다. 이벤트들이 잘못된 순서로 일어날 수 있는지의 문제는 설계의 작은 모델 위에서 모델 체커(model checker)를 돌리는 것이 적합하며, 어떤 언어에서든 그 기본값은 TLA+입니다. 코드가 모든 입력에 대해 올바르게 동작하는지의 문제는 실제 코드 위에서 돌아가는 검증기(verifier)가 적합합니다. 사용 중인 언어에서 실행되는 검증기가 없다면 에이전트는 그 사실을 알리고 수작업으로 만든 함수 모델이 아니라 생성된 입력들로 실제 코드를 테스트합니다. 모든 크기에서 성립해야 하는 속성에는 수학적 증명(proof)이 필요할 수 있습니다. 에이전트는 어떤 도구를 왜 선택했는지 알려줍니다.

이 스킬은 속성 하나를 검증하고, 깨진 코드 배리언트에서 해당 속성이 실제로 실패하는 모습을 보여줍니다. 실패하는 것을 한 번도 본 적 없는 검사는 아무것도 증명하지 못하기 때문입니다. 현재 코드가 이미 그 속성을 위반하고 있다면 코드의 용어로 된 짧은 단계 시퀀스 형태의 반례(counterexample)를 얻게 됩니다. 속성은 명시된 그대로 유지되므로 발견 사항은 온전한 발견 사항으로 남습니다. 여러분이 요청하지 않는 한 제품 코드는 바뀌지 않습니다.

또한 다음 에이전트에게 변경 사항이 검증된 코드를 건드리는지 여부, 명령어 하나로 검사를 실행하는 방법, 그리고 실제 버그와 모델링 오류를 구별하는 방법을 알려주는 프로젝트 로컬 스킬을 작성합니다. 생성기는 결과물을 넘겨주기 전에 속성을 깨뜨리는 스크래치 변경에 대해 해당 스킬을 직접 한 번 따라가 보며, 검사가 이를 반드시 잡아내야 합니다. 인계 보고서는 무엇을 어떤 도구와 범위(bounds)로 검증했는지, 검사가 무엇을 찾아냈는지, 그리고 무엇은 다루지 않는지를 명시합니다. 통과(pass)는 모델이나 범위 안에서의 통과를 의미할 뿐 전체 시스템의 무결성을 의미하지는 않습니다.

스킬은 또한 각 검사가 어느 코드를 다루는지와 검사가 마지막으로 코드와 일치했던 커밋을 기록합니다. 스킬을 건너뛴 머지나 리팩터링이 일어나면 이미 사라진 코드의 설명에 대해서만 검사가 계속 통과하는 상태가 될 수 있습니다. 그런 작업 뒤에는 [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md)을 실행하세요. 코드로부터 검증을 업데이트하고, 다시 실행하며, 업데이트된 각 검사가 여전히 실패를 잡아낼 수 있음을 보여주고, 각 실패가 검증의 드리프트인지 코드의 실제 버그인지 알려줍니다.

## 상태차트(Statechart)로 동작 보여주기

모델 용어로 된 반례는 엔지니어인 여러분을 납득시킵니다. 하지만 해당 동작을 소유한 PM이나 디자이너는 그들의 용어로 된 모습을 눈으로 보아야 합니다. 다음을 실행하세요:

```text
/statechart what the user sees when they edit a note offline
```

[`/statechart`](../../skills/statechart/SKILL.md)는 TLA+ 모델로부터 생성된, 사용자에게 보이는 모습의 Mermaid 상태차트를 그립니다. 따라서 그림과 검사된 모델이 서로 어긋날 수 없습니다. 읽는 이의 규칙("오프라인 상태에서는 Synced가 절대 보이면 안 된다")은 불변식(invariant)이 됩니다. 차트는 규칙을 위반하는 각 상태를 표시하고, 보고서는 읽는 이의 단어로 거기까지 가는 최단 경로를 제시합니다. 인계하기 전에 에이전트는 실제 코드에서 각 버그 경로를 재현하므로 모델링 오류가 버그로 둔갑해 읽는 이에게 전달되지 않습니다.

## PR 열기

```text
/poteto-mode open the pr. small ordered commits, evidence in the description.
```

[Opening a PR 플레이북](../../skills/poteto-mode/playbooks/opening-a-pr.md)은 워크트리에서 작업하며, 작업 내용을 정돈된 작은 커밋들로 리베이스하고, diff를 정리하며, 산문에서 슬롭을 걷어내고, PR 링크를 반환합니다. 뚱뚱한 PR 하나보다 좁은 범위의 PR 다섯 개가 낫고, 끝없이 커지는 브랜치보다 스택으로 쌓아 올린 후속 PR들이 낫습니다.

## Babysit으로 PR을 머지 준비 상태까지 이끌기

열린 PR에는 즉시 차단 요인(blocker)들이 쌓이기 시작합니다. CI 검사가 실패하고, 리뷰어가 코멘트를 달고, 트렁크(trunk) 브랜치가 앞으로 나아갑니다. 그러한 반복 작업을 [Babysit 플레이북](../../skills/poteto-mode/playbooks/babysit.md)에 맡기세요:

```text
/poteto-mode babysit this pr. get it green.
```

Babysit은 GitHub의 번들 워처(watcher)나 (사용 가능한 경우) Origin CLI를 통해 PR을 감시하며, 충돌 해결 → 리뷰 스레드 대응 → CI 통과 순서로 차단 요인을 처리합니다. 알려진 모든 수정 사항은 한 번의 푸시로 묶어서(batch) 반영하므로 수정할 때마다 매번 검사가 다시 시작되는 대신 한 번만 다시 시작됩니다. 사람과 봇 모두 진짜 문제와 단순 잡음을 같은 목록에 섞어서 남기기 때문에 코멘트 트리아지는 회의적인 시각으로 수행됩니다. 진짜 발견 사항은 수정을 거치고, 잡음은 스레드에 반증(disproof)을 게시하며 기각합니다. 단순히 현재 상태만 알고 싶을 때는 짧게 물어보면 Babysit이 루프를 시작하지 않고 바로 답해줍니다:

```text
/poteto-mode check on pr 123. anything outstanding?
```

Babysit은 머지 준비 완료(merge-ready) 상태에서 멈춥니다. 모든 검사가 그린이더라도 절대 직접 머지하지 않는데, 머지는 별개의 의사결정이기 때문입니다.

## Shipping으로 스택 랜딩하기

그린 상태라는 것과 안전하다는 것은 같지 않습니다. 랜딩할 준비가 되었을 때 명시적으로 말하세요:

```text
/poteto-mode land the stack.
```

[Shipping 플레이북](../../skills/poteto-mode/playbooks/shipping.md)은 무언가를 실행에 옮기기 전에 각 PR을 독립적으로 검증합니다. PR당 하나의 새로운 에이전트가 라이브로 동작을 증명하며, 변경을 심판하는 에이전트는 절대 그 코드를 작성한 에이전트가 아닙니다. 그런 다음 Shipping은 아래에서부터 연속으로 검증이 완료된 구간만을 기본적으로는 GitHub을 통해(또는 CLI를 사용할 수 있는 경우 Origin을 통해) 한 번에 하나의 PR씩 랜딩하고, 사슬을 끊는 첫 번째 PR을 보고합니다. 검증되지 않은 PR 위에 놓인 검증된 PR은 대기하는데, 이를 먼저 머지해 버리면 그 아래의 미검증 구간까지 함께 끌려 들어가기 때문입니다.
